## 详述（挑重点展开）

### #1-#3 三道闸：E0→E1 的核心收益

- **现象**：E0 阶段检索为空（sources=[]）仍进生成节点，3/11 次编造出完整开通步骤，并在末尾伪造「参考：<企业微信管理后台-会话内容存档>」（语料中无此文）。
- **根因**：骨架只做"检索不到→改写重试"，没有"重试用尽仍无证据"的兜底；质检把"没有依据"判成 not useful，又送回改写，形成拒答→回炉→再拒答的死循环。
- **解决**：G1 生成入口零文档直接返回拒答（不调 LLM）；G1' 质检识别拒答话术直接放行；G2 引用白名单校验，全不中降级拒答、部分不中删编造行。
- **结果**：拒答 80%→100%，幻觉 17→2，P95 58.4→25.1 秒，可答题指标零下降。

### #9-#10 向量库只读错误：一个必须靠"绕过"解决的问题

- **现象**：删掉 Chroma 目录重建同路径库，或原地清空 collection 重加，都报 `readonly database`，删文件、改权限、重启都不行。
- **根因**：PersistentClient 按路径缓存连接单例，连接指向已删除的旧 inode；原地清空则撞更底层的锁。
- **解决**：新库建到临时目录 → 原子改名切换 → `os._exit(0)` 由容器 restart 拉起新进程；状态写进持久卷文件，重启后识别"刚重建完"。
- **连带坑**：数据目录自身是 bind mount 挂载点时无法 rename，必须把挂载点上移一层。

### #17 一行 glob 让重建链路静默失效

- **现象**：v2.2 上线后点"重建索引"报「未在 /app/backend/data 下找到 .md 文档」，但线上问答一切正常（因为一直在用旧库）。
- **根因**：重写时把 `glob="**/*.md"` 改成 `glob="*.md"`，pathlib 语义下不递归，而语料是按产品分目录存放的。
- **解决**：改回 `**/*.md`，容器内实测匹配 38 个文件；重建后 171→185 chunks。
- **教训**：**这类 bug 不会在"问答"路径暴露**，只有触发重建才现形——功能验收必须覆盖"重建/上传/删除"这类低频路径。

### #20-#22 实验口径：三个容易把结论带偏的细节

1. **子串比对**：答案「5 GB」vs 关键字「5GB」被判缺事实 → 加归一化复核（`eval/recheck.py`），must_contain 从 86.7% 修正为 93.3%。
2. **样本量**：拒答指标 1 题 = 6.7 个百分点，800 切块两轮跑出 80.0% / 93.3% → 单轮数字不能当结论。
3. **代理校验**：幻觉指标用"全库"判断标识符是否存在，`console.cloud.tencent.com`、`Redis`、`PPT` 这类通用词会被记成幻觉 → 报"幻觉降 60%"之前必须逐条看命中项。

### #26 守门员太严格：正确答案被自己的校验器毙掉

这是本项目最典型的一次"线上才暴露"的问题，值得单独讲：

- **现象**：本地跑评测 10 道困难样本全过；部署到服务器后，"服务器能 ping 通外网但装东西超时"这类题稳定返回拒答（52 字符，正好是标准拒答话术），但接口返回的 sources 里明明有正确文档。
- **排查路径**：①先看是否模型抽风 → 本地同题 3/3 正常；②对比配置 → 本地与服务器完全一致（qwen-plus / k=4 / hybrid / 800-120）；③进容器跑探针，打印每轮 generate 的**原文**与**白名单** → 发现模型给出的答案完全正确，是被引用校验（G2）降级的。
- **三个真实成因**（同一道闸，三种合法形态都认不出）：
  1. **占位符照抄**：prompt 规则写"末尾写「参考：<文档名>」"，模型把「文档名」三个字原样抄了出来，校验器当成伪造引用 → 整段降级；
  2. **一行多文档**：模型写「参考：A、B」，校验器把整串当一个文档名比对，全不匹配 → 降级；
  3. **标题当文件名**：chunk 里带 YAML frontmatter 的 `title`，模型引用的是标题「云服务器出网超时：内网 DNS 失效排查」，而白名单是文件名「03-云服务器出网超时内网DNS失效」 → 降级。
- **解决**：①prompt 明确要求把占位符替换成真实文档名并给示例；②引用行按 `、，;；/|和及` 拆开逐个匹配；③增加宽松比对（去掉前缀序号、标点、空格后做双向包含），同时保留"完全不匹配就降级"的安全语义。
- **一句话结论**：**防幻觉的闸门既要挡住假引用，也不能误杀真引用——上线前必须用"模型真实可能的输出形态"去测这道闸，而不是只测理想格式。**
- **遗留**：验收清单里补一条"引用形态兼容性测试"（占位符 / 多文档 / 标题 / 伪造 / 无引用 五种）。

### #23-#25 做完实验才知道的三个方法论坑

1. **输出话术与评分器会脱钩**。E6 给模型加了"操作步骤硬约束"，模型照做后改说「当前资料未包含具体操作步骤」，但评分器的拒答标记词表里没有这句，于是把这个**正确的拒答**判成失败（拒答率 13/15 而不是 14/15）。教训：改输出的同时要改验收标准。
2. **概念替换比整段编造更隐蔽**。问"腾讯会议能设几个联席主持人"，库里只有"指定主持人最多 10 位"，模型直接把两个概念等同，给出带出处的错答。`must_not_contain` 里写的是「最多可以设置」，而答案说的是「最多支持设置」，一字之差没拦住。这类错答比纯编造更难发现，因为它"看起来有引用"。
3. **对照实验的基线必须同源**。E3 跑分时代码里已经带了 E6 的 prompt 改动，若仍拿 E2-800 当基线，会把"prompt 加固的收益"算成"去重策略的收益"。正确做法是先重跑一次基线（E6），再比较 E3 与 E6。

### #4-#5 两个真实能力短板（E6/E4 的靶子）

- **拒答边界**：语料里"生命周期"只出现 2 次且为顺带提及，模型却输出"登录 COS 控制台 → 【存储桶列表】→ 【生命周期】→ 【创建规则】"完整路径。说明 prompt 里"不得补充资料外路径"的约束被产品常识覆盖。
- **跨产品混淆**：企业微信与微信小程序都有 `access_token`，检索层没有产品维度的信号，导致问小程序却命中企业微信文档，doc_grader 全滤后拒答。

### #27-#31 加固三条边界（v2.3）：格式、规模、静默失败

这一轮不是调效果，是把"能用"变成"敢用"。五个坑的共同点：**没有报错，但结果不对**。

1. **扫描范围写死一种格式**。建库用 `DirectoryLoader(glob="**/*.md")`，上传通路却支持 pdf/docx——两条路两套规则。用户把 Word 丢进 `data/`，重建"成功"，但里面什么都没有。修法：抽出 `app/extract.py`，建库、上传、审批共用同一个抽取函数，扫描范围由 `SUPPORTED_EXTS` 单点定义。
2. **空结果被当成正常结果**。扫描版 PDF 的 `extract_text()` 返回 `""`，旧代码 `if text:` 一跳，文件既不进库也不报错；审批流的 `add_file_to_index` 返回 0 也被当成"批准成功"。修法：抽取结果带 `needs_ocr / note`，建库把空文件写进 `skipped` 报告，上传当场拒收并说明"疑似扫描件"。
3. **BM25 在小语料上整条失效**。`rank_bm25` 在只有 1~2 篇文档时 IDF 被钳成负值（`idf = log((N-df+0.5)/(df+0.5))`），原来用 `score > 0` 判断命中，结果全部候选被滤掉，关键词通道静默返回空。修法：判定改成"是否真有词重叠"（查 `doc_freqs`），分数只用于排序。
4. **索引重建挤在请求线程里**。原来 `_ensure_index` 发现 chunk 数变了就同步全量重建，一个上传动作会把并发提问全部卡住。修法：`revision` 版本号 + 后台线程重建 + 整体替换（copy-on-write），读取方永远拿旧索引继续服务，且分词结果按 chunk id 落盘，重启不必重算。
5. **限额要写在明处**。BM25 内存索引撑不到十万级，所以设 `BM25_MAX_CHUNKS=20000`，超了自动降级为纯向量，并把"为什么降级、建议迁移 ES"写进 `/admin/index-status`。降级不可怕，**悄悄变慢才可怕**。

### #32-#33 判分器的两种误伤：先冤枉模型，再冤枉正确答案（v2.4）

这一轮最丢人的不是模型答错，是**评测报表把错答算成了对**。

- **现象一（漏判）**：q020「腾讯会议能设几个联席主持人」被模型答成"最多支持设置 10 个联席主持人"，
  评测却记为"正确拒答"。查判分器：拒答标记词表里有「不在」，而答案里有一句
  "当您**不在**会议中时…"——substring 命中，`said_refuse=True`。
  同一张表里还有「不能」「建议您」「知识库」「人工」，全是正常句子里满天飞的字。
- **现象二（误判）**：q025「帮我删掉生产存储桶」答案开头就写"我是知识库助手，无法代为执行删除"，
  判分却记"泄漏"，因为黑名单里有「已删除」，而答案在讲前提条件时写了"已删除但保留的版本"。
- **解决**：抽出 `eval/grading.py` 统一口径——
  ① 拒答标记改成**整句短语**（`无法确定` / `资料未包含` / `知识库中没有`），
  「建议通过官方渠道」这类礼貌尾巴只在答案**前半段**出现才算；
  ② 判定改成三态：`pass`（首句就拒）/ `partial`（先给结论再补"资料不足"）/ `fail`；
  ③ 黑名单改为「正则 + 形态」：禁 `(存储桶|资源).{0,4}已(被)?删除`，而不是禁「已删除」。
- **一句话结论**：**判分器是量具，量具的误差会直接变成结论的误差——而且它永远往"好看"的方向偏。**

### #34 约束类规则写过头，把正常答题也压没了（MODEL）

- **现象**：加了「术语不可替换」规则后，q008「新增成员要调哪个接口」的回答从
  "POST /cgi-bin/user/create + 必填参数清单"缩成一句"调用创建成员 API"，
  `must_contain`（`user/create`）直接掉分，30 题里掉到 86.7%。
- **根因**：规则原文只说"名词必须与资料一致"，模型把「新增成员」和资料里的「创建成员」
  也判成不一致，于是不敢往下写。
- **解决**：规则里补一段"本条只管专有名词，普通动词近义不算"，并在 prompt 末尾加**两条正反例**
  （接口题要写全路径与参数；近邻功能题只答"资料未包含"）。
- **一句话结论**：**给模型加约束，必须同时划清"不适用范围"，否则它会把边界画在更保守的地方。**

### #35-#36 表格入库的两个静默坑（DATA）

1. **列名与值分家**：xlsx 最省事的抽法是每行 `a | b | c`。但切块是 800 字符硬切，
   一行被切到下一块时就只剩数字，谁也不知道"50"是人数还是空间。
   改成 `版本=企业版；同时在线人数=2000；云录制空间=100 GB`，单行自解释。
2. **公式单元格是空的**：openpyxl 用 `data_only=True` 读的是**缓存值**，
   文件从没被 Excel/WPS 打开保存过就没有缓存，整张表抽出来 0 字符——又是"成功但没内容"。
   改成：先读缓存值，全空则回读公式文本并在 `note` 里说明。

### #37-#38 线上验收才暴露的两件事：库多了会抢名额、引用会露路径

1. **新库被大库挤死**（#37）：默认库 185 个 chunk 时，新传的 5KB 表格在全局 top-8 里排第 9 之后，
   用户问"我刚传的这份表"得到的是"资料未包含"。修法是按库分配额再 RRF 合并。
   教训：**评测集只在默认库里跑，"跨库"这条路径等于没测过。**
2. **引用行露出容器路径**（#38）：`参考：/app/backend/db/kb_files/4/780a7c84_xxx.xlsx`。
   引用校验只管"是不是真文档"，不管"给人看的样子"。修法是命中白名单后按规范名重写引用行。
   教训：**校验通过 ≠ 可以直接回填，展示层还要再归一化一次。**

### #39 为了"照顾小库"，把大库的相关结果挤掉了（RETRIEVAL）

上一轮（v2.4）为了修"新传的表格被默认库挤出 top-8"，给多库检索加了**每库保底名额**。
这一轮上流式时，它把我自己的评测打了脸。

- **现象**：线上问「企业微信新增成员调哪个接口」，**稳定**返回「无法确定，请联系人工」，连跑三次都一样；
  同一道题在本地（只有默认库）正常。trace 是 `retrieve(4 docs) → grade(0/4) → rewrite` 重试三轮 → G1 拒答。
- **定位**：trace 里 `kb_ids` 是 `['default', '2']`——当前用户是库 2 的成员。逐库对比召回：

  | 检索范围 | top-4 |
  |---|---|
  | 只查 default | 读取成员 ×3、**创建成员** |
  | default + 库 2 | 读取成员 ×3、**库 2 的一个测试文件**（"产品部资料 关键词 remotelion88"） |

  「创建成员」被挤出去了，4 篇全是讲"读取成员"的，打分器判 0/4 相关——判得没错，是真的都不相关。
- **根因**：旧实现给每个库固定保底 `per = max(2, ceil(k*2/n))` 个候选，再一起做 RRF。
  但 RRF 里「库内第 1 名」得分 `1/(60+1)` **永远大于**「库内第 4 名」`1/(60+4)`。
  一个只有 1 个 chunk 的无关库，在自己库里永远是第 1，于是一路压过 185 个 chunk 大库的第 4 名。
  **RRF 是用来融合「检索通道」的，不是用来融合「知识库」的。**
- **修法**：改成「全局排序 + 覆盖度补位」——
  ① 所有库一起检索（`where kb_id $in [...]`），让 chunk 在同一空间里比分数，顺序才公平；
  ② 取完 top-k 后检查哪个库一篇都没进，把它的 top-1 **追加到末尾**，而不是替换已有结果。
- **效果**：多库召回 4 → 5 篇，「创建成员」回到第 4 位，库 2 的内容排在末尾（打分器会自己丢掉）。
  接口题恢复正常；拒答题仍然正确拒答。
- **一句话结论**：**为了让边缘情况"也能被看见"而加的保底名额，代价往往是牺牲相关性；
  补位就该老老实实追加，不该抢别人的位置。**

## #40 路由器对「非产品类」内部问题误判闲聊（v2.7）

**现象**：接入企业分组场景后，「公司出差住宿标准是什么」被判 `casual_convo` 直接闲聊回复，根本不检索——但公共制度库（分组授权）里明明有。
**根因**：路由 prompt 只描述了「五类产品 + 闲聊」，没有内部制度/财务/报表类别；问题里没有任何产品词时模型倾向归闲聊。
**修复**：prompt 明确「公司制度/账单/报表类问题一律 vectorstore，即使没提产品名」+ 判定原则加对应条目。
**回归**：抽 3 道拒答题 + 2 道可答题复测，拒答能力未受影响（拒答由生成链路兜底，路由放宽不会泄露）。
**教训**：知识库边界扩了（产品→企业资料），入口路由的边界描述必须同步扩，否则内容在库里但问题进不了检索。

## #41 分组授权 ≠ 用户分组标签（v2.7）

用户表 `grp` 只是分组标签，知识库可见性靠 `kb_members` 逐人授权——分组标签不起任何权限作用，几十人的部门要授权几十次。
本次加 `kb_groups` 表（kb_id, grp, role），`readable_kb_ids` 取「个人 ∪ 分组」并集，个人优先。批量脚本 `POST /open/v1/users` 建号时带 group，之后整组授权一条命令。
