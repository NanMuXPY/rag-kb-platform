## 〇、设计前提：先说清 6 个真实约束

这 6 条是从 `backend/api/main.py`、`backend/app/workspace.py` 里读出来的**事实**，不是推测。后面所有交互都是从它们推导出来的，先摆在这里，免得后面每节都要重复解释。

| # | 事实（代码依据） | 对交互的强制约束 |
|---|---|---|
| **C1** | `GET /kbs` 返回**数组、全量、无分页参数**（`main.py:333`），排序固定 `ORDER BY k.id` | 分页/排序只能前端做；顺序必须是"先排序再切片"，否则第 2 页会出现第 1 页的漏项 |
| **C2** | 筛选参数 `dept / level / status` 都是**单值等值比较**（`main.py:345-350`），`q` 只匹配 `name + code + description` 三个字段的小写包含 | 筛选只能单选；多选要么改后端，要么前端二次过滤导致"共 N 个"页码失真。所以：**单选 + 跨维度可叠加** |
| **C3** | 没有回收站接口：`delete_kb` 只把文件 `status='deleted'`、`delete_file` 移到磁盘 `.trash/`（`workspace.py:274,503`）；`list_files` 恒过滤 `status!='deleted'` | **删除类操作在界面上不可撤销**。文案不许写"可在回收站恢复"，确认强度必须相应拉高 |
| **C4** | `update_kb_meta` 白名单 **不含 `code`**（`workspace.py:229`） | 编码建库后不可改。界面上必须**只读展示 + 写明原因**，不能给一个输了才报错的输入框 |
| **C5** | `kb_role` 优先级：`super` > **个人成员** > 分组 > 默认库 viewer（`workspace.py:150-169`）。**取"先命中"而非"权限更大"** | 个人授权**会收紧**分组授权。张三个人=只读 + 分组=库管 → 实际只读。界面必须显示"实际生效角色 + 来源"，否则管理员会以为授权没生效 |
| **C6** | `POST /admin/kbs`、`PATCH`、`DELETE`、`GET /admin/kb-matrix`、`GET /admin/users` 全部依赖 `require_admin_user`（系统角色 `admin`/`superadmin`）。**v1.5 例外**：`GET /kbs/{id}/candidate-users` 只要 `kb_admin` | 库管理员（`kb_admin`）若是普通员工，**改不了元信息、进不了矩阵**；但**选人不再受影响**（候选接口已放开）。因此降级形态只剩两处 |

另外两条不影响架构但影响文案：

- `owner` 字段**只是元信息**，不产生任何授权（`kb_role` 完全不读 `owner`）。
- 默认库 `id=1`「产品通用知识库」**不可删、不可归档**（`workspace.py:237,275`），且文件区恒空（内置语料不入 `kb_files`）。

### 1.2 三层导航的分工（防止层级混乱）

| 层 | 换什么 | 形态 | 出现在 |
|---|---|---|---|
| 一级 `view-nav` | 换模块 | 胶囊 | 始终 |

| 控制台 `drawer-tab` | 换控制台内视图 | 下划线 tab（沿用现有） | 仅控制台 |

**控制台 tab 顺序（规格）**：`语料索引 → 用户管理 → 权限矩阵 → 审计日志`，矩阵固定第 **3** 位。位置不是审美选择：**"设分组"是矩阵的前置动作**（分组是矩阵的列，没有分组就没有列），两个 tab 必须相邻且顺序为"先建组、再看矩阵"。

**为什么控制台不新增第五种形态**（上面这条顺序的理由）：控制台已有 `drawer-tab`，**矩阵不是新 tab —— 它是已有第 3 个 tab 换内容**（`tabMatrix` 改造前就已存在：`frontend/index.html:263-266` 的按钮序是 `tabKb → tabUsers → **tabMatrix** → tabAudit`，`app.js:468-475` 的 `ADMIN_TAB_IDS` 也是这个序）。新增形态解决不了问题（层级还是三层），只增加学习成本。

### 1.3 详情页分区顺序的理由

`文件 → 成员与授权 → 分组授权 → 设置`：按**日常操作频率**排，不按"配置逻辑"排。文件每天动，元信息一年动两次。设置放最后还有个副作用：**删除按钮落在页面最底部**，天然避开了误触。

| `""` / `#chat` | `renderChat()` | 已登录 | 回登录页 |

分发伪码（给前端照抄结构，不必照抄实现）：

```
onhashchange → parse(location.hash) → {module, id, section, query}
  → guard() 失败则 replace 到兜底 hash 并停下
  → 若 module 变化 → 更新 .vnav active + 折叠 rail（innerWidth<1180）
  → 若 id 变化 → 重新拉详情数据；否则只切分区（不重拉）
  → render()
  → 恢复滚动位置（§2.4）
```

### 2.2 三类状态各存哪：这是最容易做错的一张表

| 状态 | 存哪 | 理由 |
|---|---|---|
| 当前库 id、当前分区、当前控制台 tab | **URL** | 可分享（"你看财务库的成员"直接发链接）、可回退、硬刷新不丢 |
| 搜索词 `q` | **URL**（`replaceState`） | 可分享页面级视图；用 **replace** 而非 push，否则打 5 个字进 5 条历史，后退键变成退格键 |
| 筛选 `dept / level / view` | **URL**（`pushState`） | 领导会把"财务部的机密库"这个筛选结果发给同事；后退应回到上一个筛选态 |
| 页码 `page`、每页 `size` | **URL**（`pushState`） | 同上。`size` 同时写 localStorage 作为下次默认 |
| 表格密度（舒适/紧凑） | **localStorage** `kb_density` | 个人物理偏好，跨会话有效，与具体筛选无关，进 URL 只会让链接变脏 |
| 每页条数偏好 | **localStorage** `kb_pageSize` | 同上（URL 里的 `size` 优先） |
| 列表滚动位置 | **内存** `Map<routeKey, scrollTop>` | 存 URL 会污染链接、存 localStorage 会让"下次打开"跳到奇怪位置；只需要"本次返回" |
| 已勾选的批量集合 | **内存**（Set of id） | 绝不持久化：刷新后仍选中 128 项然后误点删除是最坏的事故 |
| 表单未保存草稿（详情页设置分区） | **内存** | 分区切换不丢，刷新即丢（并提示，见 §5.4） |
| 上传队列 | **内存** | 断点续传无接口，不做假承诺 |
| 详情页数据缓存 | **内存**（60s TTL，按 kb_id） | 来回切分区不重复请求；超 60s 视为脏，进入时静默重拉 |
| 抽屉的"来源元素"引用 | **内存**（`lastFocus`） | 关闭后焦点要回到原处（§9.3） |

### 2.3 结论：返回列表要不要还原筛选？

**要还原，而且不要靠内存，要靠 URL。** 理由三条：

1. **视觉规范 §2.3 的原始诉求是"别让用户回到列表第一页"**。URL 是唯一真相：`location.hash` 里已经有全部条件，返回时天然还原，不存在"内存变量被某次渲染清掉"这类偶发 bug。
2. **URL 还原比内存还原多解决两个真实场景**：硬刷新（F5）后条件不丢；把筛选结果发给同事对方看到同样的列表。
3. **成本几乎为零**：`#kb` 已经是路由，query 解析是同一个函数的一部分。

唯一让步：搜索词用 `replaceState`（不堆历史）、滚动位置用内存。**滚动位置不进 URL**，因为 `#kb?...&scroll=1240` 这种链接有副作用——对方打开时页面会在你上次的位置，而不是他自己想看的地方。

### 2.4 滚动位置还原

- 只有 `list → detail → 返回` 与 `list → 抽屉 → 关闭` 这两条路径还原滚动位置。
- key = `${q}|${dept}|${level}|${view}|${page}|${size}`。key 变了就丢弃记录（换了筛选，旧位置没意义）。
- 还原时机：表格 `tbody` 渲染完成后的下一帧（`requestAnimationFrame`），否则 `scrollTop` 会被设成 0。
- 记录上限 20 条，超出按插入顺序淘汰（`Map` 天然保序）。

### 2.5 无权限 / 不存在的详情页

`#kb/999` 直接访问，或 `#kb/7` 但权限被收回：

- 后端表现：`GET /kbs/{id}/files` → 403「无权访问该知识库」；不存在的库 → 403（`kb_role` 返回 `None` 与无权限同一分支，前端区分不了）。
- **因此文案必须同时覆盖两种可能**，不能猜"不存在"：

```
▤（36px --line-strong）
你没有访问这个知识库的权限
它可能已被删除，也可能需要管理员授权。请联系知识库负责人或系统管理员。
[返回知识库列表]        ← 文字按钮，不是主按钮（主按钮会暗示"这里有正向操作可做"）
```

- 焦点落在标题上（`tabindex="-1"`），`document.title` 改为「无权访问 · 知识库」。
- 页面外壳保留（topbar 可点），不要整屏报错——用户还需要从别处出去。

## 三、列表页交互

### 3.1 搜索

| 项 | 决定 | 理由 |
|---|---|---|
| 防抖 | **280ms** | <200ms 中文输入法组字过程中会连发（"财务"会打出 `cai`/`caiw` 两次请求）；>350ms 能被感知成卡。280ms 是打完一个双字词的平均间隔 |
| 匹配字段 | `name`、`code`、`description` | 后端 `q` 就匹配这三个（`main.py:353`）。**不匹配 `dept`/`owner`** —— 想按部门找请用部门筛选，两条路混在搜索里会让结果无法解释 |
| 大小写/空格 | 去首尾空格，不区分大小写 | 后端已 `lower()` |
| 请求时机 | 防抖后发 **1 次** `GET /kbs?q=...` | 服务端过滤。**不做前端二次过滤**（前端过滤会导致本轮 `file_count` 等统计与"共 N 个"对不上） |
| 加载表现 | 视觉规范 §5.1：保留旧数据 + 2px 进度线 | — |
| 清空 | 输入框右侧 `✕`（有值时出现），点击清空并 `replaceState` | — |
| 快捷键 | `/` 聚焦（§9.2） | — |
| 无结果 | 空态「没有符合条件的知识库」+「清除筛选」 | 视觉规范 §5.2 第二种 |

### 3.2 筛选

**结论：每个维度单选，维度之间可叠加。不做多维多选。**

**理由（不是偏好，是 C2 决定的）**：后端 `dept`/`level`/`status` 是等值比较。要做"多选部门"只有两条路：
(a) 后端改成 `IN (...)` —— 超出本次范围；
(b) 前端循环请求 N 次或拉全量后自己筛 —— 后者会让页脚"共 128 个"与真实结果不一致，而**治理场景里"共几个"本身就是决策依据**，不能骗人。

具体控件：

| 控件 | 形态 | 选项 | 与 URL 的映射 |
|---|---|---|---|
| `ufilter` | 小胶囊 ×3 | 全部 / 我管理的 / 已归档 | `view=all｜mine｜archived` |
| 部门 | 胶囊 + 下拉（`<details>` 或 popover） | 「全部部门」+ `GET /admin/users` 去重 group（升序） | `dept=` |
| 分级 | 胶囊 + 下拉 | 全部分级 / 公开 / 内部 / 机密（选项前置线框签预览） | `level=` |
| 清除筛选 | 文字按钮，**仅当有任一条件时出现**，位于工具条最右 | — | 清 `q/dept/level/view`，`page` 归 1 |

**状态不单独做筛选胶囊**：`已归档` 已是 `ufilter` 的一项。两个入口控同一个字段（`status`）必然打架（用户在 ufilter 点"全部"但状态筛选还停在"归档"，页面看起来没反应）。**一个字段只允许一个入口。**

「我管理的」在后端没有参数，前端按 `my_role === 'kb_admin' || 'super'` 过滤——**这条会破坏 C1 的"先排序后切片"吗？不会**，因为它作用在排序之前的数据集上，流程是：`全量 → 按 view 过滤 → 排序 → 切片`。必须按这个顺序，否则页码会错。

`ufilter.active` 已有蓝色态，视觉规范明确不加"已筛选 3 个条件"这类噪音文案，本文照办。

### 3.3 排序

**可排序列只有 2 个：编码 / 文件数**（视觉规范 v1.1 §3.5 由 3 个收敛为 2 个；「更新时间」改名「变更时间」且**不可排序**）。本文只定**默认值**与**行为**：

> **v1.5 补一句**：B1 修好之后（`updated_at` 全链路刷新），这一列**技术上已经可以排序**了。仍维持不可排序，是因为"找出落后的库"本质是**筛选**需求（"30 天没动过"），不是排序需求 —— 排序只能把落后的库挪到某一端，用户仍要一屏屏找；真要做，应该加一个筛选而不是给列头加箭头。恢复排序需要视觉改 §3.5（2→3 个可排序列），**记为可选、不排期**。

| 列 | 可排序 | 排序键 | 空值排位 |
|---|---|---|---|
| 编码 | ✅ | 字符串升序（`KB-0002` < `KB-0010`，定宽编码恰好字典序=数字序） | `''` 排最后 |
| 文件数 | ✅ | 数值 `file_count` | 空当 0 |
| 变更时间 | ❌ | —（列头无 `▲▼`，不可点；`title="包含库配置变更与文件上传/审批/删除"`） | — |

- **默认排序：编码 ↑**。理由两条：
  1. **稳定顺序建立空间记忆**。按时间排，每次进页面顺序都在变，用户每次都要重新扫一遍找"我上次改的那个"。按编码排，用户知道"新库总在最后、默认库在最前"。
  2. **时间序的收益远小于它的代价**：按时间排，每次进页面顺序都在变，"我上次改的那个"每次都要重新扫。原写作时 `updated_at` 只在 `PATCH` 时变（上传不 bump），语义不可靠，所以当时直接不给排序权重；**B1 已修（`touch_kb` 全链路刷新），但结论不变**，理由换成上面那条（这是筛选需求，不是排序需求）。这一列现在的 `title` 说实话：`包含库配置变更与文件上传/审批/删除`。
- 点击列头：`无 → ↑ → ↓ → 无`（三态循环，第三态回到默认），`aria-sort` 同步；不可排序列不响应点击、无 `aria-sort`。
- 排序 → 重置 `page=1`（否则排序后停在第 5 页看到的是新的第 5 页，用户会以为丢了数据）。
- 排序字段与方向**不进 URL**（默认排序已覆盖 90% 场景；进 URL 会让链接膨胀，且排序是个人偏好而非共享视图）。存内存即可。

### 3.4 分页 vs 加载更多 —— **结论：分页，每页 20**

| 判据 | 分页（选中） | 加载更多 |
|---|---|---|
| 后端现状 | 一次返回全量，前端切片成本 0 | 后端无 `limit/offset`，"加载更多"没有性能收益，是**假的**加载更多 |
| 能不能回答"一共几个" | 页脚「共 128 个」恒定可见 | 只有"已加载 40 个"，用户不知道还剩多少 |
| 批量作用域能不能说清 | 能：「已选全部 128 项」 | 不能：用户无法表达"我把所有符合条件都选上" |
| 返回列表还原 | 一次切片，落点精确 | 需重放 N 次请求且数据可能已变，落点漂移 |
| 几十到几百的规模 | 20/页 = 2–15 页，页码控件装得下 | 128 项要滚 6 屏，找第 3 页等于从头滚 |

- 每页 20（下拉可选 20 / 50 / 100，存 localStorage）。
- 页码控件：`首页 · 上一页 · 1 2 3 … 7 · 下一页 · 末页`；总页数 ≤ 7 时全部显示，不出现省略号。
- 页码与 `size` 进 URL（§2.2）。
- **已知上限**：`GET /kbs` 全量返回。库数 > 500 时首屏数据量约 250KB 且 `list_kbs` 的 4 个相关子查询会变慢。**500 是本方案的上限**，超过需后端加 `limit/offset` + 前端虚拟滚动。写进 §11 作为待办，不在本次实现。

### 3.5 行与行内操作

- **整行可点进详情**：`tr[tabindex="0"]`，`Enter` 等同点击；行内按钮必须 `stopPropagation`（视觉规范 §3.10 已定）。
- 行内操作**最多 2 个按钮 + 1 个 `⋯`**（视觉规范上限 3 个可见控件）：

| 位置 | 控件 | 行为 |
|---|---|---|
| 行内 | `成员` | → `#kb/{id}/members`（无 `kb_admin` 权限时**不显示**，不是置灰——置灰的按钮会让人反复去点） |
| 行内 | `⋯`（32×32，`aria-label="更多操作"`） | 打开小菜单（定位在按钮下方右对齐，`--z-dialog`−1，宽 168） |
| 菜单项 1 | `查看审计` | → `#admin/audit` 并预填 `kb_id` 过滤（非 admin 隐藏此项） |
| 菜单项 2 | `归档` / `恢复启用` | 按 `status` 切换；确认见 §8 |
| 菜单项 3 | `删除知识库` | `--red`；仅 `admin/superadmin` 且 `id !== 1`；确认见 §8 |
| 菜单项 4 | `复制编码` | 写剪贴板 `KB-0007`，toast「已复制 KB-0007」 |

- 菜单：`Esc` 关闭、点外部关闭、焦点移入第一项、关闭后焦点回 `⋯`。
- `⋯` 内一项都不可用时（如普通员工看默认库），**整个 `⋯` 不渲染**，不留空壳。

### 3.6 列表的空态与轻提示（已按视觉规范 v1.1 §5.2 收敛）

⚠️ 原视觉规范 v1.0 写的"真空态：一个库都没有"**在本产品几乎不可达**：`GET /kbs` 恒包含默认库（`kb_id==1` → 兜底 `viewer`）。可达的常态不是"空"，而是**"只有 1 行"**。

v1.1 分成了两个组件，交互上必须分清：

| 组件 | 触发条件 | 表现 | 文案（由 UX 定，形态由视觉定） | 动作 |
|---|---|---|---|---|
| **空态大块** | **仅 `rows === 0`**（默认库被误删 / 接口返回空 / 数据未初始化） | 表格容器内 36px `▤` + 衬线主文案 + 副文案 + 动作，上下留白 64 | 「还没有知识库」/「先建一个，把制度文档传进来」 | 主按钮「新建知识库」 |
| **`hint-bar` 轻提示条** | `rows === 1` 且唯一一行是默认库（`id===1`） | 32px 高、无框无底、位于工具条与表格之间、12px `--muted`、行首 `·` | 「只有一个默认库 · 默认库是内置语料，不能上传。**新建一个知识库** 来放你们部门的文档」（末段是 12px `--blue` 文字按钮） | 文字按钮「新建一个知识库」 |
| **无结果空态** | `rows > 0` 但搜索/筛选后 0 条 | 同空态大块 | 「没有符合条件的知识库」/「试试缩短关键词，或清除筛选」 | 文字按钮「清除筛选」 |
| **无权限** | — | **本产品不实现**（v1.1 §3.6 已废弃该行态） | — | — |

`hint-bar` 的三条交互规则（形态之外的补充）：

1. **无 `admin` 权限时，末段不渲染蓝色文字按钮**，改为同一句里接灰字：`请联系管理员为你建库`。理由：给一个点进去必然 403 的按钮，比不给更糟。
2. **`hint-bar` 在搜索/筛选态下不出现**。用户正在缩小范围时，提醒"只有一个默认库"是错位的（他可能正在搜索另外 30 个库）。
3. **`hint-bar` 不参与任何状态判断**。它只是提示，所以：`rows === 1 && 是默认库` 才出现，且**不占 60px 工具条、不替换工具条**，页面高度只多 32px。

⚠️ 同理，视觉规范 §3.6 的「不可访问行态（`opacity:.55` + 状态列「无权限」）」**已废弃，不要实现**。它对应的场景是"能看到但进不去"，而本产品的列表压根不返回那种行。

### 3.7 两个"推导列"必须自曝（授权范围 / 变更时间）

这两列的**值不是后端字段，是前端算的**。推导值不自曝，就是一次欺骗：用户会把它当权威数据去汇报，一旦后端加字段、规则一变，历史截图全错。

| 列 | 推导规则（写死在渲染函数里，附注释） | 列头 `title`（必须写） |
|---|---|---|
| 授权范围 | `id===1 → ◎全员`；`group_count>0 → ▤{group_count} 组`；否则 `◦{member_count} 人` | `按成员/分组数量推导，明细见库详情` |
| 变更时间 | 直接取 `updated_at`（v1.5 起上传/批准/驳回/删除都会刷新，见 B1） | `包含库配置变更与文件上传/审批/删除` |

两条硬规则：

1. **`▤N 组` 的格子 `title` 追加"另有 M 名成员单独授权"**（`member_count - 1 > 0` 时才追加，`-1` 是减掉创建者）。否则"3 组"看起来覆盖了所有人，实际还有 5 个人是单独授权的。
2. **成员再多也不升格为「◎全员」**（v1.1 §10.2 第 4 条裁定）。只有默认库是"全员可读"，这是权限模型的事实（`kb_role` 对 `kb_id==1` 兜底 `viewer`），不是数量推断。一个库有 200 个成员也不是全员——宁可显示`◦200 人`，不要显示一个让人误判"谁都能看"的 `◎`。

### 4.3 编码自动生成规则

后端逻辑（`workspace.py:215`）：`code` 为空 → `KB-{id:04d}`（如 `KB-0008`），并在同事务里查重。

**前端不允许"预览编码"**。理由：真实编码由自增 `id` 决定，并发建库时前端猜的数字会错——宁可显示文字也不显示一个可能错的编号。

界面上：

- 未开启自定义时，字段位置显示**只读文本**：
  `编码保存后自动生成（形如 KB-0008），建库后不可修改`
- 打开「自定义编码」开关 → 变为可输入，默认填入 `KB-`，并给出规则提示：
  `建议 KB-<部门简称>-<3位序号>，不超过 12 个字符（列表列宽上限）`
- 校验：`/^[A-Z0-9-]{3,12}$/`（前端）；后端上限 24 字，前端更严是为了列宽不截断。
- 冲突：后端 400 `知识库编码「KB-0007」已被占用` → 字段级错误原样透传 + 焦点回该字段。
- 建库成功后 toast：`已创建，编码 KB-0008`（**把生成的编码显式告诉用户**，否则编码列对用户来说是个谜）。

### 4.4 校验规则与错误文案（逐条，可直接抄进代码）

校验时机：`blur` + 提交时全量校验。**不在 `input` 每次按键时报错**（会边打字边红）。

| 场景 | 位置 | 文案 |
|---|---|---|
| 名称空 | 名称下方，`--red` 12px | `请填写知识库名称` |
| 名称 >50 字 | 同上 | `名称最多 50 个字，当前 53 个` |
| 名称重名 | 同上（后端 400 透传） | `已有同名知识库，换一个名字` |
| 名称含首尾空格 | 静默 trim，不报错 | — |
| 部门未选 | 不报错 | — （合法） |
| 负责人选了已停用账号 | 字段下方 `--amber` 提示（不阻断） | `该账号已停用，仍可作为负责人记录` |
| 编码格式不符 | 编码下方 | `编码只能包含大写字母、数字和短横线，3–12 个字符` |

2. Dialog 关闭；
3. `location.hash = '#kb/8/files'` 直接进详情 —— **不要**回到列表让用户在 128 行里找新建的那个。配合默认排序「编码 ↑」，新库必然在列表末页，回列表等于让人找不到。

### 4.5 部门字段：选择还是自由输入？—— **结论：选择（下拉）**

理由：

1. **筛选与矩阵都靠 `dept` 等值匹配**（C2）。自由输入必然出现「财务部 / 财务 / 财务室」三个值，筛选一次只能命中一个，等于筛选功能当场失效；矩阵里还会出现三个近似列。
2. **部门不是用户的私有概念，是组织数据**。它应该与「用户管理 → 设分组」同源（`users.group`），而不是让每个建库的人各写一套。
3. 降级路径明确：目录里没有目标部门时，选择器底部给一行提示 —— `找不到目标部门？先到「控制台 → 用户管理」给成员设分组，分组名会成为部门选项。`（而不是允许自由输入——那会毁掉 1 和 2）。
4. 建库表单的负责人下拉来自 `GET /admin/users`（建库本身就要系统管理员，C6 已确认），所以这份数据**恒可用**，无需降级。**注意区分**：成员分区的选人用的是 `GET /kbs/{id}/candidate-users`（`kb_admin` 即可），两份数据不要混用。

## 五、详情页四个分区的交互

四个分区共用一套反馈规则，先立规矩：

| 反馈层 | 用在哪 | 形态 | 时长 |
|---|---|---|---|
| 字段级 | 表单校验 | 字段下方 12px 文字 | 常驻至修正 |
| 行级 | 行内操作失败 | toast + 该行 `outline: 2px --red` 1.5s | 1.5s |
| 区块级 | 分区列表加载失败 | 区块内错误条 + 「重试」（视觉规范 §5.3） | 常驻 |
| 页面级 | 403 / 404 | 整页说明（§2.5） | 常驻 |
| 成功 | 所有写操作 | 右上 toast，含对象名 | 2.5s |
| 可撤销成功 | 归档、移除成员、收回分组 | 右上 toast + 「撤销」按钮 | **10s** |

**全部确认框用 `<dialog>`，禁止原生 `confirm()`/`alert()`/`prompt()`。** 现状 `app.js` 里有 6 处原生弹窗（`app.js:532,615,803,896,930,944`），必须替换。理由：原生 confirm 无法显示"这个库有 128 个文件"这类决策所需上下文，按钮文案也不可控（"确定/取消"放在危险操作上等于把用户推向危险）。

### 5.1 文件分区（`#kb/{id}/files`）

**页面结构**：页头（面包屑 + 标题 + 编码 + 分级签 + 状态徽标 + 元信息行 + 主操作「＋ 上传文件」）→ `subnav` → 上传队列卡（有队列时）→ 待审批 `hint-bar`（有 pending 时）→ 文件表 → 页脚。

⚠️ **v1.4 结构变更**：这里是**一张表**。历史版本（v1.0–v1.3）把 pending 行抽到一个"待审批区"独立列表里渲染，v1.4 撤销该结构，理由见 §5.1.2 开头。

#### 5.1.1 上传

| 项 | 决定 |
|---|---|
| 入口 | 页头主操作「＋ 上传文件」（`editor` 及以上可见；`viewer` 不渲染该按钮，改在左下方一行提示「你是只读成员，如需上传请联系库管理员」） |
| 选择 | 点击 → 系统文件选择，`multiple` 开启；同时支持拖到 `.dropzone` 区域（整区高亮 `--blue` 描边） |
| 前置校验（前端） | 扩展名 ∈ `md/txt/pdf/docx/xlsx/pptx`；单文件 ≤ 20MB；文件名非空。不通过 → 进队列就标失败，**不发请求** |
| 并发 | **串行，一次 1 个**。理由：后端每传一个文件就要抽文本 + 可能 `add_file_to_index`，且 `_db_lock` 是全局锁；并发上传会让"已入库"的反馈乱序 |
| 队列位置 | 文件表上方一条队列卡（不是 Dialog），高度自适应，最多显示 5 条 + `还有 3 个…` |
| 单条状态 | `等待` → `上传中`（2px 不确定进度线，fetch 无上传进度事件，不假装百分比）→ `待审批` / `已入库` / `失败：原因` |
| 同名文件 | 前端拿现有 `files` 列表比对，命中则队列条出现琥珀提示：`「运维手册.pdf」已存在（v2），上传后将覆盖为 v3，旧版自动备份` |
| 成功后 | 队列条保留 5s 后收起；`file_count` / `pending_count` 与页头副信息同步 +1（不整页重拉） |
| 失败 | 该条红字原因（后端 detail 原样透传），右侧「重试」单条重试 |

后端真实错误必须能落地（不要自己造文案，直接显示 detail）：

| 后端 detail | 界面补充的一行建议 |
|---|---|
| `不支持的文件类型 .zip（仅 md/txt/pdf/docx/xlsx/pptx）` | `请先解包或转成 PDF` |
| `文件超过 20MB 上限` | `可分卷压缩后分多次上传` |
| `未能从《扫描件.pdf》提取文字：未检测到文本层` | `扫描件请先做 OCR 再上传` |
| `只读权限，如需上传请联系知识库管理员` | `请联系库管理员提升你的角色` |

#### 5.1.2 待审批：一条 `hint-bar` + 一个审核弹窗

`pending_count > 0` 时，文件表**之上**出现一条 **32px `hint-bar`**（视觉 §5.2 形态，`--amber-bg` + `1px --amber-line`），单行、不换行、内容溢出时尾部省略：

> `· 待审批 3 个，审核通过后才会进入问答索引。` **全部批准**

**pending 行不再抽成独立列表，就是文件表的普通行**（`.st-pending` 徽标 + 基准序置顶 + 参与复选框批量）。

> **为什么撤销 v1.0–v1.3 的"待审批区"独立列表**（这是本文本轮唯一的结构改动，三个理由都在本产品里可验）：
> 1. **否则 `.st-pending` 是第 6 个不可达态**。视觉 v1.4 §11.8 给状态列定了三件徽标；pending 行若不在表里，`.st-pending` 永远渲染不出来。§11.2 末已经用同一个理由废弃过 5 个态，不能自己再造一个。
> 2. **同一批数据两套渲染必然两套行为**。独立列表要另写列宽、另写点击、另写批量，而它和表格共用同一份 `files` 数组 —— 现状 `app.js:1858` 就是拿同一个 `fileRowHTML` 喂两个容器，改一处忘一处只是时间问题。
> 3. **`hint-bar` 已经够用了**。计数 + 批量入口一行放下，比占 3 行高的区块省下的不是像素，是"表头在哪儿"的位置感。

`hint-bar` 的文案**对所有人一样**（它陈述的是事实），差别只在右侧的动作：

> `· 待审批 3 个，审核通过后才会进入问答索引。` ｜ 能审批的人（`kb_admin`/`super`）后面跟 **全部批准**；`editor`/`viewer` 只看到这句话，**不给按钮**（不做"请联系管理员"这种没有出口的引导 —— 上传者本来就该知道"等审核"，而不是被告知去求人）。

**复选框只服务一件事：批量批准**（别让它变成装饰）。真实场景是"5 个里 3 个能入库、2 个要拒"，只给「全部批准」会逼用户逐个点 3 次弹窗。

| 位置 | 行为 |
|---|---|
| 行复选框 | **只在 `pending` 行渲染**；`approved`/`rejected` 行的单元格留空（列 44px 恒在，不因数据增减而塌缩，避免横向跳动） |
| 表头复选框 | 勾选 = 选中**当前全部 `pending` 行**（不是本页所有行），`title="选中全部 3 个待审批文件"`；无 `pending` 时该复选框 `disabled` + `title="没有待审批文件"` |
| 勾选 ≥1 后 | `hint-bar` 右侧由 `[全部批准]` 变为 `[批准选中 2 个]` + `[全部批准]`（后者降为 ghost）；取消勾选恢复原样 |
| 批准选中 | 与「全部批准」同一个确认框、同一套部分失败清单（§7.4），标题换成 `批准选中的 2 个文件？` |

文件表**不做**批量删除 / 批量下载：删除是强度 3 的单条决策（§8.1），批量下载会让浏览器连弹 N 个下载框，两个都不值得做。

**行内只有一个「审批」按钮，点开是审核弹窗**（`<dialog>`，`640px`，`max-height: 76vh`，body 可滚，footer 吸底）：

| 部位 | 内容 |
|---|---|
| 标题 | `审批「扫描件.pdf」`（`--serif` 16/700，同 §8.2 ①） |
| 副信息 | `v1 · 2.1MB · 李四 · 3 小时前上传`（12px `--muted`，` · ` 分隔，缺项省略） |
| 正文 · md/txt | 渲染原文（复用 `docDialog` 的 `marked` + `DOMPurify` 管线；>50k 字符截断，底部一行 `仅显示前 50000 字，请下载核对全文` + 「下载」次级按钮） |
| 正文 · pdf/docx/xlsx/pptx | 一行 `该类型无法在线预览，下载后查看` + 「下载」次级按钮（复用 §5.1.3 的下载权限判定）。**与行内 `title` 同一句**：同一个事实只允许一个版本 |
| 正文 · 取文件失败 | `无法读取文件：「扫描件.pdf」可能已被清理。` + 「关闭」，**不显示批准按钮**（读不到内容就不该让人批） |

| 批准入库 | **无**（正向高频，§8 强度 1） | 弹窗关，焦点回该行「审批」按钮，toast `已入库，「运维手册.pdf」· 42 chunks，已进入问答索引`；`hint-bar` 计数 −1 | toast `批准失败：文件不存在或不在待审批状态` + 整表静默重拉（多半是别人先处理了） | `kb_admin`/`super` |
| 拒绝 | **弹窗内二次态**（不叠第二个 `<dialog>`）：footer 换成 13px `拒绝后无法再批准，上传者需重新上传。` + 左 `返回`（ghost，默认焦点）/ 右 `确认拒绝`（`.btn-danger`） | 弹窗关，toast `已拒绝「扫描件.pdf」` | toast `拒绝失败：文件不在待审批状态` | 同上 |

> **为什么不给行内「预览」按钮**（这是视觉问的那个问题的实质）：
> ① 加了它，pending 行的按钮就是 预览/下载/审批/删除 **4 个**，内容宽 `24×4 + 12×3 = 132 > 100`，124 的列必溢出 —— 正是视觉 v1.4 刚修掉的那类 bug，只是换了个位置复发。
> ② 更关键：**预览按钮是可跳过的**。行内摆着「预览」和「批准」，管理员照样直接点批准，盲批问题只是"看起来修好了"。把内容放进审批弹窗，**"没看到内容就批不了"变成结构性保证**，不依赖自觉。
>
> **代价要认**：单条审批从 1 次点击变 2 次（审批 → 批准入库）。批量路径（全部批准 = 1 击 + 1 确认）没变，所以真实代价只落在"零星几个"的场景。若上线后库管反馈单条太慢，回退方案是：把「批准」提回行内直接可点，把「拒绝」移进行抽屉（抽屉本来就在），行内仍是 3 个按钮 —— **这是留了后路的取舍，不是漏算了效率**。
>
> **批准后不做滚动跟随**：基准序是「待审批优先 → 上传时间降序」，批准后该行离开置顶簇，可能落到视口外。**不滚动、不高亮**（看不见的高亮等于没有），反馈只靠 toast 里的文件名 + `hint-bar` 计数 −1。不要用"自动滚到新位置"补偿 —— 那会把用户从当前位置带走，而他通常还有下一个要批。

⚠️ **重要修正**：现状 `app.js:769` 只在 `status === 'approved'` 时给预览按钮，导致管理员**盲批**。后端 `download` 对 `kb_admin/super` 放行未审批文件（`main.py:463`），所以待审批文件技术上可预览。**必须改**：预览入口落在审批弹窗里（正文区），而不是加一个行内按钮。

⚠️ 「批准」**不提供撤销**。`approve_file` 要求 `status === 'pending'`，批准后无法退回待审；反向只有"删除"（会掉索引，且不可在界面恢复）。**「拒绝」同样不提供撤销**（同一条 `status === 'pending'` 前置）。所以：
- 批准按钮**不弹确认**但成功 toast **不带假的"撤销"**（假装可撤销比没有更糟）；
- 缓解措施是"批前能看"（弹窗强制看内容）+ "批错能删"（删除按钮就在同一行）。

#### 5.1.3 文件表

列（**列名/字段/宽度见附录 D1**；形态与令牌由视觉规范负责）：`复选框` ｜ `文件名（主 + 版本·大小·上传人·分块次行）` ｜ `状态` ｜ `上传时间` ｜ `操作`。

**操作列按钮矩阵 —— 前端照抄这 5 行**（列宽 124，内容宽 100）：

| 角色 × 行状态 | 按钮（渲染顺序即从左到右） | 内容宽 |
|---|---|---|
| `pending` × 库管 | `审批` `下载` `删除` | 96 ✓ |
| `approved` / `rejected` × 库管，md/txt | `预览` `下载` `删除` | 96 ✓ |
| `approved` / `rejected` × 库管，其它类型 | `下载` `删除` | 48 |
| 非库管 × `approved`（md/txt / 其它） | `预览` `下载` / `下载` | 48 / 24 |
| 非库管 × `pending` / `rejected` | **无**（空单元格，见下） | 0 |

**「审批」只在 `pending` 行渲染。非 `pending` 行不渲染，也不做"禁用占位"**（v1.6 定案）：

1. 一个在该行**永远不可能变可用**的禁用控件，是"不可达态"的第二种伪装形态 —— 用不可达态解决不可达态，逻辑上不成立（我们已经为此废弃过 6 个态，见 §11.2 末 + §十一之六）。
2. 原生 `disabled` **不可聚焦**：键盘用户 Tab 直接跳过这个位置，读屏用户听到的按钮数从 3 变 2；`title` 在触屏根本不出现 —— 摆一个只有鼠标用户能"看见"的说明，等于对另一部分用户不存在。
3. 状态列已经写着「已入库」，再来一个灰按钮是把同一句话说第二遍，且说得更弱。

> **判据：禁用态分三类，不要一刀切**（v1.8，与视觉 §3.12 对齐后细化）
>
> | 类型 | 定义 | 做法 | 本文的例子 |
> |---|---|---|---|
> | **locked（暂时用不了）** | 同一行的其它操作能把它解锁 | **画**，`title` 说明**钥匙在哪** | 成员表 `kb_admin` 行的「移除」：改成「只读」后就能移除 |
> | **forbidden（策略禁止）** | 谁都解不开，但**这条策略在界面别处没有落点** | **画**，`title` 写规则原句；这是规则唯一的落点 | 创建者行的「改角色」「移除」：来源列只写了「创建者」这个人是谁，没写"他不能动" |
> | **unreachable（状态终局）** | 这一行的状态不会逆转，能力永远不再存在 | **不画**；状态列已经说过一遍了 | 已入库文件的「审批」：`status` 是终态，没有任何操作能回到 `pending` |
>
> **区分 forbidden 与 unreachable 的那一问**：*删掉这个按钮，用户还能从别处读到这条规则吗？* 能 → 不画；不能 → 画。
> 创建者行 = 能读到"他是创建者"，但读不到"创建者不可移除"→ **画**。文件表审批 = 状态列写着「已入库」，而"不能再批一次"这件事**不需要被知道** → **不画**。
>
> 一句话版：**用完不用的按钮不要画；暂时用不了的按钮要画，并告诉用户钥匙在哪；规则没有别处可读时，允许画一个"说明型"的灰按钮。**
> 视觉把这层写成通则并发回来一句，值得照抄：**允许例外，但必须能算出代价** —— 创建者行每库恒定 1 行、噪声成本≈0，换回的是"创建者不可移除"这条规则在界面上唯一的落点；说不出代价的例外，就只是偏好。
>
> v1.12 补一句配套的：**所以例外不做"总表"，只按级登记**（记号级进视觉 §3.8 编号表，能力级留在授予处）。理由见 §6.1 末 —— 一句话：**登记表会让人跳过"算代价"这一步。**

**位置稳定靠右对齐，不靠按钮数量恒定**（视觉 §3.10 已立为通则，一句话版：**"位置恒定"不靠占位保，靠右对齐保**）：`删除` 恒贴最右，按钮数在 0–3 之间变化时它的 x 坐标不变。**数量可以变，危险动作的位置不能变** —— 用户第二次点删除，不会因为这行少了个「审批」而点到别的东西。列宽本身由 `<colgroup>` 固定 124，**也不会因为少一个按钮而变窄**：两个真实诉求（列宽稳定、位置固定）都已被满足，不需要用假按钮来"看起来整齐"。

- **为什么 `pending` 行没有行内「预览」**：`pending` × 库管已经有 `审批`/`下载`/`删除` 三个位置，再加预览就是 4 个 = **132 > 100**，124 必溢出。预览在**审批弹窗正文**里（§5.1.2）—— 而且这正是修"盲批"的方式：不是多给一个可跳过的按钮，而是把内容放进必由之路。
- **非库管在 `pending` / `rejected` 行上一个按钮都没有，这是后端的真实限制**：`GET /files/{fid}/download` 的判定是 `status != 'approved' and role not in {kb_admin, super}` → 403 `文件未通过审批`，**没有"上传者本人"这个例外**（`main.py:458-465`）。所以上传者传完也点不开自己的文件。这条已记为 **B6**（见 §11），后端若放开，非库管行会多出一个 `下载`（24px，仍 ≤3）。
- **无按钮时单元格留空**，不写 `—`：`—` 在本文里专用于"计数列值为 0"（视觉 §3.8），而**"当前没有可执行操作"不是数据缺失** —— 写 `—` 会让人以为漏渲染（**视觉 §3.8 例外登记 B**）。
- **为什么会右对齐就够（几何澄清）**：按钮等宽（2 字 = 24px）、间距恒定（12px）、整体右对齐，于是从右边缘起算的每个槽位 x 都是常量 —— `删除` 在最右、`下载` 在右数第 2 格、`审批`/`预览` 在右数第 3 格。**每个"存在"的按钮位置都不变**，变的只是"第 3 格这一行有没有东西"。所以"删掉渲染会让按钮组左边界跳"这个担心成立，但它跳的是**空白**，不是任何按钮；这也正是成员表、分组表的操作列一直在做的事。
- **零按钮 ≠ 没关系**：这一行仍然要能被读屏读出状态，见本节末尾的"行级无障碍"。

**行级无障碍（v1.6 补，team-lead 要求）**：非库管的 `pending`/`rejected` 行一个按钮都没有，如果行本身也不可读，读屏用户听到的是**一个空行**。

| 对象 | 要求 |
|---|---|
| `tr` | `aria-label` 按固定顺序拼：`{文件名}，{状态}，{上传人}上传，{相对时间}`，例：`扫描件.pdf，待审批，李四上传，3 小时前`。`tr[tabindex=0]` 的 Enter 仍是"打开详情抽屉" |
| 状态徽标 | 自身要有可读文本（`待审批`/`已入库`/`已驳回`），**不能只靠颜色与位置**；若用 `<span>` 承载，加 `aria-label` |
| 复选框（仅 `pending` 行） | `aria-label`：`选择 扫描件.pdf 以批量批准`，不要只给一个裸 checkbox |
| 空操作单元格 | 不加 `aria-hidden`（读屏跳过空单元格是自然行为），也**不要**塞一个 `aria-label="无可用操作"` —— 每行都念一遍"无可用操作"是噪音，状态已经在行 `aria-label` 里说过了 |

**基准顺序（无 `▲▼` 时）**：**`pending` 优先 → `uploaded_at` 降序**。`pending` 是"等你干活"的簇，置顶；同组内按时间倒序。
> 但**基准序只在基准态生效**：一点「上传时间」列头就是纯时间序（`↓`/`↑`），不再夹带"待审批优先"。排序必须是真的，偷偷加私货的排序会让用户对整张表的顺序失去信任。此时待审批仍然可发现 —— `hint-bar` 有计数和「全部批准」，每行还有徽标。

| 动作 | 入口 | 确认 | 成功反馈 | 失败反馈 | 权限 |
|---|---|---|---|---|---|
| 审批 / 批准入库 / 拒绝 | 行内 `审批` → 审核弹窗 | 见 §5.1.2 | 见 §5.1.2 | 见 §5.1.2 | `kb_admin`/`super` |
| 预览 | 行内 `预览`（仅 md/txt，仅 `approved`/`rejected` 行；`pending` 行的预览在审批弹窗里） | 无 | Dialog 原文 | toast `预览失败：文件已丢失（可能被清理）` | 有库权限即可 |
| 下载 | 行内 `下载` | 无 | 浏览器下载，无 toast（浏览器自带） | toast `下载失败：文件已丢失（可能被清理）` | `approved` 文件：有库权限即可；**非 `approved`：仅 `kb_admin`/`super`**（上传者也不行，见 B6） |
| 删除 | 行内 `删除` | 确认框（§8 强度 3） | toast `已删除「运维手册.pdf」`（**不带撤销**，C3 无恢复接口） | toast + 行红框 | `kb_admin`/`super` |
| 查看详情 | 点击行 | 无 | 右侧抽屉：路径 / 版本 / 分块数 / 上传人 / 审批人 / 审批时间 / 下载次数 | — | 有库权限 |

非 md/txt（pdf/docx/xlsx/pptx）**不给预览按钮**，行内只有「下载」，`title` 为 `该类型无法在线预览，下载后查看`。**这条已定案，不留待办**（论据在视觉 v1.11 §11.8，本文只记结论）：

- Office 类要引第三方库，与"无构建、`vendor/` 只放两个小库"的纪律冲突；
- **但 PDF 是"技术上做得到、也仍然不做"** —— 浏览器原生能渲染 PDF，所以这条裁定真正的理由不是"做不到"，而是**渲染出来 ≠ 内容被审过**：审批的前提是"读不到内容就不该批准"，滚动两屏就点批准等于没读。**想重启这个话题，先驳这一条**，别拿"PDF 明明能预览"当理由 —— 那正是被否决过的那个论据。
> 按钮文案就是 2 个字的「下载」，**不要写「下载查看」**（4 字 = 48px，与「删除」并排后 84px，虽仍在 100 内但会把列撑到临界，且视觉 §11.8 的按钮集是 `下载`/`审批`/`删除`）。"不能在线看"这件事靠 `title="该类型不支持在线预览，请下载后查看"` 说，不靠把动词拉长。

### 5.2 成员分区（`#kb/{id}/members`）

> 权限门槛：`GET /kbs/{id}/members` 仅 `kb_admin`/`super`。`editor`/`viewer` 直接访问 URL → 分区显示「需要知识库管理员权限」+ 「返回文件列表」文字按钮，不整页报错。

#### 5.2.1 添加成员

| 项 | 决定 |
|---|---|
| 入口 | 分区右上「＋ 添加成员」（或页头次操作） |
| 控件 | 用户名输入 + 角色 3 选 1 + 「授权」 |
| 用户选择方式 | **v1.5 起只有一种**：输入即搜，数据来自 `GET /kbs/{id}/candidate-users`（`kb_admin` 即可调用，**不需要系统管理员**）。返回 `{users:[{username, display_name, group}]}`，下拉每项显示 `显示名 · @账号 · 分组`。**接口已排除"已直接授权"和"非激活"账号**，所以不会出现重复添加，也不会出现停用账号 |
| 无候选人时 | 下拉里一行浅灰：`没有可添加的账号（所有激活用户都已直接授权）`，输入框保留，不发请求 |
| 角色 | 单选：`只读 viewer` / `可上传 editor` / `库管理员 kb_admin`，默认 `只读`（安全的那一边） |
| 已存在的成员 | 候选里不会有；若通过接口直接 POST 了已存在的人，后端 `ON CONFLICT` 会更新其角色 → 前端提示 `张三 已是本库成员（只读），继续将更新其角色` + 角色预填当前值 |
| 成功 | toast `已授权 张三 为「只读」` + 列表该行出现并以 `--blue-bg` 高亮 1.5s + 输入框清空、焦点留在输入框（连续加人） |
| 失败 | 字段级：`授权失败：需要知识库管理员权限` / `授权失败：服务器异常（500），请稍后重试`。**"用户不存在"不写了**：选人来自下拉，选不到就选不到，没有拼写错误这种失败（v1.5，B2 修好后删除） |

#### 5.2.2 每一行只呈现"一个结论 + 一条来源链"

这是 C5 的直接产物，也是本分区最重要的信息设计。**视觉落点已由视觉规范 v1.2 §11.3 定死：角色列恒一个值，冲突全部下沉到「授权来源」列。**

```
张三   zhangsan              只读        直接（另 ▤ 财务组）      王芳   3 天前   [改角色][移除]
       @zhangsan             ↑恒一个值    ↑深色在前=决定者
       ↑ 角色列 hover: "个人授权优先于分组授权，已覆盖分组「财务组」的 库管理员"
```

四条硬规则：

1. **角色列永不出两个徽标、也不做"↑↓ 表示被收紧"这类标记**。两个徽标 = 用户以为一个人有两个角色 = 逼他自己算 `min(个人, 分组)`。这个运算界面必须做完，用户只读结论。
2. **被收紧这件事只由两处表达**：来源列把决定者放前面并在后面用 11px `--muted` 挂被覆盖段；角色列 `title` 写清"覆盖了谁、覆盖的是什么角色"（文案见附录 D2.1）。
3. **不再追加"⚠ 个人授权优先"这类琥珀提示行**（初版有，v1.2 撤掉）。理由：它会和"孤儿分组授权"的琥珀标记撞语义，且一行里同时出现两个琥珀，用户会以为出了两个问题。
4. **授权来源列不做删除线、不拆成两行**（视觉 §11.3 已禁）：权限表里划掉东西会让人怀疑数据出错；一个成员的来源必须能一眼读完——这是"我正在改谁"的判断依据。

#### 5.2.3 改角色 / 移除（禁用档位见附录 D2.3）

| 动作 | 入口 | 确认 | 成功 | 失败 |
|---|---|---|---|---|
| 改角色 | 点击行内角色文字 → 小弹层（3 radio + 「保存」） | 无（即时生效，可再改回） | toast `张三 的角色已改为「可上传」` | 弹层内错误条 + 保留选择 |
| 移除 | 行内 `移除`（`--red` 文字） | 确认框（§8 强度 2）+ 成功 toast 带 **10s 撤销** | toast `已移除 张三 ｜ 撤销` | toast `移除失败：成员不存在或为库管理员` |

**三条防错硬规则（前端拦，不等后端报错）：**

1. **任何 `kb_admin` 都不能移除**。后端 `remove_member` 的 SQL 带 `AND role!='kb_admin'`（`workspace.py:307`），会对 `kb_admin` 返回 404「成员不存在或为库管理员」。所以 `kb_admin` 行的「移除」**渲染为 disabled**（视觉 §11.3），`title` 分两种：创建者写 `创建者不可移除`，其他库管理员写 `库管理员不可直接移除，请先把角色改为「只读」`。
2. **创建者的「改角色」也禁用**，`title="创建者恒为库管理员，请添加其他成员作为库管理员"`。这是本文比视觉 §11.3 多的一条：后端允许"先降级再移除"，不禁改角色的话，「创建者不可移除」只是两步路的假门槛（推导见附录 D2.3）。
3. **不能把最后一名库管理员降级**。后端不拦，这会让一个库变成**无人可管**（谁都无法审批文件、改授权）。前端在提交前拦：若目标是本库唯一 `kb_admin` 且新角色 ≠ `kb_admin` → 阻止并提示：`这是本库唯一的库管理员。请先把另一位成员设为库管理员，再修改这个人的角色。`

**成员表空态**：`rows === 0` **不可达**（创建者恒为成员），可达态用 `hint-bar` 两变体 —— 文案见附录 D2.4，不要把空态大块写在成员表里。

#### 5.3.1 授整组

| 项 | 决定 |
|---|---|
| 入口 | 分区右上「＋ 整组授权」 |
| 分组选择 | **必须从已知分组中选**（`GET /admin/users` 的 `group` 去重，显示 `财务组 · 12 人`），不提供自由输入。选不到目标分组时给出口：`找不到目标分组？先到「控制台 → 用户管理」给成员设分组，分组名会成为选项。` |
| 角色 | 3 选 1，默认 `只读` |
| 覆盖已有 | 该组已授权时，选择器提示 `财务组 已授权「只读」，继续将改为「可上传」` |
| 成功 | toast `已授权「财务组」（12 人）访问本库，角色「只读」` —— **带人数**，因为这是"影响了一批人"的操作 |
| 失败 | `授权失败：需要知识库管理员权限`；分组在两次请求之间被改空时，后端会返回 400 `分组「财务组」不存在，请先在用户管理中创建该分组的成员` → **原样透传**（v1.5，B3 已校验） |

**为什么强制从列表选，不给自由输入（v1.5 更新）**：**B3 已修**——`set_group_grant` 现在校验分组存在，不存在直接 400（**文案原句在上表「失败」行，此处不复述**）。也就是说**孤儿授权新建不出来了**，第二道防线已经落到后端。

但选择器仍然保留，理由变了（从"防脏数据"变成"省一次往返"）：手输的正确率永远低于选，而错一次要弹一次 400。

**孤儿授权的展示保留，但降级为"历史脏数据清理"**：
- 修复前写入的孤儿行仍可能留在库里（矩阵的列来自 `list_groups()`，这类行**在矩阵里根本不显示**），所以在分组表里保留标记：人数 `0` + 次行 `该分组当前没有任何成员`（`--amber` 12px），并把「收回」做成该行唯一按钮。
- 这是**唯一**能让管理员发现并清理历史脏数据的地方，所以不能因为"新建不出来了"就删掉。
- **这里的琥珀表示"数据异常待处理"，不是"影响面警示"**（后者被视觉 §11.4 明令禁止在行内出现）。

#### 5.3.2 收回 / 改角色（护栏在确认弹窗，不在行内）

| 项 | 决定 |
|---|---|
| 入口 | 行内 `收回`（`--red` 文字）/ 点击角色文字改角色 |
| 确认 | **必须确认**（§8 强度 3），且确认框里写明影响人数 |
| 确认文案 | 标题 `解除「财务组」的整组授权？`；正文 `该组 12 名成员将无法再检索本库文档（其中 3 人另有个人授权，不受影响）。` |
| **影响面警示（人数 ≥ 20 时）** | 确认框内**加一行 12px `--amber`**：`本次改动影响 24 人`；正文随后列出受影响账号前 3 个 + `等 24 人`。这是 amber 在本屏的**唯一合法落点**（"等你确认"） |
| 人数来源 | `groups[].total / active`（矩阵接口同一数据源）。**无 `admin` 权限时拿不到** → 降级文案：`该组全体成员将失去访问权（个人授权除外）。` |
| 成功 | toast `已收回「财务组」的访问权 ｜ 撤销`（10s） |
| 失败 | toast `收回失败：该分组未被授权` |

**行内为什么一个字都不提示"影响 24 人"**（视觉 §11.4，本文照办）：人数列只把数字字重 500→600 + 一条 `title`。6 列表格里突然一个橙色、还可能多行同时触发，amber 立刻贬值，用户对橙色的反应会从"要注意"降到"又是它"。**"影响面"是操作后果，属于确认环节，不属于列表。**

#### 5.3.3 空态

**空态大块**（`rows === 0`，本表这个状态是**可达**的）：`还没有整组授权` / **`按分组授权后，组内成员（含之后新加入该组的账号）自动获得权限`** / 动作「＋ 整组授权」。

> 那句副文案**一个都不能省**（视觉 v1.2 §11.5）。它是全产品唯一说明"分组授权会覆盖未来加入的成员"的地方 —— 删掉它，管理员就不知道"今天新入职的人要不要再单独加一次"，而这个误解的代价是漏授权或重复授权。

## 六、权限矩阵视图（`#admin/matrix`）

治理的核心。数据一次拿全：`GET /admin/kb-matrix` → `{groups:[{group,total,active}], rows:[{kb_id,name,code,dept,level,status,grants:{组:角色}}]}`。

### 6.1 布局：本产品唯一允许横向滚动的表格（规格见视觉规范 v1.1 §10.1）

```
       ○ 只读    ◐ 可上传    ● 库管理员    · 点单元格切换      ← 图例，表格上方一行
┌──────────────────────────┬────────┬────────┬────────┬────────┬────────┐
│ 知识库                   │财务组  │运维组  │产品组  │管理层  │未分组  │  ← z-index 3 / 交叉格 4
│                          │ 12 人  │ 8 人   │ 5 人   │ 3 人   │ 2 人   │
├──────────────────────────┼────────┼────────┼────────┼────────┼────────┤
│ 产品通用知识库  ●启用     │        │        │        │        │   +    │  ← z-index 2（首列）
│ KB-0001 · 内部           │        │        │        │        │        │
├──────────────────────────┼────────┼────────┼────────┼────────┼────────┤
│ 财务制度库  ●启用         │ ○ 只读 │        │        │ ● 管理 │        │
│ KB-0007 · 机密           │        │        │        │        │        │
└──────────────────────────┴────────┴────────┴────────┴────────┴────────┘
  ↑ 冻结分界线 1px --line          ↑ 空单元格 hover 时显示 ＋（--line-strong）
```

**为什么允许横向滚动**（对视觉规范 §3.1「不提供横向滚动」的**能力级唯一例外**，授予处 = 视觉 §10.1，交互规格 = 本节）：全文其他提到它的地方只写"见 §6.1"，理由只在这里写一次。理由：列表页的列数是**设计已知的 9 列**，可以按优先级收起；矩阵的列数是**运行时数据**（分组几个就是几个），无法收敛。强行收起 = 隐藏授权关系 = 治理视图失效。

**这条例外的"登记级别"（v1.12 规则，不是提醒）**

| 级别 | 是什么 | 登记在哪 | 例 |
|---|---|---|---|
| **记号级** | **同一个值的不同写法**（写 `0` / 留空 / 不写 `—`），消费处遍地，读者需要一处可查 | 视觉 §3.8 那张表，编号 A / B | 分组人数 `0` 显示 `0`；零按钮单元格留空 |
| **能力级** | **一种平时被禁止的能力，被允许用一次**，本身自带一套规格 | **授予它的那一节**写"唯一"，别处只写"见 §X" | 横滚 → 视觉 §10.1（交互规格见本节） |

**所以"例外清单只能有一份"要按级读**：记号级必须有唯一一份（否则读者查不全）；能力级必须"每处只有一个指向"（否则规格会分叉成两份）。**横滚不是漏登在 §3.8 —— 它属于另一种例外，登记在另一种地方。** 以前我写的是"别去 §3.8 找横滚"（一句提醒），现在它是这条规则的推论（提醒靠人记，规则会自己传播）。

**为什么不做"全局例外总表"**（视觉的判断，我同意，而且他的理由比"难维护"硬得多）：记号级能集中，是因为它只替换一个值，**集中成本为零**；能力级一旦进总表，就变成"任何东西都能被登记进来"的通道 —— 而本文 §5.1.3 的护栏要求**每条例外都能算出代价**（几行？占了什么？换回了什么？）。**登记表会把这个代价问题悄悄跳过：表格里的格子是免费的，代价不是。** 换句话说，集中登记对"值"是便利，对"能力"是**免责通道**。

**与列表页的形态区分**：矩阵**强制紧凑行高 40px**（`--row-h-compact`）。它是决策视图不是浏览视图，一屏要看到尽可能多的库 × 组组合；列表页默认 48px 不动。**除矩阵外任何表格不得 `overflow-x`。**

前端实现四条（照做，别自己发挥）：

| # | 规格 | 不做会怎样 |
|---|---|---|
| 1 | `border-collapse: separate` + `border-spacing: 0` | `collapse` 下 sticky 单元格的边框会丢，冻结列与普通列之间失去分界 |
| 2 | `width: auto` + `min-width: 100%`，**禁 `table-layout: fixed`** | 写 `fixed` 会让 `width:auto` 失效，容器再窄也不溢出，**横滚根本不出现**，最右几列被压扁 |
| 3 | 首列 `sticky; left:0; z-index:2`；表头 `sticky; top:0; z-index:3`；交叉格（`th.m-row-head`）`z-index:4` + `--paper-2` | 层级错了会出现"滚动的格盖住表头"或"表头盖住冻结列" |
| 4 | 行 hover 时**冻结列跟着变色**：`tr:hover .m-row-head { background: var(--row-hover) }` | 冻结列不变色 = 整行只变一半，横向滚动时尤其像渲染 bug，非常显脏 |

- 列宽：首列 240、分组列 96（`<colgroup>` 给 240 + 96×N）。
- 首列右侧 `1px --line` 是**冻结分界线**（不是"描边"），必须实色背景 `--surface`，否则滚动内容穿透。
- 滚动暗示只靠那条分界线 + 原生细滚动条；**不做右侧渐隐遮罩**（会吃掉最右一列内容）。
- 单元格最小 44×44（触摸达标）。

**单元格内容 = 字符 + 零填充色**（角色属于"形态维度"，不占色彩预算）：

| 值 | 呈现 | 说明 |
|---|---|---|
| `viewer` | `○ 只读`（`--muted`） | — |
| `editor` | `◐ 可上传`（`--ink-soft`） | 若目标字体缺 `◐`，退化用 `上传` 二字（11px），其余字符不变 |
| `kb_admin` | `● 库管理员`（`--ink` 600） | — |
| 无授权 | 留空；hover 显示 `＋`（`--line-strong`） | `＋` 只是"可点"暗示，**不代表点击即授权**（点击只开面板） |

图例一行必须常驻表格上方（12px `--muted`，项间距 `--sp-4`），不能只在首次出现：`○ 只读　◐ 可上传　● 库管理员　· 点单元格切换`。

### 6.2 空单元格意味着什么（必须有图例，否则误读）

**空白 = 该 `(知识库, 分组)` 组合没有授权记录。它不表示"该组无人可访问"** —— 该组成员仍可能通过个人成员授权访问（C5）。上面那行图例末尾的「· 点单元格切换」不够，**这句解释必须单独出现在工具栏右端**（12px `--muted`），常驻：

`空格 = 该分组未授权 · 成员仍可能通过个人授权访问`

两条推论（交互上要贯彻）：

1. 矩阵里**不提供"未授权所以一定没权限"的汇总提示**（比如"3 个库对所有人开放"这类推断）。矩阵只能证明"哪些组被授了什么"，不能证明"谁能看什么"——后者要把个人授权也算进去，那是成员分区的活。
2. 每一行的"覆盖度"不做进度条或百分比。理由同上：分母（应覆盖人群）不存在，只存在"已授权的组"。

### 6.3 改一个格子

| 步骤 | 屏幕上发生什么 |
|---|---|
| 1. 点击格子 | 格子下方弹出小面板（宽 200，`--shadow-pop`，`--z-dialog`−1），三角尖端指向被点格子；焦点移入面板第一个可选项 |
| 2. 面板内容 | 标题 `「财务制度库」×「财务组」`（12px `--muted`）；三行 radio：`只读 viewer / 可上传 editor / 库管理员 kb_admin`（当前值预选中）；分隔线；`收回授权`（`--red`）或 `未授权`（禁用的说明行）；底部一行 `该组 12 人（3 人未激活）`（`≥20 人` 时该行字重提 600，**仍不上色**，见 §6.7） |
| 3. 选一个角色 | 立即 `POST /kbs/{kb_id}/groups {group, role}`；面板关闭；格子先变 `--paper-2` 骨架 200ms，成功后显示新角色 |
| 4. 成功 | toast `「财务组」获得「财务制度库」的可上传权限` + 撤销条（§6.6）；格子显示 `◐ 可上传` |
| 5. 失败 | 格子**回滚到原值** + toast `保存失败：服务器异常（500），请稍后重试`（不留在乐观态，乐观态不回收是治理界面最危险的事） |
| 6. 选「收回授权」 | 先确认框（§8 强度 3，带人数）再 `DELETE /kbs/{kb_id}/groups/{group}` |
| 7. 点选当前已有角色 | 不请求，只关面板（避免无意义的写入与审计噪声） |

面板键盘：`Esc` 关闭并回焦点到格子；`↑/↓` 在 radio 间移动；`Enter` 选中。

### 6.4 按行批量（一个库 × 多个组）

- 入口：行首（库名右侧）`⋯` → `这一行批量授权`。
- Dialog：标题 `批量授权「财务制度库」`；副标题一行 `当前：财务组 只读、管理层 库管理员`；主体 = 分组复选列表（`☑ 财务组 12 人（已授权：只读）`），勾选后统一设一个角色（下拉）；底部 `应用到 3 个分组`。
- 提交：**串行 N 次** `POST /kbs/{id}/groups`（无批量接口）。逐条结果 → 部分失败清单（§7.4）。
- 成功：toast `已为 3 个分组授权，其中 1 个角色被更新`。

### 6.5 按列批量（一个组 × 多个库）—— 最高风险操作

- 入口：点击列头（分组名）→ 面板 `财务组 · 12 人` + `整列授权…`。
- Dialog：`为「财务组」批量授权知识库`；副标题 `将授予 12 名成员以下 12 个知识库的访问权`；列表按分级倒序（机密在前）并显示 `[机密]` 签；其中机密库数量单独一行强调：`其中 3 个为机密库，授权后该组全部成员可检索其内容。`
- 确认强度：**强度 3**（确认框 + 可撤销 10s）。不做输组名确认（列批量可撤销，且输组名在矩阵里显得过重）。
- 提交：串行 N 次 `POST`。
- **默认全不勾选**：进入时所有库都是未勾选状态（安全的那一边），提供 `全选` 但旁边标注 `共 12 个库，含 3 个机密`。

### 6.6 误操作撤销（矩阵是"点了就生效"的地方，撤销是必需品）

规格已由视觉规范 v1.1 §5.5 定：**`--amber-bg` 底 + `1px --amber-line` 框**（不是 `--blue-bg`——它 == `--row-sel`，会与"行选中"撞语义；也不是我原提的 `--paper-2`——与页面底明度差仅 2%，60px 高的一条几乎看不见，看不见的撤销等于没有撤销）。`--amber` 的语义域是「待你处理」，撤销窗口正是"在等你决定"，不新增颜色。

| 项 | 规格 |
|---|---|
| 位置/高度 | 与批量条**共用容器与等高规则**（`--bar-h` 60px，替换工具条，表格位移 0px） |
| 文字 | 13px `--ink`：`已更新「财务组」×「财务制度库」的授权：无 → 只读` |
| 动作 | 文字按钮「撤销」12px 600 `--amber`，高 28px，边框 `--amber-line` |
| 倒计时 | 12px `--mono` `--amber`，靠右、位于「撤销」左侧 `--sp-3`；显示剩余秒数（`10s` → `1s`） |
| 关闭 | 右侧 `✕`（32×32，`aria-label="关闭提示"`）；到时 `opacity` 200ms 消失，**不做进度条** |
| 退化（同屏 amber 太多，如矩阵有 `▤ 分组签`） | `--surface` 底 + `1px --line-strong` + **左侧 `3px --amber` 竖条**；竖条必须保留，那才是让人看见它的东西 |

交互规则：

- **撤销窗口 10s，锁死，不做配置**。常量 `const UNDO_MS = 10000`，改时长只动这一处；**倒计时显示 10→1，不显示 `0`**（到 0 就是已经没了，写出来只是让人以为还能点）。
- **剩余 ≤3s 时倒计时字重 500→600，不改颜色**（视觉 v1.3）。不要用红色：红色属于危险域，撤销窗口到期不是"出问题"，只是"窗口关了"。也**不建议**为"更紧张"缩短到 8s —— 缩短窗口只降低撤销成功率，视觉上零收益。
- 撤销 = 发**反向请求**：原本无授权 → `DELETE`；原本有角色 → 再 `POST` 回旧角色。撤销本身失败 → toast `撤销失败：该授权已被他人修改，请刷新查看`。
- 撤销只针对**最近一次**操作，不做操作栈（无构建，栈的复杂度与收益不成比例）。批量操作的撤销按"整批反向"处理，文案 `已撤销上一步的 3 项授权`。
- 键盘可达：撤销条出现时**不抢焦点**（正在连续改格子时抢焦点会打断操作），但「撤销」按钮在 Tab 序列里、位置紧随工具条之后；出现时 `aria-live="polite"` 播报一次 `已更新授权，可在 10 秒内撤销`。
- **同一个库连续改两格**：后一次覆盖前一次的撤销条（只保留最近一次），文案带对象名，用户看到的是"最后一次改了什么"。

### 6.7 人数多的组怎么提示（视觉 §11.4：行内零警示，护栏全在确认环节）

| 情况 | 表现 |
|---|---|
| 列头 | 第一行 `财务组`（12px 600 `--ink-soft` 居中，超长 `…` + `title`）；第二行 `12 人`（12px `--mono` `--muted`），列宽 96 放不下时只留第一行 + `title` 带人数 |
| **`total ≥ 20`** | **行内一个字都不加**：人数数字 500→**600** + `title="该组 48 人，改动将同时影响 48 人"`。**不加 `!`、不加 amber、不加徽标**（初版我加了 `!`，v1.2 撤回）。护栏改在两条确认路径上：① 格子弹层底部那一行人数文字变 600；② 点选角色后的确认框首行加 12px `--amber`：`本次改动影响 48 人` + 受影响账号前 3 个 + `等 48 人`。若该格原本**无授权**（新增授权而非改角色），文案改为 `该组 48 人将立即获得访问权` |
| `active < total` | 列头人数显示 `48 人（6 未激活）` 的缩写 `48·6待` + `title` 说明。授权对未激活账号也生效（等它们激活后自动可读），这点必须在 `title` 里写明 |
| 人数为 `0`（孤儿组，后端不校验分组名导致） | 显示 `0`（`--muted`），**不用 `—`**（**视觉 §3.8 例外登记 A**）。列头 `title` 追加 `该分组当前没有任何成员` |
| 未分组（`group === ''`） | 单独一列 `未分组`，**列头标 `不可授权`**、整列格子不可点（后端 `set_group_grant` 会报 `分组名不能为空`）。它存在的价值是让人看到"有 2 个账号没分组，他们拿不到任何分组授权" |

> **候选角色面板里要不要提前警告**：要，但只用文字不用颜色——面板底部那行 `该组 48 人（6 人未激活）` 在 ≥20 时字重提到 600。理由同视觉 §11.4：**色只能给一处**，这里给了弹层里的 amber 就不会再给面板里的 amber，否则同屏两处橙，用户只记得"屏幕有点橙"。阈值固定 20 人，不做配置（可配置的阈值等于没人配）。

### 6.8 矩阵的其他状态

| 状态 | 表现 |
|---|---|
| 加载 | 8 行 × 5 列骨架（视觉规范 §5.1） |
| 没有任何分组（`groups` 只剩 `""`） | 空态：`还没有任何分组` / `分组是矩阵的列。先到「用户管理 → 设分组」给账号设分组，再回来授权。` / 按钮 `去用户管理` |
| 分组很多（列 > 12） | 默认显示"有授权记录的组" + 按人数降序补足到 12 列；末尾一列 `另有 N 组 ▾`，点击展开全部（展开后该列消失）。**隐藏列时必须在表头写出"另有 N 组（其中 M 个有授权）"**，否则用户会以为看不到的地方没有授权 |
| 库很多（行 > 30） | 顶部搜索（按库名/编码，前端过滤，280ms 防抖）+ `只看机密` 勾选 + `只看启用` 勾选（默认只看启用？**不**：默认全部，因为归档库的授权仍需清理） |
| 归档库行 | 行首状态徽标 `归档`；该行所有格子的 `title` 追加 `该库已归档，授权保留但不参与问答检索` |
| 只读（无权限） | 非 admin 不可达（路由守卫） |

## 七、批量操作

### 7.1 能批量做什么（按现有接口能给到的能力，逐条核对过）

| 操作 | 接口 | 批量方式 | 结论 |
|---|---|---|---|
| 归档 | `PATCH /admin/kbs/{id}` `{status:'archived'}` | 串行 N 次 | ✅ 可批量 |
| 恢复启用 | 同上 `{status:'active'}` | 串行 N 次 | ✅ 可批量 |
| 改数据分级 | 同上 `{level}` | 串行 N 次 | ✅ 可批量 |
| 改归属部门 | 同上 `{dept}` | 串行 N 次 | ✅ 可批量 |
| 删除 | `DELETE /admin/kbs/{id}` | 串行 N 次 | ✅ 可批量（确认强度 4） |
| **导出** | 无接口 | — | ❌ **删掉**。视觉规范 §5.4 的示意图里有"导出"，本产品无导出接口，不要画一个点了没反应的按钮 |
| **移动到分组** | 无此概念 | — | ❌ **删掉**。知识库不属于分组；分组是"授权对象"不是"容器"。`POST /kbs/{id}/groups` 是授权不是移动，把它们混在一个按钮里会让人以为库被搬走了 |
| 批量加成员 / 批量改授权 / 批量移除成员 | 无批量接口 | — | ❌ 不做，且**成员表与分组表连复选框列都不加**（视觉 v1.2 §11.5）。成员与授权是低量、单项、高风险的决策，批量改权限的收益远小于误操作代价；一次误批量移除可能让 12 个人同时失去访问权，而他们只会看到"昨天还能查，今天查不到了" |
| 批量审批文件 | `POST /files/{fid}/approve` | 串行 N 次 | ✅ 做（在文件分区，§5.1.2），不进列表页批量条 |

**最终批量条（列表页）**：

```
已选全部 128 项（含未在当前页显示的 108 项）   取消选择   [归档][恢复][分级▾][部门▾]  删除
```

- 顺序：常规操作在前（ghost 32px），`删除` 最右（`--red` 文字按钮）。
- 「分级」「部门」是下拉按钮，选中值后**立即执行**（不再二次确认——改分级/部门可逆，且确认框会让批量操作变得没法用）。
- 禁用规则：选中项里含默认库（`id=1`）时，`归档` 与 `删除` 置 `opacity:.45` + `title="含默认知识库，它不可归档/删除"`（视觉规范要求禁用不隐藏）。
- 选中项含自己无 `admin` 权限的库：本产品不存在（列表只返回有权限的库），但 `PATCH` 仍需 `admin`（C6）——若当前用户是 `kb_admin` 而非 `admin`，**整个批量条不渲染**（他连单个都改不了，给批量条更糟）。

### 7.2 二次确认文案

| 操作 | 强度 | 文案 |
|---|---|---|
| 批量归档 12 个 | 2（可撤销） | 标题 `归档 12 个知识库？` 正文 `它们的文档将不再参与问答检索，历史授权保留。随时可以恢复。` 按钮 `取消` / `归档 12 个` |
| 批量改分级为机密 12 个 | 1（可撤销） | 无确认框，直接执行 + toast + 撤销条 |
| 批量删除 5 个 | 4（不可逆） | 标题 `删除 5 个知识库？` 正文第一行 `此操作不可撤销，界面内无法恢复。` 然后列出前 3 个名字 + `等 5 个`，再一行 `这些库共 47 个文档将同时不可见。` 输入框 label `请输入 DELETE 以确认`（批量无法逐个输名字，用固定词）按钮 `取消` / `永久删除 5 个`（**实底危险按钮 `.btn-danger`**，输入正确前禁用） |

> 弹窗外观（3px `--red` 通栏条、标题衬线 16/700、按钮左取消右危险）由视觉规范 v1.1 §10.3 定，见 §8.2。

### 7.3 部分失败怎么呈现

串行 N 次请求必然出现部分失败。**呈现必须能回答三个问题：哪几个成功、哪几个失败、为什么。**

- 全部成功：toast `已归档 12 个知识库` + 撤销条。
- 有失败：**不关闭任何东西**，把一个成绩单 Dialog 叠在上面：

```
3 个成功，2 个失败

✓ 财务制度库        已归档
✓ 运维手册库        已归档
✓ 产品规范库        已归档
✕ 采购合同库        失败：服务器异常（500）
✕ 临时测试库        失败：该知识库不存在（可能已被他人删除）

[重试失败的 2 项]        [关闭]
```

- 列表**只移除成功的行**（失败的仍在，且行级 `outline --red` 1.5s），并重新计算"共 N 个"。
- 重试只对失败项再跑一遍；再次失败则保留 Dialog 并更新原因。
- 无障碍：Dialog 打开时 `role="dialog"` + 焦点落在标题；成绩单整体 `aria-live="polite"` 不重复播报（用 `role="status"` 在 Dialog 内一次性呈现）。

## 八、破坏性操作的确认强度分级

四级。"默认值必须是安全的那一边"落到每一级上，就是**默认焦点与默认按钮永远不是那个破坏性的**。

| 强度 | 形态 | 适用 | 默认焦点 | 可撤销 |
|---|---|---|---|---|
| **1** | 无确认，直接执行 | 改分级、改部门、改角色、批准入库、创建 | — | 部分（改分级/部门/角色可再改回；批准不可） |
| **2** | 一次点击 + 确认框（`取消` 在左、默认聚焦） | 归档、移除成员、拒绝文件、收回单个分组 | `取消` | ✅ 10s 撤销条（**拒绝文件除外**，见 8.1） |
| **3** | 确认框 + 影响面清单（列出人数/文件数） | 收回分组授权、删除单个文件、按列批量授权 | `取消` | ✅ 10s（删除文件除外，C3） |
| **4** | 输入名称确认（`确认` 按钮在输入正确前禁用） | 删除知识库（单个）、批量删除 | 输入框 | ❌ 不可逆 |

### 8.1 四者的具体强度与理由

| 操作 | 强度 | 理由 |
|---|---|---|
| **删除知识库** | **4** | 不可逆（C3），且连带让 N 个文档从问答里消失。输入库名，让手指离开回车键 0.5 秒 |
| **归档知识库** | **2** | **真的可逆**（`PATCH status=active` 立刻恢复检索）。给 4 级确认是过度设计，会让用户不敢用归档——而归档恰恰是"不想删的库"的正确归宿。但必须说清后果：`问答将不再引用本库文档` |
| **移除成员** | **2** | 可逆（再 `POST members` 同角色即可），且单点影响一个人 |
| **收回分组授权** | **3** | 可逆，但**一次影响一批人**（12 人失去访问权）。升级到 3 级是因为"影响面"而不是"不可逆" |
| **删除单个文件** | **3** | 不可逆（C3 无恢复接口）+ 会让一段知识从问答里消失。确认框必须写明 `界面内无法恢复` |
| **批量删除知识库** | **4** | 同单个删除，且输名字已不可行 → 输 `DELETE` |
| **拒绝文件** | **2** | 一次确认就够：文件没进过索引，删掉的只是"这次上传"。但**不可撤销** —— `approve_file` 前置 `status='pending'`，驳回后无法再批准，上传者只能重新上传（旧记录留在列表里作为"已驳回"，可在该行删除）。所以这一项**不给撤销条**，确认框必须写 `拒绝后无法再批准，上传者需重新上传。` |

### 8.2 确认框的通用写法（避免写成"确定要删除吗"）

四行结构，缺一行就是不合格的确认框：

```
① 标题（衬线 16/700）：动作 + 对象 + 数量    「删除知识库「财务制度库」」
② 后果（最重要的一行，13px --ink-soft）：具体、可核对的数字
   「将同时移除 128 个文件的索引记录，12 名成员与 3 个分组授权一并失效，问答不再引用。」
③ 不可逆性声明（仅 3/4 级）
   「此操作不可撤销，界面内无法恢复。」
④ 按钮：取消（左，ghost 36px，默认焦点） + 动作（右，实底危险按钮 .btn-danger）
```

**外观硬规格**（视觉规范 v1.1 §10.3，全系统唯一允许出现红色实底按钮的地方）：

| 项 | 规格 |
|---|---|
| 容器 | 现有 `<dialog>` + `--shadow-pop`，宽 `min(480px, 92vw)` |
| 顶部通栏条 | **3px `--red`**，贴顶、贯穿全宽、无圆角（靠 `overflow:hidden` 裁齐） |
| 标题 | `--fs-lg` 16px `--serif` 700 |
| 正文 | `--fs-sm` 13px `--ink-soft` |
| 二次确认输入 | 库内有文件时要求输库名；输入框用现有规格（`--paper-2` 底 + `1px --line`） |
| 按钮顺序 | **取消在左、危险在右，固定不反转**（反转会让肌肉记忆点错） |
| 危险按钮 | `.btn-danger`：`--red` 底 + `--seal-ink` 字，hover `--red-dk`，disabled `opacity .45` |
| 禁用 | 该按钮**只能**出现在破坏性确认弹窗内；列表行内、页头、菜单里一律用 `--red` 文字按钮 |

**禁止的写法**：「确认删除？」「此操作不可恢复，是否继续？」（"是否继续"是让用户猜后果）。
**禁止的措辞**：任何含"回收站""可恢复""可以撤销"的删除文案——没有恢复接口（C3），说了就是骗人。归档/移除成员/收回分组这三类**可以**且**必须**写"可撤销"，因为它们真的可逆。

## 九、键盘与无障碍

### 9.1 Tab 顺序（每个页面一条线性路径，不设 tabindex 正数）

**列表页**

```
topbar 一级导航（问答→知识库→控制台）
→ 页头「＋ 新建知识库」
→ 工具条：搜索 → ✕ 清空（有值时） → ufilter ×3 → 部门 → 分级 → 清除筛选（有值时） → 密度
→ 表头复选框
→ 表格 body：每行 tr（tabindex=0） → 行内「成员」 → 「⋯」
→ 页脚：每页条数 → 首页 → 上一页 → 页码 → 下一页 → 末页
```

**详情页**

```
面包屑上一级（「知识库」可点，回列表）
→ 页头主操作（上传文件） → 溢出 ⋯
→ subnav ×4（左右方向键在 tab 间移动，Enter/Space 进入）
→ 内容区（见各分区）
```

**文件分区内部的 Tab 序（v1.4 结构变更后新增，唯一一条）**：

```
待审批 hint-bar 的「全部批准」（有 pending 且能审批时）
→ 表头复选框 → 每行 tr → 该行行内按钮（0–3 个，顺序 = §5.1.3 矩阵）
```

- `pending` 行的第一个行内按钮是「审批」，**它就是该行的主入口**，不需要先 Tab 过别的按钮。
- 从审批弹窗关闭后焦点回**该行的「审批」按钮**（不是回表头、不是回 hint-bar）：批准下一个时不用重新 Tab 一整行。
- **零按钮行（非库管的 `pending`/`rejected`）在 Tab 序列里只剩 `tr` 本身**：这是正常的，但要保证 `tr` 的 `aria-label` 说清了状态（见上一条），否则键盘/读屏用户 Tab 到这里只能听到"行"。
- **禁用按钮（成员表「移除」/「改角色」这一类 locked 状态）必须仍可 Tab 到，且有可见焦点环**（`:focus-visible`，全局 `2px --blue`）。既然我们选择 `aria-disabled` 而不是原生 `disabled`，就必须把焦点可见一起做掉 —— 只保留可聚焦却不给焦点环，等于让键盘用户"点进空气里"（视觉 v1.6 §11.8 同步要求）。

- 表格行的 `tr` 不可放进 Tab 序列两次：`tr[tabindex=0]` 只承担"进详情"，行内按钮各自独立可聚焦。Tab 走到 `tr` 上时**不显示行操作**（视觉规范已要求行操作默认常显，所以不需要 hover/focus 才出现）。
- **`tr` 必须有 `aria-label`**（v1.6）：读到行时先听到"这是什么、什么状态"，而不是"行 7，空白"。文件表按 `{文件名}，{状态}，{上传人}上传，{相对时间}` 拼（§5.1.3），成员表按 `{姓名}，{生效角色}，{来源}` 拼。这条在**零按钮行**上是唯一的可用信息来源，不是锦上添花。
- 抽屉打开时，**焦点移入抽屉，背景不遮罩**（视觉规范 §9）——因此背景仍可 Tab 到，这违反了"模态焦点陷阱"。解决：抽屉用 `role="dialog" aria-modal="false"`，并在抽屉打开时把 `.kb-detail-body` 设 `inert`。这样"不遮罩"的视觉要求与"焦点不漏"的无障碍要求同时满足。

### 9.2 快捷键（3 个，不多不少）

| 键 | 作用 | 作用域 | 冲突处理 |
|---|---|---|---|
| `/` | 聚焦搜索框 | 列表页 | 在 `input`/`textarea`/`dialog` 内不触发 |
| `N` | 打开「新建知识库」 | 列表页，仅 `admin/superadmin` | 同上；`Shift+N` 不触发 |
| `Esc` | 关闭最上层：弹层 → 抽屉 → Dialog → 清空搜索框（有值时） | 全局 | 有未保存修改时先弹确认，不直接关 |

- **不做**排序、翻页、全选的快捷键：这三个都有可见控件，加键位只增加记忆负担与冲突面。
- 所有快捷键在工具条最右的 `⋯` → `快捷键` 中列出（一个只读 Dialog，三行）。
- 快捷键**不做开关**（3 个键不需要配置面板）。

### 9.3 焦点管理（6 个场景写死）

| 场景 | 焦点去哪 | 为什么 |
|---|---|---|
| 进入详情页（点行/Enter） | 详情页 `<h1>`（`tabindex="-1"`）+ `document.title = '财务制度库 · 知识库'` | 读屏用户需要知道"页面变了"，且虚拟光标位置重置到标题 |
| 返回列表（面包屑） | **回到刚才那一行的 `tr`** | 视觉上滚动位置已还原；焦点不跟上，键盘用户会从页头重新 Tab 一遍 |
| 打开抽屉 | 抽屉标题（`tabindex="-1"`）；关闭后回**触发元素** | 通用规则，无一例外 |
| 打开 Dialog | Dialog 内第一个可交互元素；**危险确认框则是「取消」** | 危险操作的默认焦点永远在不危险那侧 |
| 关闭 Dialog（Esc / 取消 / 完成后） | 回到触发它的按钮 | 若该按钮已不存在（如列表行被删）→ 焦点回 `<h1>` |
| 切换 subnav 分区 | 新分区的第一个 `h2`（`tabindex="-1"`），**且 subnav 的 tab 保持选中态可继续左右键切换** | 分区切换是"同一页里翻页"，不是"跳转"，焦点不该跑回页头 |

补充：批量条出现/消失时**不移动焦点**（移动会打断选择动作），改用 `aria-live="polite"` 播报 `已选 3 项`。

### 9.4 无障碍清单（可逐条验收）

**结构**

- [ ] 表格是真 `<table>` + `<caption class="sr-only">`（列表页 `知识库列表，共 128 个`；矩阵 `知识库与分组的授权关系`）
- [ ] 表头 `<th scope="col">`；矩阵首列 `<th scope="row">`；排序列 `aria-sort="ascending|descending|none"`
- [ ] 分区用 `<section aria-labelledby="{h2-id}">`；subnav 用 `role="tablist"` + `role="tab"` + `aria-selected` + `aria-controls`
- [ ] 抽屉 `role="dialog" aria-modal="false"` + 背景 `inert`；Dialog `role="dialog" aria-modal="true"`

**键盘**

- [ ] 全站可仅用键盘完成：找库 → 进详情 → 改分级 → 归档 → 返回列表并停在原行
- [ ] 矩阵可仅用键盘完成：Tab 到某格 → `Enter` 开面板 → `↑↓` 选角色 → `Enter` 生效 → `Esc` 回格子
- [ ] 焦点环恒可见：`outline: 2px solid var(--blue); outline-offset: -2px`（表格行内用 `-2px` 贴边，避免被 `overflow:hidden` 裁掉）
- [ ] 无 `tabindex` 正数；无 `outline: none`
- [ ] `Esc` 在每一层都能关闭（弹层 → 抽屉 → Dialog），且不会连带关闭下一层

**读屏**

- [ ] 每个图标按钮有 `aria-label`（`⋯` → `更多操作`、`✕` → `关闭`）
- [ ] 矩阵每个格子按钮的 `aria-label` 完整：`财务制度库 × 财务组：当前未授权，回车修改`
- [ ] 状态不只靠颜色：状态徽标带文字（视觉规范已定）；分级用线框签 + 文字；成员角色用文字 + 字重
- [ ] 表单错误：`aria-invalid="true"` + `aria-describedby` 指向错误文字；提交失败后焦点移到第一个错误字段
- [ ] 操作结果：成功 toast `role="status"`；失败 toast `role="alert"`；`aria-live` 容器常驻 DOM（后插入的 live region 不被播报）
- [ ] 加载中：`aria-busy="true"` 在容器上；骨架块 `aria-hidden="true"`

**对比度与动效**

- [ ] 12px 文字 ≥ 4.5:1（视觉规范 §4.6 已给出验收表）
- [ ] `prefers-reduced-motion: reduce` 下：抽屉/弹层瞬开、骨架静止、撤销条不倒计时动画（但 10s 仍按真实时间过期）
- [ ] 触摸目标：桌面 ≥ 28×28（`::after` 扩热区），移动 ≥ 40×40；矩阵格子 ≥ 44×44

## 十二、验收清单（交互层，逐条可测）

> **流程项（v1.7 补、v1.9 加固，不是界面项）**：任何一条设计结论**改动或撤回**时，必须同时通知**视觉 / UX / 前端**三方。规则一句话：**结论有主，但引用它的文档没有主，改结论的人负责把引用一起改掉。**
>
> **加固做法（v1.9，视觉提的，本文照办）**：
> 1. **只引章节号，不复制结论正文**。本文凡引用视觉结论一律带 `§`；数值（列宽、断点、令牌）在我这里重复出现只是为了方便阅读，**冲突时以视觉章节为准**。
> 2. 被引章节变更时，引用方只需判断"这个章节号是否仍成立"，不必逐字对账 —— 这也是本轮两份文档各写反一次的根因：**都复制了结论正文，于是各自演化了两个版本**。
> 3. 反过来也成立：本文的结论被别人引用时，被引用的是章节号，所以**结论要留在章节里，不要散落在注记、脚注、附录里** —— 散落的结论没法被正确引用。
> 4. **理由可以留在原地，规格必须回到它的归属章节**（v1.10，视觉提的，回赠给他的"结论留在章节里"）。判据：一段文字里出现**可执行的数值、顺序、文案原句、状态判定**，它就是规格，不管它挂在哪个"为什么"下面 —— 挪回归属章节，理由块里只留"为什么"。
> 5. **每条举例都必须能对应到一个当前可渲染的行状态**（v1.10，视觉提的）。例句、`title`、按钮文案都长得像规格，读者会照抄；所以**失效的例句必须删掉或当场标注失效**，不能留在原地等人抄走。本文目前有 0 条失效例句（v1.6 那条"该文件已审批，无需重复操作"从一开始就没进本文），但这条判据以后每次改状态模型都要重跑一遍。
> 6. **对账动作优先于"再读一遍"**（v1.12，视觉的推论，我同意并补了例证）：如果一条规格从没被人拿去过账，它大概率已经错了 —— 本文 §1.2 那句"矩阵是第 4 个 tab"活了十个版本，就是因为它从没和代码对过账。所以改文档时优先**加一条可执行的对账动作**（数一次 `<th>` 数、`grep` 一次文案原句、点一次最右列的按钮），而不是"再通读一遍"。**通读只能发现"读不通"，发现不了"写错了"。**

要点：

1. 页头只有 1 个主操作；「批量」属于工具条不属于页头（视觉规范 §7 陷阱 3）。
2. 工具条的控件顺序 = 用户实际操作顺序：先搜、再缩范围（ufilter）、再精筛（部门/分级）、最后清空。
3. 行操作常显（非技术人员用，hover 才出现等于没有）。
4. 复选框列**恒在**，任何档位、任何模式都不移除（视觉 v1.11 §3.2：线上 `no-check` 模式用 `display: none` 去掉列，而 `<colgroup>` 里还留着那一列的 `<col>` —— **两份列数一旦不等，从缺口起后面所有列整体左移一格**，库名列被压成 0 宽、右侧凭空多出约 100px 留白）。窄容器下退让的是「上传时间」，不是复选框：**少一列 ≠ 少一个能力**，批量批准在 `hint-bar` 里本来就不依赖它。
5. 最后一列是「变更时间」且**列头不可点**（视觉规范 v1.1 §3.5）；「范围」列显示 `▤3 组` 这种带计数的形态，`title` 自曝是推导值（§3.7）。
6. `hint-bar` 与表格之间只隔 8px，它不占 60px 工具条——**不要**为了提示而把页面顶下去。

产品通用知识库 ●启用    │      │      │      │      │  ＋    │        ← 首列 sticky
KB-0001 · 内部   [⋯]  │      │      │      │      │        │

要点：

1. **空格子的语义必须常驻可见**。这是整张表唯一会被误读的地方（"空格 = 没权限"是错的，成员可能走个人授权）。
2. 列头必须带人数：授权是"影响一批人"的操作，人数是决策依据。
3. `未分组` 列不可点（后端拒绝空分组名）；它的格子连 `＋` 都不显示。
4. 撤销条出现在工具条位置（等高 60px、`--amber-bg` 底、不位移）。
5. 首列 + 表头双 sticky，行高 40px（紧凑）。这是全产品唯一允许横向滚动的地方（§6.1）。
6. 格内是**字符 + 文字**，零填充色：角色不占色彩预算（视觉规范 §4.5 的"形态即维度"）。

## 附录 C · 响应式交互差异（只改交互，不改视觉）

视觉规范已经定死了 9 列 / 7 列 / 5 列 / 卡片四种形态与容器查询阈值。**这里只写"形态变了之后交互怎么变"**，不重复版式。

| 形态 | 交互差异 |
|---|---|
| **9 列 / 7 列**（≥860 容器） | 无差异。行内 2 按钮 + `⋯` 全部可见 |
| **5 列**（660–859） | 行内按钮从 2 个收到 1 个（`⋯`），`成员` 移进 `⋯` 菜单第一项。理由：收掉的 授权范围/负责人 恰恰是判断"要不要点成员"的依据，此时进成员页的动机变弱，收进菜单不损失效率 |
| **卡片**（<660） | ① 卡片右上 `⋯` 打开**同一个菜单**（不是新菜单）；② 整卡可点进详情，`⋯` 内部 `stopPropagation`；③ 复选框保留在卡名左侧；④ 批量条同样替换工具条（页面级工具条保留搜索与筛选）；⑤ 卡片间 `--sp-2` 8px，**不做左滑手势**（无构建、易与浏览器返回手势冲突） |
| **≤720 详情页** | ① `subnav` 横向滑动，切换分区后**把激活 tab 滚进视野中**（`scrollIntoView({inline:'nearest', block:'nearest'})`，`behavior` 跟随 `prefers-reduced-motion`）；② 分区计数（`文件 128`）在窄屏隐藏，只留分区名；③ 设置表单 `--content-form` 失效，占满宽度；④ 页头主操作降为图标 + 文字（不折叠成纯图标，中文单字图标不可辨识） |
| **≤720 抽屉** | `width: 100vw`；`Esc`/`‹ 返回` 关闭；打开时 `body` 锁滚动；焦点管理同桌面（§9.3） |
| **文件表收列**（容器：≥640 全 5 列 / 520–639 / <520 卡片） | ① 收到 4 列时「上传时间」并入文件名次行（`v2 · 2.1MB · 李四 · 42 分块 · 3 天前`，时间放末尾）；② **只退「上传时间」，复选框列不退**（v1.11 起复选框恒在，视觉 §3.2）；**批量批准更不能因为收列而消失** —— 它在 `hint-bar` 里是独立按钮，不依赖复选框列；③ 卡片模式下「预览」不可用时（非 md/txt），卡片内提示 `下载查看` |
| **成员表收列**（容器：≥860 全 6 列 / 660–859 / 440–659 / <440 卡片） | ① 收「授予人+授予时间」时**成对收**，不留半条审计信息；② 收到 3 列时「授权来源」列消失，**只把决定段并入成员列次行**（`@zhangsan · 决定来源：直接`；无 `display_name` 时写 `决定来源：直接`，不重复账号），被覆盖段不并入——决定段短、被覆盖段长，这样截断永远不会吃掉结论（视觉 §11.3）；③ 抽屉里必须能看全量来源链，否则窄屏用户永远看不到"被谁覆盖" |
| **分组表收列**（容器：≥740 全 6 列 / 640–739 / 500–639 / <500 卡片） | ① 收「授权人+授予时间」同样成对；② 收到 4 列时「人数」并入分组次行（`12 人 · 3 未激活`）——此时已无竖向比较需求（视觉 §11.2）；③ 但 **`≥20` 的字重标记在并入次行后仍然保留**（`24 人` 加粗），否则收窄后"影响面大"这一唯一线索消失 |
| **≤720 矩阵** | **矩阵不可用**，改为替代视图：先选知识库（下拉或复选），再给出一列分组清单（沿用 `.user-row` 形态，行高 48px：`☐ 分组名 13/600 · 当前角色 select.role-select`，与视觉规范 v1.1 §10.1 末段一致）。理由：240px 冻结列 + 96px×N 在 390px 上只剩 1.5 列，等于没做。替代视图与矩阵**共享同一套请求与撤销逻辑**，只是布局不同；撤销条形态不变（仍是 amber 横条，只是宽度 100%） |
| **触摸（pointer: coarse）** | ① 行内文字按钮热区扩到 40×40（视觉小、热区大）；② 矩阵格子 44×44；③ 单元格长文本 `title` 在触摸下不可用 → 该列改为**点击整行进详情看全名**（`title` 保留给指针设备）；④ 拖拽上传在移动端保留（Safari 支持有限，`<input type="file">` 兜底始终可见）；⑤ 输入框字号 ≥16px 防 iOS 聚焦缩放（视觉规范已定） |

**一条跨形态规则**：任何形态下，**破坏性操作的确认强度不降级**。卡片模式下的删除，依然是"输库名确认"，不因为屏幕小而简化成一次点击。

**一条实现硬要求，但它是交互问题不是版式问题**：收一列必须**三处同步**——该列所有 `td`/`th` 隐藏（CSS）+ `<colgroup>` 里删掉对应 `<col>`（JS）+ 重建后核对合计宽 ≤ 当前档位容器宽（视觉 v1.11 §3.3）。少同步一处，列映射从缺口起整体左移一格，后果不是"难看"而是：

| 用户做的事 | 实际命中的是 |
|---|---|
| 点「负责人」列表头（以为在排序/筛选） | 相邻列的表头 |
| 点某行的「成员」按钮（在 `⋯` 收起后的位置） | 左边一格的内容 |
| 横向滚动到"最右"找「⋯」 | 右侧约 100px 空白 |

**所以这类 bug 报上来会写成"点错了""按钮失灵"，而不会被写成"列没对齐"。** 验收时不要只看截图对齐：**点一次最右列的按钮，确认打开的是那一行那一列的东西。**

> 另外**「已驳回」必须用 `.st-reject` = `--ink-soft` on `--paper-2`**，不能用 `--muted`：`--muted` 在 `--paper-2` 上只有 3.9:1，不过 AA。现状代码里 `.ustatus.s-rejected` 用的正是 `--muted`，**必须一起改**。驳回是终态不是故障，所以用中性灰、不用朱砂；驳回原因放抽屉（后端 `approve_file(reject)` 不存理由，所以确认框不收集理由，见 §11 B5）。

> **为什么把版本/大小/上传人/分块塞进次行而不单独成列**：文件表只有一个扫读问题——"这是什么、什么状态、什么时候来的"。版本号大小分块是**审核时才要看的**，它们进抽屉（§5.1.3 行点击）不损失效率；而单独成 4 列会把文件名挤到 200px，正好毁掉最关键的那一列。视觉把这条提炼成了通则：**主字段所在列永远优先分配宽度，其余列按"是否参与扫读决策"排优先级。**
>
> **可排序**：本表只有「上传时间」可排（视觉 v1.3 §11.5）。**基准顺序 = `pending` 优先 → `uploaded_at` 降序**；点列头 `无 → ↓ → ↑ → 无`，第三态回基准。`↓/↑` 是纯时间序，**不再叠加"待审批优先"**（排序必须是真的，理由见 §5.1.3）。
>
> **`审批` 是否常驻**：本列只给宽度，**结论不在这里复述**（v1.9 引用规范，见 §十二）。一句话摘要：只在 `pending` 行渲染，规则与理由见 §5.1.3，按钮组合见 §5.1.3 的 5 行矩阵。
> 留一句给未来的自己：**"列宽稳定"和"位置固定"是两件事**，前者由 `<colgroup>` 固定宽度就已成立，后者靠右对齐就能拿到 —— 凡是有人（包括我）提议"为对齐摆一个用不了的控件"，先问"这两个诉求是不是已经被别的机制满足了"。

#### D2.0 没有 `display_name` 时怎么显示（视觉 v1.3 §11.7）

| 数据情况 | 主字段 | 次行 |
|---|---|---|
| 有 `display_name` | 姓名 13/600 `--sans` | `@username` 12 `--mono` `--muted` |
| 无 `display_name` | `username` 13/600 **`--mono`** | **不出次行**（避免同一串字符出现两遍） |
| `display_name === username` | 按"无 display_name"处理 | 同上 |

- **不弹错、不显示"未知用户"、不留空**。内部系统的账号员工认得，用户名本身就是有效标识；等宽字形本身就是"这是账号不是姓名"的视觉信号，比加"（账号）"三个字省地方。

#### D2.1 角色列的 `title`（结论必须能追溯到来源）

| 情况 | `title` |
|---|---|
| 只有直接授权 | `生效角色来自直接授权` |
| 只有分组授权 | `生效角色来自分组「财务组」` |
| 直接 + 分组，直接更宽或相同 | `生效角色来自直接授权（同时属分组「财务组」，个人授权优先）` |

#### D2.2 授权来源列的五种形态（视觉 §11.3 已定，这里只标数据来源）

| 形态 | 判定（前端可算，全部由 `members` + `kbs` + 分组表 得出） |
|---|---|
| `直接` | 该用户在 `members` 里，且不属任何被授权的分组 |
| `▤ 财务组` | 不在 `members` 里，仅因分组获得权限（**这类行只读**，操作列只有「改角色」→ 实际语义是"转为直接授权"） |
| `▤ 财务组 +2` | 命中 2 个以上被授权分组，`title` 列全部组名 |
| `直接（另 ▤ 财务组）` | 既在 `members` 又在被授权分组里；前半 `--ink` 600，后半 11px `--muted` |
| `创建者` | `username === kb.created_by`（数据来自 `GET /kbs` 的 `created_by`） |

- **不做"删除线"标被覆盖段**（视觉 §11.3 已禁）：权限表里划掉一行会让人怀疑数据出错。
- 截断永远发生在被覆盖段（次要），**决定段永不被截**。前端实现要点：两段各包一个 `span`，只给后一段 `overflow: hidden; text-overflow: ellipsis`，前一段 `flex: none`。

#### D2.3 操作列：四档禁用（与视觉 v1.3 §11.3 同表，**其中档位 2 我保留禁用，理由见下**）

| 档位 | 行类型 | `改角色` | `移除` | 原因文案（`title`） |
|---|---|---|---|---|
| 1 | 创建者（`created_by === username`） | **禁用** | **禁用** | 改角色：`创建者恒为库管理员，请添加其他成员作为库管理员`；移除：`创建者不可移除` |
| 2 | 其他 `kb_admin` | 可用 | **禁用**（视觉 v1.3 写"可"，**必须以本文为准**，见下） | `库管理员不可直接移除，请先把角色改为「只读」` |
| 3 | `editor` / `viewer` | 可用 | 可用 | — |
| 4 | 库里唯一的 `kb_admin`（非创建者）降级时 | **提交前拦截** | 可用 | `该成员是当前唯一的库管理员，请先指定另一名库管理员` |

**档位 2 为什么必须禁用（不是设计偏好，是后端会报错）**：`remove_member` 的 SQL 是 `DELETE FROM kb_members WHERE kb_id=? AND username=? AND role!='kb_admin'`（`workspace.py:305-308`）。对任何 `kb_admin`（不只创建者）执行移除，`rowcount=0`，接口返回 **404「成员不存在或为库管理员」**。所以档位 2 的「移除」若渲染成可点，用户点下去只会拿到一个像是"这个人不存在"的报错——比灰着更难懂。**唯一能移除 kb_admin 的路径是先降级（档位 4 的拦截只针对"最后一个"，其他 kb_admin 可以降级）再移除。**

**禁用态怎么画（v1.7，视觉 v1.6 §11.8）**：

| 项 | 规格 |
|---|---|
| 文字按钮（本表 `改角色`/`移除` 都是） | `color: var(--muted)` **换色**，**不加 `opacity`** —— 文字按钮没有边框底色撑形，透明度会淡到读不出，而"读得出字"是禁用态唯一的自我解释（4.6:1 ✓） |
| 语义色 | **一律收回**：`--blue`/`--red` 都退成 `--muted`。灰色的红按钮会让人读成"这是个危险的不可用操作"，信息反而错 |
| 可聚焦 | `aria-disabled="true"` + **保留 `tabindex="0"`**，拦截 click/Enter；不用原生 `disabled`（不可聚焦 → 读屏听到的按钮数变少） |
| 焦点环 | **必须可见**（`:focus-visible`，全局 `2px --blue`）。能聚焦就必须看得见焦点，否则键盘用户 Tab 过来屏幕上零反馈 |
| `cursor` | `not-allowed`；hover 不改色、不加底色 |
| `title` | 说明**怎么解锁**，不是复述"不能"。✅ `库管理员不可直接移除，请先把角色改为「只读」`；❌ `该成员不可移除`（把用户已经看到的结论念一遍，等于没说） |

> 判据（§5.1.3 三类）：档位 2/3 的禁用是 **locked**（改角色能解锁）；档位 1（创建者）两个按钮是 **forbidden** —— 谁都解不开，但"创建者不可移除"这条规则在界面上没有第二个落点，所以**画**，`title` 承载规则原句；文件表那个「审批」是 **unreachable**（状态终局、状态列已说明），所以**不渲染**。

**为什么要禁创建者的「改角色」**：同一条后端条件的另一面——"先把创建者降级成只读、再移除"是两步即可绕过"创建者不可移除"的路径，最后会得到一个"显示为只读、移除按钮却灰着"的怪东西。禁掉改角色，这条路才真正封死；它同时保证"库里永远至少有一个能管的人"，与 §5.2.3 的"唯一库管理员不可降级"是**同一条防错原则的两面**。视觉把这句总结得比我好，照抄在这里：**禁用要禁在"能让约束失效的那一步"上，而不是禁在约束最终触发的那个按钮上。**

#### D2.4 成员表的空态：`rows === 0` **不可达**，用 `hint-bar` 两个变体

⚠️ 与列表页同一类问题：`create_kb` 会把创建者写成 `kb_admin` 成员（`workspace.py:220`），所以成员表**至少恒有 1 行（创建者）**，空态大块永远不出现。可达的是这两种常态，按 `hint-bar`（32px，视觉 §5.2 规格）处理：

| 状态 | `hint-bar` 文案 |
|---|---|
| 只有创建者一行，且无任何分组授权 | `· 目前只有你（创建者）能访问这个库。 **添加成员** 或 **按分组授权**` |
| 只有创建者 + 有分组授权 | `· 除你之外没有单独授权的成员；当前 3 个分组（24 人）可访问本库。 **添加成员**` |

`rows === 0` 仍保留空态大块的实现（防"创建者被从用户表删掉"的极端情况），但文案必须诚实：`成员数据为空` / `未读到创建者记录，请刷新或联系平台管理员。`**不要**写"还没有单独授权的成员"（那会让人以为这是正常状态）。

#### D2.5 排序

- 基准顺序（默认，无 `▲▼`）：**角色权重降序**（`kb_admin` > `editor` > `viewer`）→ 姓名升序。
  ⚠️ 不能直接用后端返回顺序：`list_members` 的 `ORDER BY role, username` 是按**字符串**排的，实际结果是 `editor → kb_admin → viewer`（字母序），库管理员被夹在中间。前端必须按权重重排。
- 唯一可排序列「授予时间」：`无 → ↓ → ↑ → 无` 三态，第三态回基准顺序。
- 角色与来源列**不可排**（一个是固定权重，一个是聚合推导，排序没有意义）。

### D3 分组授权表（6 列，已与视觉 v1.2 §11.2 合并）

接口返回：`[{grp, role, granted_by, granted_at}]`（**没有成员数**——人数要从 `GET /admin/users` 的 `group` 聚合或矩阵的 `groups[].total` 拿；v1.5 的 B2 只解决了选人，**没给 `member_count`**，这一项仍挂在待办上）

| # | 列 | 宽 | 对齐 | 主 / 次 | 交互语义 |
|---|---|---|---|---|---|
| 1 | 分组 | auto（min 200） | 左 | 主 `grp` 13/600；次 `3 未激活`（12 `--muted`）；**孤儿组**次行 `该分组当前没有任何成员`（12 `--amber`） | 孤儿行：操作列只留「收回」一个按钮 |
| 2 | 人数 | 76 | **右** `--mono` | 计数；`≥20` 时字重 500→**600** + `title="该分组 24 人，改动将同时影响 24 人"` | **不加 amber、不加徽标**（护栏在确认弹窗，见 §5.3.2） |

> - **A（推荐）**：保持「收回」+ 操作列 112，本表不动，完整语义放确认弹窗标题 `解除「财务组」的整组授权？`；
> - **B**：操作列 112 → 144（内容宽 120），总宽 716 → 748，≥740 断点连锁改 **≥760**，`500–639` 那档也要重算。
>

#### D3.1 人数与孤儿组的判定

| 情况 | 人数列 | 次行 |
|---|---|---|
| 分组存在，`total=12, active=9` | `12` | `3 未激活` |
| 分组存在，全员激活 | `12` | 无次行（不显示 `0 未激活` 这种废话） |
| **分组在用户表里不存在**（孤儿授权：B3 修复**前**写入的历史数据，新建已不可能） | `0` | `该分组当前没有任何成员`（`--amber`） |
| 分组存在但 0 人 | 同孤儿行处理（`list_groups` 里不出现即视为不存在） | 同上 |

- **人数 `0` 显示 `0`，不用 `—`**（**视觉 §3.8 例外登记 A**）：空组是可清理的动作对象，`—` 会让人以为数据缺失。矩阵列头人数同理。
- 孤儿的琥珀**不是"影响面警示"**，是"数据异常待处理"。两者都用 `--amber` 但语义不同，别混——视觉 §11.4 禁的是后者。

#### D3.2 排序

- 基准顺序（默认）：**人数降序** → 组名升序。理由：本表唯一的治理问题是"哪个组影响面大"，人多的先看到；组数一般 3–8 个，稳定顺序的价值低于影响面排序。
- 可排序列：**人数、授予时间**（`无 → ↓ → ↑ → 无` 三态，第三态回基准）。
- 角色列不可排；分组名不设排序（它已作为兜底键固定在基准里，再加列头排序会与基准打架）。

> **三张表统一的五条硬规则**（与列表页同源，避免前端各写一套）：
> 1. 计数类（人数/文件数/分块数）**右对齐 + `--mono` + tabular-nums**；`0` 显示 `—`（视觉 §3.8），**只有一处例外且已登记**：分组人数 `0` 显示 `0`（**§3.8 例外登记 A**，见 D3.1）。
> 2. 时间列**右对齐 + `--mono` 12px `--muted`**，`title` 恒为绝对时间 `YYYY-MM-DD HH:mm:ss`。
> 3. 状态/角色**不共用列**：状态是徽标（形态 = 实底），角色是文字 + 字重（形态 = 字重）。混用会让一行出现 2 个色块。
> 4. 三张表都**不给横向滚动**（`table-layout: fixed` + `@container` 收起，与列表页同一套）。只有矩阵例外（§6.1）。
> 5. **成员表与分组表都不加复选框列、不做批量**（视觉 v1.2 §11.5）：成员与授权是低量、单项、高风险的决策，批量改权限的收益远小于误操作代价。文件表保留复选框（`pending` 行按批批准是真实需求，且 `hint-bar` 里另有「全部批准」兜底）。
