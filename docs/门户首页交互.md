## 一、信息架构：门户的"唯一任务"

### 1.1 唯一任务

> **在 3 秒内想起"我上次问到哪了"或"该问什么"，然后进入一次对话。**

判据：门户上不允许出现第二件事。所以**门户不做**：新建库、管理成员、看审计、改配置、看索引状态 —— 这些都在 `#kb` / `#admin`，越界就是"少了一个页面"。

### 1.2 区块顺序（单列三段 + composer，与设计文 §二 骨架一致）

```
┌──────────────────────────────────────────────────────────────┐
│ 下午好，李工                                   [控制台 ›]（仅管理员）│
│ 你有 4 个知识库的访问权限 · 上次提问 3 天前                      │
│ ─────────────────────────────────────────────────────────────│
│ 我有权限的知识库                                    全部 4 个 › │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐                        │
│ │ 财务制度  │ │ 产品手册  │ │ 客服话术  │   （≤3 张，auto-fit）    │
│ └──────────┘ └──────────┘ └──────────┘                        │
│ 最近更新：财务制度库 2 小时前 · 产品手册 昨天 · 客服话术 3 天前   │ ← 单行 strip
│                                                              │
│ 最近提问                                             会话 ›   │
│  企业微信 access_token 过期怎么办   产品手册  2 小时前    ›     │
│  …（4 行）                                                    │
│                                                              │
│ 常用问题                                                      │
│  · 对象存储怎么创建存储桶？                                    │
│  · 企业微信如何获取 access_token？                             │
│  …（5 条）                                                    │
├──────────────────────────────────────────────────────────────┤
│ composer（既有 .composer-wrap，常驻，不挪位）                   │
└──────────────────────────────────────────────────────────────┘
```

**顺序理由（不是审美）**：

1. **知识库在最前**：用户先确认"我能查什么"，再决定问什么。它是唯一能进治理页的入口。
2. **「最近更新」贴着卡片**：它回答的是"这些库里哪个刚被人动过"，只有紧贴库卡才有意义；单独成段会把 32px 的信息撑成 200px 的段落。
3. **最近提问第二**：回访用户最高频的动作。放中间是因为它需要"看"，不需要"选"。
4. **常用问题贴底**：新人的兜底，不在老用户的主路径上；放在最近提问正下方，形成"没历史 → 往下就是样例"的自然下坠。
5. **composer 常驻底部**：**不随态变化**。门户与对话共用同一个 `.composer-wrap`，进出两种态时它不动位置（这是"不跳页"的关键，设计文 §1.2）。

### 1.3 与前三个模块的关系（重要：门户不是第 4 个页签）

```
一级导航：［问答］［知识库］［控制台］        ← 仍然是三个，不加第四个
│
├─ #chat          问答模块的 idle 态 = 门户        ← 不是新视图，是 #viewChat 的另一种内容
├─ #chat/s/{id}   问答模块的 thread 态 = 对话       ← 同一容器，同一路由模块
├─ #kb            知识库列表（模块入口）
├─ #kb/{id}/…     库详情（子页，已有两级结构）
└─ #admin/{tab}   控制台（模块入口）
```

**为什么不做成 `#home` 第 4 个视图**（我原方案，已撤回）：

1. **语义**：门户上每个可点元素最终都打开同一条问答流。页签应当是"并列目的地"，而门户的每个出口都通向问答自己 —— 加页签等于把"入口"伪装成"模块"。
2. **成本**：`#home` 要动四处既有代码（`showView` 的视图数组 `app.js:72-82`、`parseHash` 默认值 `app.js:1025`、非管理员兜底 `app.js:68` 与 `app.js:1046`）；idle 态只动 `#viewChat` 内部，路由模块不变。
3. **现状已经长这样**：`#viewChat` 里的 `#empty`（`index.html:97-107`）就是一个带 5 条样例的空态 —— 门户是"把一个空态扩写成概览"，不是"新建一个页面"。这是最小改动，也是最不容易做坏的改动。

**「问答」页签的点击行为（唯一变化）**：恒去 `#chat`（= 门户）。在 thread 态点它 = 回门户 = 准备换话题，**这就是被删掉的「＋ 新会话」的替代路径**（§2.5）。
**反向不成立**：门户没有"进入当前会话"的按钮 —— 用户要看上次的对话，点「最近提问」或左栏会话项（两个入口都有明确对象，比一个"继续"按钮准）。

## 二、会话模型裁定（本文最核心的一节）

### 2.1 现状

| 位置 | 行为（行号为**改动前**，现值见括注） |
|---|---|
| `#btnNew`（`index.html:69`） | 点一次 → `newSession()`：`unshift` 一个空会话、渲染、聚焦输入框（旧 `app.js:199-206, 762`）。**现已删**，DOM 与绑定都不存在 |
| `renderSessionList()` | 按 `sessions` 数组顺序渲染，当前会话高亮（现值 `app.js:263`） |
| `showApp()` | 若 `sessions` 为空，**自动**建一个空会话（旧 `app.js:69`；现值 `app.js:51`）——即"进来就有一个空对话" |
| `appendMsg()` | 首条 user 消息截 22 字当标题（现值 `app.js:414-419`） |

问题不在"有会话"，而在**把"会话管理"这件系统的内部事，做成了一个需要用户按的按钮**。用户的原话是"感觉没必要"，这是对的：他不知道什么算"一个会话"，只知道"我在问一件事"。

### 2.2 裁定：**删除按钮 + 自动新建**（采纳 team-lead 的倾向方案）

**删除** `#btnNew`（含 `.btn-new` 样式与它的事件绑定；施工后 DOM 里已无此 id）。**新会话只在"从门户发起一次新提问"时产生**，用户全程不按任何"新建"按钮。

> **判据用路由，不用 `current`**：门户 = `#chat`（无 `s`），thread = `#chat/s/{id}`。**不能**用"`current.msgs` 是否为空"判断当前该显示哪个 —— 从 thread 点「问答」回门户时，`current` 里还留着上一个会话（有内容），而门户上不该显示它。所以进入 `#chat` 时 `current` **不清空**，只是不渲染；下一次发送再由 `ensureFreshSession()` 决定复用还是新建。

| 入口 | 是否新开会话 | 说明 |
|---|---|---|
| **门户 composer 回车发送** | **是**（走 `ensureFreshSession()`） | 用户明确"问一件新事"的唯一自由入口 |
| 点「常用问题」句子 | **是**（同一条路径） | 把句子写进 composer 并立即发送，等价于用户手打（设计文 §3.5） |
| 点「最近提问」某一行 | **否** | 打开原会话（§4.4），**不发请求** |
| 点左栏会话项 | **否** | 已有对象的跳转 |
| **thread 态 composer 追问** | **否，永不** | 同一会话内连续追问是"会话"的定义，不是新话题 |
| thread 态发送失败后重试 | **否** | 失败不改变会话归属，否则重试会把上文切断 |
| thread 态点「问答」页签 → 门户 → 发送 | **是** | 这是"我要换话题"的唯一路径，两次点击，可接受 |

### 2.3 `ensureFreshSession()` 的 7 条边界（前端照抄，不许自由发挥）

```
function ensureFreshSession() {
  if (current && current.msgs.length === 0) return current;  // ① 复用空会话
  newSession();                                              // ② 否则新建
  return current;
}
```

1. **当前会话为空（`msgs.length === 0`）→ 复用，不新建**。理由：`showApp()` 在首次登录时已经建了一个空会话（`app.js:69`），若门户第一次发送再建一个，左栏会立刻出现两条「（未命名会话）」，纯噪声。
2. **当前会话有内容 → 新建**。这是自动方案的全部智能，不需要更多。
3. **同一会话内连续追问不新开**。判据是"从对话页输入框发出的"，无论问几句。
4. **`current` 为 null（清缓存/首次登录且已禁用 `showApp` 的自动建会话）→ 新建**。`showApp()` 里那句"空就 `newSession()`"（`app.js:69`）**保留**，但它的产物是空会话，会被 ① 复用，不会堆。
5. **切换库/切页签不触发新建**。门户 → 知识库 → 回门户，`current` 未变，`ensureFreshSession()` 的结果不变。
6. **发送失败不删会话**。会话里留着 1 条 user + 1 条 `request failed` 的 assistant 消息，用户能在对话页看见失败原因并重试。**不要自动回滚**：回滚会让"我刚才问了什么"凭空消失。
7. **绝不产生 0 消息的持久化记录**：`persistSessions()` 前过滤 `msgs.length === 0` 的会话（当前会话除外，它可能正等着第一条消息）。理由见 §2.4 的容量规则。

> **为什么不选"保留一个『新对话』文字按钮"**：那只是把同一个按钮改小、改灰、改名，用户依然要理解"会话"这个概念。而**门户本身就是"新话题选择器"**——把新建动作挪到"选话题"的地方，语义才闭合。
> **为什么不选"每条消息一个会话"**：会话的用处是多轮上下文（后端 `sessions.put_history` 按 `identity:session_id` 维护）；一条一问会让每次追问都丢掉上文，等于砍掉 RAG 的多轮能力。

### 2.4 30 条上限与淘汰规则

| 规则 | 值 | 理由 |
|---|---|---|
| 保留条数 | **30 个会话**（不是 30 条消息） | 与现状常量一致，不改用户已习惯的量级 |
| 淘汰方向 | 淘汰**最旧**（数组尾），保留最新 | 用户回访的是最近的事 |
| 当前会话 | **永不淘汰**，即使它是第 31 个 | 淘汰正在看的会话 = 页面上的对话还在、刷新就没了，最坏的事故 |
| 落盘时机 | 每次 `appendMsg` / `newSession` / 会话置顶后 | 现状已如此，不改 |
| 配额超限 | `setItem` 抛 `QuotaExceededError` 时，从尾部删 1 个会话重试，最多 5 次；仍失败 → toast `本地历史已满，最早 5 个会话已清理` | localStorage 约 5MB，`sources+trace` 会让单条回答到几 KB；必须有一条**不会白屏**的兜底 |

**B1（已修，`app.js:203-216`）**：改动前 `persistSessions()` 写的是 `sessions.slice(-30)`，在"新会话在头部（`unshift`）"的前提下，写掉的是**最新那条**。

```
问题：sessions = [新, ..., 旧31]  → slice(-30) = [第2新, ..., 旧31]   ← 新会话没落盘
修法：sessions.slice(0, 30)                                             ← 保留最新 30
```

**现值（施工后）**：`app.js:203` 的注释就写着这条结论（"`slice(0,30)`，不是 `slice(-30)`：后者会写掉最新那条"），实现改成 `keep` 循环（`app.js:207` 起）：跳过 0 消息会话、`keep.length >= SESSION_MAX` 时跳过非当前会话、当前会话永不淘汰 —— **语义与 `slice(0,30)` 等价且更严**（多了"空会话不落盘"）。配额兜底也在同一函数内（尾部删 1 重试，最多 5 次）。

复现动作（留在验收清单里，防回归）：连发 31 条新提问（每条形如"测试 N"，都在门户发出）→ 刷新页面 → **最新那条应仍在列表首位**，消失的是最旧一条。这条 bug 在自动新建方案下更容易触发（用户不按按钮，但系统自己在建），所以 B1 与自动新建必须同批上线 —— 现在两者同批。

### 2.5 用户会追问的三个"那我怎么……"

| 问题 | 结论 | 理由 |
|---|---|---|
| 怎么开一个全新对话？ | 点顶栏「问答」回门户（或已在门户直接）→ 在 composer 里提问 | 两步，且第二步是"说一件事"，不是"管理会话" |
| 怎么找回上个月的对话？ | 左侧会话栏（桌面常驻，`<720px` 由 ☰ 抽屉呼出）；门户只列最近 4 条 | 已有能力，不改；全量在栏里 |
| 怎么删掉一个会话？ | **不做**（本次范围外，且无此需求证据） | 加"删除会话"= 加确认框 + 加撤销 + 加空态，成本远高于收益；30 条自动淘汰已经兜住了容量问题 |

|---|---|---|---|
| `""`（空） | **`replaceState` → `#chat`**（不留历史） | 已登录 | 回登录页 |
| `#chat` | **门户（idle）**：三段 + composer | 已登录 | 回登录页 |
| `#chat/s/{sessionId}` | **对话（thread）**：`openSession(s)` → 消息流 + composer | 已登录 + `s` 存在于本地 | **静默回落**到 `#chat`（门户），不 toast |
| `#kb` / `#kb/{id}/…` / `#admin/{tab}` | 不变 | 不变 | 不变 |
| 无法解析的串 | 回 `#chat` + toast `页面不存在，已返回问答` | — | — |

**解析要求（`parseHash` 只需加 3 行）**：`mod === "chat"` 时若 `seg[1] === "s"` 且 `seg[2]` 非空 → `{ module:"chat", sessionId: seg[2] }`；否则 `sessionId: null`。session id 形如 `s_1730000000000`（`app.js:200`），只含字母数字下划线，**无需 URL 编码**。

**为什么会话 id 进 URL 路径段而不是 query**：交互规范 §2.2 的分工是"**身份进路径**（`#kb/{id}/files`）、**筛选进 query**（`?q=&page=`）。会话 id 是"我正在看哪个对象"，属身份。写成 `#chat?s=` 会让同一件事出现两种写法，下一个接手的人必然写错一种。

**`s` 找不到时为什么静默**：`s` 是本机会话 id，链接发给同事必然找不到。这不是用户错误，弹"会话不存在"只会制造一次无意义的惊吓。回落 = 门户（也就是"你什么会话都没打开"的真实状态），**不要**回落成"最新会话"—— 那会让用户以为自己点错了地方。

**空 hash 用 `replaceState`**：`location.hash = "#chat"` 会压一条历史，按后退会停在 `#chat` 而不是离开站点，形成"退不出去"的假死。

### 3.2 门户 ↔ 对话（全部入口，穷举）

| 从 | 动作 | 到 | 历史 |
|---|---|---|---|
| 门户 | composer 回车 | 新建/复用会话 → `#chat/s/{id}`（消息立即发出） | push |
| 门户 | 点常用问题句子 | 同上（句子写入 composer 再发） | push |
| 门户 | 点最近提问某行 | `#chat/s/{该会话id}`（**不发请求**） | push |
| 门户 | 点知识库卡 | `#kb/{id}/files`（**不是**对话，§5.4） | push |
| 门户 | 点「全部 N 个 ›」 | `#kb` | push |
| 门户 | 点「控制台 ›」（仅管理员） | `#admin/index` | push |
| 对话 | 点顶栏「问答」 | `#chat`（门户） | push |
| 对话 | 点左栏会话项 | `#chat/s/{另一id}` | **replace**（同页切内容，不该为每次点击都留一条历史） |
| 对话 | 浏览器后退 | 门户（若上次是从门户进来的） | pop |

> 对话之间用 **replace** 的理由：在会话栏里连点 5 个会话，后退键应该回到门户，而不是"退回第 4 个会话"。与交互规范 §2.2"搜索词用 replace"同一条判据：**同一页内的内容切换不该堆历史**。

### 3.3 后退语义（三条必须成立）

1. **对话 → 后退 → 门户，滚动位置还原**（`±2px`）。与交互规范 §2.4 同一机制：内存 `Map<"#chat", scrollTop>`（门户是单容器滚动，key 恒为一个），`renderPortal()` 完成后的 `requestAnimationFrame` 里恢复。**不进 URL**（带 `scroll=` 的链接会把对方带到你的位置）。
2. **门户草稿随后退还原**：门户有 composer，草稿 = 没发出去的那句话。存**内存**（`portalDraft: string`），在门户与对话之间往返、以及会话切换时都保留；**发送成功后清空**；**刷新即丢**（理由见 §3.4）。
3. **门户不因后退而重新请求 `/kbs`**：`myKbs` 已在内存，`renderPortal()` 是纯渲染。刷新才重新拉。

### 3.4 草稿存哪（直接给结论）

| 草稿 | 存哪 | 理由 |
|---|---|---|
| 门户 composer 内容 | **内存**（`portalDraft`） | 与交互规范 §2.2「表单未保存草稿 = 内存」一致。**不进 localStorage**：下次打开看到上次的半句话，用户会以为系统替他记住了不该记的东西；而一句话重打成本约 3 秒 |
| 对话 composer 内容 | **内存**（`draftBySession: Map<sessionId, string>`，切会话保留，发送后清空） | 同一会话切走再回来还在，是"我没发完"的自然预期；跨会话不串（串了会把 A 的问题发到 B） |

## 四、"最近提问"的取数规则

### 4.1 数据从哪来

只有一个源：`localStorage["kb_sessions_v3_{username}"]` 里各会话的 `msgs`，筛 `role === "user"`。**没有任何后端接口提供这个数据**（H1）。

### 4.2 取数算法（伪代码，前端照抄）

```
// ① 补时间戳：appendMsg 时写 ts = Date.now()（新增字段，旧数据没有，向后兼容）
// ② 会话置顶：appendMsg 之后把该会话移到 sessions[0]（见下"为什么"）

function recentQuestions(limit = 5) {
  const items = [];
  sessions.forEach((s, si) => {
    s.msgs.forEach((m, mi) => {
      if (m.role !== "user") return;
      items.push({ s, m, si, mi });
    });
  });

  // 排序键：有 ts 用 ts；无 ts 的旧消息 ts=0，落在所有新消息之后，
  // 彼此之间按「会话位置升序 + 消息位置降序」——与补 ts 之前的观感一致
  items.sort((a, b) =>
    (b.m.ts || 0) - (a.m.ts || 0) || a.si - b.si || b.mi - a.mi);

  const seen = new Set();
  const out = [];
  for (const it of items) {
    const key = it.m.content.replace(/\s+/g, " ").trim();   // 去重键：归一化空白
    if (!key || seen.has(key)) continue;
    seen.add(key);
    out.push(it);
    if (out.length === limit) break;
  }
  return out;
}
```

**取 5 条、渲染 4 行**：`recentQuestions(5)` 取 5 条（供段头「会话 ›」与去重后的完整度），**页面只渲染前 4 行**（设计文 §3.4 的行高预算：4 × 44 + 段头 34 = 210）。第 5 条不丢，它在 rail 里是第 5 项。

**为什么必须"会话置顶"**：`sessions` 的顺序原先只反映**创建时间**（`unshift` 只在新会话时发生）。用户 10:00 建会话 A、10:30 建 B、11:00 又回到 A 追问 —— 数组是 `[B, A]`，按顺序取会把 A 的新提问排在 B 的旧提问后面。**解法**：`appendMsg` 成功后把所在会话 `splice` 出来 `unshift` 回头部（`touchSession()`）。

- 顺带修好了左侧会话栏的顺序：从"最近创建"变成"最近使用"，这才是会话列表该有的序。
- `current` 是同一个对象引用，`splice/unshift` 不影响它，无需重赋值。
- **不用 `sessions.sort()`**：`sort` 不稳定地重排会打断 `renderSessionList` 的插入顺序假设；`splice + unshift` 是 O(n) 但 n≤30。

### 4.3 显示的四个字段

| 字段 | 来源 | 空值兜底 |
|---|---|---|
| 问题文本 | `m.content`，单行截断（CSS `ellipsis`，不截字符串） | `（空问题）` |
| 相对时间 | `tsInfo(m.ts)`（复用 `app.js:839` 的 `tsInfo`） | `较早` （无 ts 的旧数据） |
| 来源库 | 该会话最后一条 assistant 消息的 `sources[0].kb_id` → `kbLabel()` | **该行不渲染这一段**（不是写 `—`）。`—` 表示"字段在、值没读到"；这里表示"值本身就不存在"，两者不能混用（后台 §3.8 与设计文 §3.4 的规则在这里不冲突） |
| 会话标记 | 该会话 `msgs.length` > 2 时显示 `· 3 轮` | 不显示 |

**为什么不显示"会话标题"**：标题就是首条问题的前 22 字（`app.js:346`），和"问题文本"重复。一行里出现两次几乎一样的字，是视觉噪声。

### 4.4 点击行为：**在原会话继续**（不重问）

结论：点一行 → `openSession(s.id)` → `pendingAnchor = {sessionId:s.id, msgIndex}` → `navigate("#chat/s/" + s.id)`（push）→ 滚到该条并高亮 → 聚焦输入框。**不发请求。**

**理由三条**：

1. **重问要花钱且答案会变**。同一个问题再跑一次完整 RAG 链路（路由→改写→检索→打分→生成），几秒延迟 + 一次 LLM 费用，而用户想要的往往只是"我当时看到的那段话"，不是"再答一次"。
2. **重问会丢上文**。新会话没有历史，多轮追问（"那它的配额呢？"）就接不上了 —— 而"最近提问"里的问题，恰恰最可能是要接着问的。
3. **重问是幂等的，用户自己就能做**：进原会话，把问题再发一遍即可（两秒），系统不必替他决定。

**要不要滚到"那一条"**：**要，但锚点只存内存，不进 URL**。

- 点击时把 `{sessionId, msgIndex}` 记进 `pendingAnchor`，导航后由 `renderMessages()` 在末尾把该条 `scrollIntoView({block:"center"})`，并加 1.2s 的 `--blue-bg` 底（`prefers-reduced-motion` 下不加过渡）。
- **为什么不进 URL**：`#chat/s/{id}/m/3` 这类链接只在本机有效，多一段路径只会让"发给同事"的链接更像有效的。刷新后没有锚点 → 滚到底部，这是可接受的自然退化。
- **为什么不像 rail 那样滚到底部**：从 rail 进来是"接着聊"；从"最近提问"进来是"我要看这条当时问了什么"。两个入口的意图不同，落点就该不同 —— 但**都不重问**（§4.4 开头）。

### 4.5 边界

| 条件 | 表现 |
|---|---|
| 0 条历史（新员工） | 段 2 收缩为 32px `hint-bar`：`· 还没有提问记录 · 在下面挑一个问题开始`（§8.2 有完整文案）。**不留空白块** |
| 只有 1 条，且就是 1 秒前发的 | 正常显示 `刚刚`；不隐藏、不去重掉 |
| 关掉浏览器再回来 | 数据仍在（localStorage）；**换设备/换浏览器/清缓存 → 消失**，这是设计事实，不在界面上写"云同步"之类的假承诺 |
| 30 条会话被淘汰 | 被淘汰会话里的提问同步从"最近提问"消失（同一个数据源，天然一致） |
| 消息文本超长 | CSS 单行 `ellipsis`；`title` 放全文（≤120 字） |

## 五、"我有权限的知识库"

### 5.1 数据源与请求次数

`GET /kbs`（H5），**门户只发这一次**。实现要求：

- 复用 `loadMyKbs()` 的 **in-flight Promise**（新增 `myKbsPromise`），与引用卡共用一次请求；引用卡那边继续"失败静默"（`app.js:3452`），**门户这边必须报错**（§8.3）。
- `myKbs` 非空（`showApp` 已预取）→ 直接渲染，**0 请求**。
- 门户渲染完成后再到达的数据 → 调一次 `renderPortalKbs()`（幂等重绘该区块），不做整页重渲染（否则会打断用户已经开始的滚动/点击）。

### 5.2 排序与截断

```
排序：my_role 权重（super 4 > kb_admin 3 > editor 2 > viewer 1）降序
     → updated_at 降序 → id 升序（兜底稳定）
截断：最多 3 张卡；count > 3 时才渲染段头动作「全部 N 个 ›」→ #kb
```

**为什么按角色权重排**（设计文 §3.3 定，我一度改成按 `updated_at`，已回转）：卡片回答的是"**我能在这里做什么**"，能管的库要排在前面；一旦按时间排，一个只读库会因为"昨天有人传了文件"顶到第一张，而用户在这个库里连上传按钮都没有。

**代价与补偿是一组，必须一起读**：按角色排就把"最近动过"这个时间信号弄丢了 → 所以 §5.6 的**「最近更新」strip 必须存在**，它专门承担时间信号。**两者是一组，不许只留一个**：删了 strip，卡片顺序就没有时间依据；把卡片改回按时间排，strip 又变成重复内容。这条在验收里有对应动作（§13：上传一个文件后，卡片顺序**不变**，但 strip 第一位变成该库）。

**「全部 N 个」的渲染阈值 = 卡片阈值**（count > 3）：只有 1–3 个库时，动作指向的页面里只有它自己，等于给了一个空跳转；且"全部 3 个"与"3 张卡"并排会读成"还有更多"。

### 5.3 卡片内容（版式与字段见设计文 §3.3，这里只补三条交互口径）

| 口径 | 结论 | 理由 |
|---|---|---|
| 我的角色 | **不单独占一个元素**，写进整卡 `title`：`你是这个库的只读成员`（文案复用 `ROLE_CN`，`app.js:793`） | 卡片版式已被"分级戳 + 状态徽标"占满两个徽标位（设计文 §3.3 的色彩预算：一卡最多 1 实底 + 1 线框）。**若上线后出现"不知道自己在库里能干什么"的反馈**，把状态徽标换成角色签（同位置、同 20px、改动 1 行），见 §14.3 第 2 行 |
| 变更时间 | 标签写 `变更` 而非 `更新`，`title` = `仅记录库配置变更，上传文件不计` | `kbs.updated_at` 的语义是"元信息/文件增删/审批"，与"有人上传了文件"不是一回事（交互规范 §3.7 已裁定口径）。写"更新"会让用户误判库里多了新资料 |
| 默认库（`id===1`） | 文件数位置显示 `—`（`--muted`），`title` = `默认库不使用文件区，语料随镜像发布` | 默认库的 `kb_files` 恒空（内置语料不入表）。写 `0` 会被读成"这个库是空的" |

- 归档库**不置灰**（设计文 §4.1）：归档是"存在且正常"，由 `.st-arch` 中性徽标表达；置灰会让 4 张卡里 1 张看起来像渲染失败。**卡片仍可点**（旧文件仍要能翻）。

### 5.4 点卡片去哪 —— 以及**不能**做什么

结论：`#kb/{id}/files`（该库文件分区）。

**必须写进代码注释的一条**：**后端没有"按库提问"能力**（H4）。`/chat/stream` 只收 `question + session_id`，检索范围由 `readable_kb_ids(user)` 在服务端算（`main.py:133`）。所以：

- ❌ 不做"问这个库"按钮 —— 点下去的回答会引用**所有**可见库，用户会以为它只查了这一个。
- ❌ 不做"选中某库后提问范围变窄"的界面暗示（例如卡片上的勾选框）。
- ✅ 卡片上不出现任何"提问"字样；`title` 写明 `打开该库的文件列表`。

> 如果将来要这个能力，需要后端给 `/chat/stream` 加 `kb_ids`（`/open/v1/chat` 已有同名字段，可参考），**再**改门户。这是"后端无此能力，前端不实现"的标准处理。

### 5.5 空 / 少 / 多

| 条件 | 表现 |
|---|---|
| 1 个库（只有默认库） | 1 张卡**铺满整行**（`auto-fit` 自动并轨，不是 1/3 宽）+ 页头副行 `你有 1 个知识库的访问权限`；**不渲染「全部 1 个 ›」**（节点不存在，不是 `hidden`） |
| 4 个以上 | 只渲染前 3 张 + 段头「全部 N 个 ›」（N = 接口返回条数，不是 3） |
| 0 个库 | **不可达**（默认库恒对全员开放）—— 若真出现（数据损坏），按 §8.3 错误态处理，不写"你没有任何知识库"这种把系统故障说成事实的文案 |

### 5.6 「最近更新」——一句话 strip，不是第四个 section

**它不是第四个 section，是"长在段 1 内部"的一行**（团队已裁定，设计文 §3.3/§3.4/§十二 三处一致）。存在的唯一理由：**卡片按 `my_role` 权重排（§5.2），时间信号因此丢失，必须由这一行补回来。** 删掉它不会"减少重复"，只会让"哪个库刚被人动过"在整个首屏上无处可读。

为什么不单独成段：段头 + 间距 + 空态会把它撑到 100px 以上，而首屏只剩 32px（段 1 已按 140 计：段头 22+12 + 卡片 74 + 更新条槽 32）。

| 项 | 规格 |
|---|---|
| 位置 | 段 1 卡片行**下方 8px**，作为段 1 的最后一行（无外框、无底色、无段头） |
| 形态 | 单行，`--fs-xs` 12px `--muted`，前缀 `最近更新：` |
| 内容 | 按 `updated_at` 倒序取**前 3 个库**：`{库名} {tsInfo(updated_at)}`，` · ` 分隔；不足 3 个就少显示 |
| 超长 | 整行单行截断（`ellipsis`），`title` 给全部三个库的完整文案 |
| 高 | 24 内容 + 8 上距 = **32**（正好吃掉设计文 §2.2 的全部余量） |
| 数据 | 与段 1 同一个 `GET /kbs` 响应，**0 新增请求** |
| 空/错 | 与段 1 同生共死：段 1 失败 → strip 一起隐藏（不单独报错） |

**预算已裁定（2026-11-02，team-lead）**：段 1 = **140**（22+12 段头 + 74 卡 + 8 上距 + 24 条高）、段 2 = 210、段 3 = 214，合计 **747** = 900 − 65(topbar) − 88(composer)，**余 0**。空态（1 库 0 提问）页总高 **603**。

**唯一降级阀**：实测破版时**只降最近提问 4 → 3 行（省 44px）**。不动内边距、**不砍更新条**（砍了它，卡片顺序就没有时间依据，见本节开头）。

## 六、「常用问题」

### 6.1 裁定：**保持静态**（后端无此能力）

`main.py` 46 条路由中没有"热门问题""搜索日志""问题推荐"任何一条（H6）。**不臆造**：不做"按你的可见库动态生成"，不做"最近被问得最多"。

### 6.2 但必须做两件"静态也不寒酸"的事

1. **单一数据源**：现在 5 条样例写死在 `index.html:100-106`（`data-q` + 显示文案两处），门户要用就必须复制一份 —— 那就是两个版本各自演化。改为 JS 常量：

```js
const SAMPLES = [

  { q: "微信小程序服务器域名怎么配置？",   label: "小程序服务器域名怎么配置？" },

```

门户与对话页空态**共用这一个数组**（对话页 `#samples` 由 JS 填充，HTML 里那 5 个 `<button>` 删除）。

2. **文案覆盖度规则**（可核对，不是"感觉覆盖了"）：5 条必须**分别**命中一个可见库的 `name` 或 `description` 关键词，且不能全部落在同一个库。当前 5 条覆盖「对象存储 / 企业微信 / 腾讯会议 / 小程序 / 云服务器」——正好是 `topbar` 里那 5 个产品线（`index.html:91`），与默认库语料一致。**改动样例时按这条核对**：把 5 个字面主题与 `GET /kbs` 返回的库名做一次对账。

### 6.3 交互

| 控件 | 行为 |
|---|---|
| 句子点击 | **先把原文写进 composer，再走同一条"门户发送"路径**（`ensureFreshSession()` → `#chat/s/{id}` → `send(q)`） | 
| 句子键盘 | `Tab` 可达（原生 `<button>` 但**无边框无底色**，看起来是文字）；`Enter`/`Space` = 点击 |
| 句子长文案 | 允许换行（不用 `ellipsis`）；`max-width: 100%` |
| 为什么先写 composer 再发 | 用户能看到"系统要发的是这句话"，也给了 0.3 秒的反悔窗口（发送是 async，`busy` 前置判断）；与手打完全同一条代码路径，**不写第二个发送函数** |

**为什么从胶囊改成句子列表**（设计文 §3.5 的裁定，我采纳）：5 个 `.sample` 胶囊在 1200 版心里会换成 3+2 两行、行高不一，读起来像"标签云"；而 `.ufilter` 已经占用了胶囊形态表达"可切换的筛选项"。改成 `·` 开头的句子列表后，形态本身就在说"这是一问，点了就执行"。

### 8.2 四态 × 区块（新员工的"1 个库 + 0 条提问"不能像崩了）

| 区块 | 加载 | 空 | 错误 | 无权限 |

**四条判据**（每条都能在截图里数出来）：

1. **不留空块**：任何 >40px 且无内容的容器都不合格。空的那一段要么是 32px `hint-bar`，要么整段不渲染。
2. **1 张卡铺满整行**，不是 1/3 宽留两个洞（`auto-fit` 自动并轨，设计文 §2.3）。

### 8.3 分区错误不整页报错（硬规则）

门户的三个数据源（`/kbs` / localStorage / 常量）**各自独立降级**：

- `GET /kbs` 失败 → **只有库区块**变成一行错误 + 重试。**绝不**整页白屏、绝不 `toast` 报错（toast 2.5s 消失后，页面还是空的）。
- 错误文案（与设计文 §4.4 同一句）：`读取知识库列表超时（5s）`（13px `--red`）+ `重试`（12/600 `--blue`）。**不写三段式归因**：一句话说得清的事，三句话只会稀释「重试」这个动作。
- **401 例外**：`/kbs` 返回 401 说明登录过期，必须 `showAuth()`（与 `api()` 封装一致，`app.js:820`），不能降级 —— 降级会让用户在一个"已登出"的页面上继续点。
- 重试按钮：只重发 `/kbs`，不清空其余区块；重试期间按钮变 `重试中…` 并 `disabled`。

## 九、键盘与焦点

### 9.1 Tab 顺序（一条线性路径，无 `tabindex` 正数）

```
⓪ 左侧会话栏（DOM 在 main 之前 → 实际最先；桌面常驻，移动端抽屉关闭时 `[inert]` 排除）
① 页头「控制台 ›」（仅管理员；普通员工这个节点不存在，不是 hidden）
② 知识库卡 1 → 卡 2 → 卡 3 → 「全部 N 个 ›」（count ≤ 3 时无此项）
③ 最近更新 strip（**不可聚焦**：它是纯文字，没有任何动作）
④ 最近提问第 1 行 → … → 第 4 行 → 「会话 ›」
⑤ 常用问题第 1 条 → … → 第 5 条
⑥ composer 输入框 → 「发送」按钮
```

**为什么「最近更新」不进 Tab 流**：一段不可点的文字被 Tab 到，键盘用户会以为"这里应该有动作"。它不承载交互，就不该占一个焦点位（对比：知识库卡是链接，必须有焦点）。

**卡片的可聚焦性**：卡片是 `<a href="#kb/7/files">`（真链接，支持中键新标签），不是 `div` + `onclick`。理由：门户是"导航页"，导航就该是链接；`div` 会丢掉"新标签打开""复制链接""右键菜单"三件事。

### 9.2 Enter / Esc / 方向键

| 位置 | Enter | Esc | 其他 |
|---|---|---|---|
| 知识库卡（获得焦点） | 打开 `#kb/{id}/files` | 无动作 | — |
| 常用问题句子 | 写入 composer + 发送 | 无动作 | `Space` 同 Enter |
| 最近提问行 | 打开原会话并滚到该条（§4.4） | 无动作 | — |
| 门户 composer | 发送（新建/复用会话后进 thread） | **不清空输入框**（同下） | `Shift+Enter` 换行（现状 `app.js:750`） |
| 对话 composer | 发送（同会话追问） | **不清空**（用户常按 Esc 想收起输入法，清空会误删长问题） | 同上 |
| 移动端抽屉 | — | 关闭抽屉（现状点外部关闭，`app.js:773`） | — |

**门户没有全局快捷键**。理由：门户是"看一眼就走"的页面，加 `/` 聚焦之类会与知识库列表的 `/` 搜索（`index.html:137` 提示）抢语义。

### 9.3 焦点管理（4 个场景写死）

| 场景 | 焦点去哪 | 理由 |
|---|---|---|
| 登录成功进入门户 | 页头 `<h1>`（`tabindex="-1"`） | 读屏需要知道"页面变了"；与交互规范 §9.3 同一规则 |
| 点卡片进 `#kb/{id}/files` | 详情页 `<h1>`（已有逻辑） | 不变 |
| 门户发送 → thread | **composer 输入框**（沿用发送后 `input.focus()`） | 用户下一步是"接着问"；跳到消息区会让键盘用户往回 Tab |
| thread 点「问答」→ 门户 | **composer 输入框** | 用户的下一步必然是"问新问题"；回页头要再 Tab 10 次才到输入框 |
| 从 `#kb` 返回门户 | **刚才点出去的那张卡** | 该卡是链接、恒存在（数据没变时）。若数据已刷新导致卡消失 → 回「我有权限的知识库」段标题（`tabindex="-1"`），不回页头 |

## 十、移动端 390px

### 10.1 会话抽屉：**保留**

- `#rail` 与 `#railToggle`（☰）保留，宽度 `min(300px, 84vw)`（现有 `app.css:553`，390px 下 = 300px）。
- **理由**：门户只展示**最近 4 条**提问，全量历史（30 条会话）的唯一入口就是抽屉。删了抽屉 = 门户变成"只能看 4 条"的孤岛。

**必须同时修一处状态判断（否则门户在 720–1180 直接丢掉会话栏）**：`showView()` 里 `rail-collapsed` 的条件是"非 chat 视图且宽度 <1180"（`app.js:83`）。门户与对话同属 `chat` 模块，**现状天然满足**；但如果前端顺手把条件改成"非 chat 或 非 thread"（很容易写错），720–1180px 区间**没有 ☰ 按钮**（`.rail-toggle` 只在 `<720px` 显示，`app.css:559`），会话栏就彻底打不开了。

```
判据必须按视图白名单：name === "kb" || name === "admin" 时才折叠
不要按"是不是 thread 态"折叠（门户也要保留会话栏）
```

### 10.2 折叠顺序（390px）

**版式与阈值全部以设计文 §七 为准**（卡片 3→2→1 列由 `auto-fit` 自动完成，无新断点）。本文只补"顺序变了以后交互上要注意什么"：

| 档（**一律写容器上界**） | 变化 | 交互要求 |
|---|---|---|
| 容器 ≤ **923** | 卡 3 → 2 列（由 `auto-fit` 自算，不写 `@container`） | 卡仍是 `<a>`，焦点顺序不变 |
| 容器 ≤ **767**（`@container portal (max-width: 767px)`，`app.css:2411`） | 最近提问 4 → 3 行 | 用 `display:none`（`nth-child(n+4)`）把第 4 行**移出可访问树与 Tab 序**即可，这已经是"不存在"的语义。**不能**改用 `visibility:hidden` / `opacity:0` / `left:-9999px` 这类"留着位置"的隐藏 —— 那些读屏仍读得到、Tab 仍进得去 |
| 容器 ≤ **611**（`app.css:2414`） | 卡 2 → 1 列；最近提问 3 → 2 行 | 同上 |
| 容器 ≤ **419**（390 档） | 最近提问整段收进 `<details>`（默认收起，`summary` 36px）；**展开后该行只留「时间」**，来源库与轮次由设计文 §3.4 隐藏（宽度不够，问题段要留 218） | **收起时必须把内部行移出 Tab 流**（`<details>` 天然做到）；展开后顺序恢复。`summary` 的 `aria-expanded` 由浏览器维护，不要手写 |

**为什么阈值必须写成上界**（v1.2）：`max-width: 768px` 会**包含** 768，和"< 768"差一行；同一个断点如果一处写 `min-width: 860px`、一处写 `max-width: 859px`，迟早出现 859/860 之间的窄缝。设计文 §七 已统一为上界（767 / 611 / 419），本文的档位名跟着改，别在代码里换回 `<`。

**390 的实际阅读顺序**：页头 → 知识库卡（1 列）→ 最近更新 strip → 最近提问（折叠）→ 常用问题 → composer。
**为什么 390 不把常用问题提到最前**（我原方案）：`<details>` 折叠后最近提问只占 36px，常用问题已经在首屏内；再调顺序会让桌面与移动的阅读顺序不一致，而"位置稳定"比"省 20px"值钱。

**移动端必须保住的一件事**：composer 固定在底部（既有 `.composer-wrap`），任何折叠都不能把输入框挤出视口 —— 它是这个页面唯一的主操作。

### 10.3 容器查询宿主：`.portal-inner`，不是 `.portal`（v1.2）

```
.portal-inner { container-type: inline-size; container-name: portal; }   /* app.css:2006-2008 */
```

**挂错一层不会报错，只会静默偏一档**：`container-type` 挂在 `.portal` 上时，量到的是 1192（含外层内边距）而不是版心 1136 —— 差 56px，`767` 这条阈值实际在**视口 823** 才触发，所有档位整体偏移，而页面上没有任何报错。表现是"某个宽度下布局忽然变了，但按 CSS 算不该变"。

交互侧只记一条：**本文 §10.2 的 767 / 611 / 419 是"版心宽度"，不是"视口宽度"**。用 DevTools 验时要把容器宽度调到 767（选中 `.portal-inner` 看 computed width），别调视口 —— 这是唯一能一眼看出"宿主挂错"的办法。
