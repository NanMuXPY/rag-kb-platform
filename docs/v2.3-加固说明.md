# v2.3 加固说明：格式、规模、静默失败

> 起因：汇报前梳理"这个作品还有哪些短板"，列了三条——① 只认纯文本 ② 38 份文件规模小
> ③ 单机部署。本轮解决了 ①②（③ 属部署架构，暂不动），所谓"解决"的标准是：
> **不再有静默失败，超限时能自己说出来。**

---

## 一、改了什么

### 1. 一条抽取通路（`backend/app/extract.py`，新增）

改造前是两套逻辑：建库用 `DirectoryLoader(glob="**/*.md")`，上传用 `pypdf`/`python-docx`。
结果是把 Word/PDF 放进 `data/` 目录，重建"成功"但一个文件都没进去。

现在统一为 `extract_path() / extract_bytes()`：

| 格式 | 处理 |
|---|---|
| `.md` / `.txt` | 按 utf-8 → gb18030 → utf-16 顺序试解码，取乱码最少的那个（存量 GBK 文档很常见） |
| `.docx` | 段落 + 表格（表格按行拼成 `a \| b \| c`，原来只读段落，参数表全丢） |
| `.pdf` | 逐页 `pypdf` 抽文字层；单页损坏只记 errors，不整本放弃 |
| 扫描件 | 识别"无文字层的页"，`needs_ocr=True`；配 `OCR_MODEL` 后渲染 160dpi 交视觉模型转写 |

扫描范围由 `SUPPORTED_EXTS` 单点定义，建库、上传、审批三处共用，不会再出现"两条路两套规则"。

### 2. 空结果必须汇报

- 建库：抽不出文字的文件写进 `skipped`（含文件名、原因、是否需 OCR），随 `/admin/index-status` 返回
- 上传：`save_file` 先验抽取，抽不出就是 400，直接把原因给用户（"疑似扫描件，未启用 OCR"）
- 审批：`add_file_to_index` 抽不出文字时抛 `ValueError`，不再"批准成功但 0 chunk"

### 3. BM25 关键词索引：从"每次全量重建"到"后台增量跟进"

| 改造前 | 改造后 |
|---|---|
| chunk 数一变就在请求线程里全量重建 | `revision` 版本号 + 后台线程重建，读取方拿旧索引继续服务 |
| 重启后第一次提问要重算全部 token | 分词结果按 chunk id 落盘（`.bm25.pkl`），重启直接复用 |
| 全库一个索引，查询扫全部 | 按 `kb_id` 分区建索引，只算用户有权限的库，权限隔离顺带多一层保障 |
| 超过阈值就慢到不可用 | `BM25_MAX_CHUNKS=20000`，超了自动降级纯向量并在状态里写明原因和建议 |

### 4. 入库并发化 + 进度可见

- embedding 由"10 条串行"改为"多批并发（默认 4 并发）+ 指数退避重试 4 次"
- 重建过程上报 `phase`（extract → split → embed → swap → done）、已处理块数、百分比、耗时
- `/admin/rebuild` 立刻返回，`/admin/index-status` 随时可查进度

## 二、验收证据（本地实测）

**格式抽取**（`temp/fixtures` 五类样本）：

| 样本 | 结果 |
|---|---|
| 两页文字 PDF | 109 字，pages=2，needs_ocr=False |
| 扫描版 PDF（图片页） | 未开 OCR：0 字 + note「1/1 页无文字层（疑似扫描件）」；开 `OCR_MODEL=qwen3-vl-plus` 后：56 字，engine=vision-ocr |
| 带表格 docx | 61 字，表格行 `参数 \| 含义` 正常带出 |
| GBK 编码 txt | 26 字，中文无乱码 |
| 空文件 / 损坏 PDF / xlsx | 分别给出「未抽出任何文字」「原文可能已损坏或被加密」「不支持的格式 .xlsx」 |

**混合格式目录扫描**：`产品A/说明书.pdf`、`产品B/参数表.docx`、`产品B/笔记.txt` 三份入库，
`扫描件.pdf`、`空.md` 进入 skipped 报告并标注 `needs_ocr`。

**关键词通道**：查询「生命周期 冷热分层 存储桶」命中排障文档；kb_id=7 的内容在 `["default"]`
权限下检索不到（隔离生效）；`revision` 变更后后台重建自动追平。

**效果回归**：`eval/run_eval.py --limit 3 --persist db_e2_800`，recall@4 100%、MRR 1.000、
幻觉 0，与改造前一致；线上重建 185 chunks 通过，问答正常。

## 三、仍然存在的边界（要如实说）

1. **Excel / PPT 不支持**。表格与版式需要单独的切块策略（按行切、按卡片切），不是加个解析器就完事。
2. **OCR 按页计费**。默认上限 30 页/文件，超出的页会被跳过并在 note 里写明；大批扫描件入库前应先估算成本。
3. **BM25 是内存索引**。2 万 chunk 以内单机够用，再往上要换 ES/OpenSearch——降级阈值和迁移建议已写在状态接口里。
4. **单机部署没动**。有持久化挂载，但没有自动备份、没有副本、没有健康检查切换。这是下一轮的事（③）。

## 四、配置项速查

```bash
# 支持格式（代码内单点定义，不需要配）
# backend/app/extract.py -> SUPPORTED_EXTS = {".md", ".txt", ".pdf", ".docx"}

OCR_MODEL=qwen3-vl-plus     # 留空 = 只识别不转写
OCR_MAX_PAGES=30
OCR_API_KEY=                # 留空则复用 EMBEDDING_API_KEY
OCR_API_BASE=               # 留空则复用 EMBEDDING_API_BASE

EMBEDDING_CONCURRENCY=4     # 入库并发批数
BM25_CACHE=True             # 分词缓存落盘
BM25_MAX_CHUNKS=20000       # 超过即降级纯向量
```
