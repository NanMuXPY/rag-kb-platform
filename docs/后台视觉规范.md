## 一、为什么要单独立一套后台规范

现状 `#viewKb` 的结构是「横向 chips 选库 → 下方三段堆叠」。7 个库时还能用，到 30 个就散架：

| 维度 | 现在（chips） | 实测后果 |
|---|---|---|
| 库数量承载 | 一行 4–6 个，换行即失控 | 7 个库已换行；30 个库会吃掉首屏 1/3 |
| 可扫读字段 | 只有 `name` + `my_role` | 领导要看「哪些库是机密的、谁负责、多久没更新」——**一个都看不到** |
| 排序 / 筛选 / 搜索 | 无 | 找库靠肉眼扫，这是「不像后台」的核心原因 |
| 选中态与详情 | 选中后同一屏向下展开三段 | 文件多时页面长度无上限，返回顶部要滚 2000px |
| 版心 | 880px（阅读版心） | 9 列表格在 880px 内必然挤压折行 |

**结论**：不是配色不正规，是**缺少「列表页」这一层基础设施**。正规感 ≈ 可扫读的表格 + 稳定的页头 + 明确的层级，不来自更深的颜色或更粗的线。

## 二、版面骨架

### 2.1 三层骨架（一级 / 二级 / 三级）

```
┌───────────────────────────────────────────────────────────────┐
│ rail 248px  │ topbar 56px：品牌 · [问答｜知识库｜控制台] · 身份  │ ← 一级导航（不动）
│             ├───────────────────────────────────────────────────┤
│  会话列表    │ view-pad（整页滚动；横内边距 28 / 20 / 14）        │
│             │   ┌── 版心 --content-work: 1200px ───────────┐    │
│             │   │ 页头  20/16：面包屑 12 · 衬线标题 20 · 按钮 │    │
│             │   │ 工具条 60：搜索 280 · 筛选胶囊 · 密度 · ⋯  │    │
│             │   │ 表格：表头 40（sticky）/ 行 48 或 40        │    │
│             │   │ 页脚 48：共 128 个 · 分页                   │    │
│             │   └────────────────────────────────────────────┘    │
└───────────────────────────────────────────────────────────────┘
```

- 一级导航（问答 / 知识库 / 控制台）**位置不动**，仍在 topbar 中部。它表示「换模块」，是这个系统的身份锚点，动了就要重学。
- 版心从 880px 提到 **1200px**：`--content-work`。880px 是「一行 34 个汉字」的阅读宽度，不是表格宽度。**阅读版心与工作台版心必须分开**，这是后台观感的第一道分水岭。
- 1440 视口实际可用：1440 − 248 − 56 = **1136px**；1920 视口封顶 1200px（不让表格拉成一条）。

### 2.2 是否需要二级导航？——需要，但只在详情页

很多后台把二级导航做成「模块内的页面切换」（全部库 / 待审批 / 归档），结果和一级导航的胶囊长得一样，用户分不清自己在第几层。这里分开定义：

| 层级 | 表示什么 | 形态 | 位置 | 出现时机 |
|---|---|---|---|---|
| 一级导航 `view-nav` | 换**模块**（问答/知识库/控制台） | 胶囊（现有 `.vnav`） | topbar 中部 | 始终 |
| 列表页筛选 `ufilter` | 换**数据范围**（全部/我管理的/已归档） | 小巧胶囊（现有 `.ufilter`，12px） | 工具条左侧 | 列表页 |
| 二级导航 `subnav` | 换**同一对象内的分区**（文件/成员/分组/设置） | **下划线 tab**（新增） | 详情页页头下方 | 仅详情页 |

**形态不同 = 语义不同**，这是防止层级混乱最省事的办法。二级导航用下划线而非胶囊，理由：胶囊已被一级导航占用（白色浮起块 = 可切换模式），下划线贴着一条基线 = 「我在同一份档案里翻页」。

```css
/* 二级导航：44px 高，激活项 2px 下划线，不使用 box-shadow（边界靠线） */
.subnav {
  display: flex; gap: var(--sp-8);
  height: var(--nav2-h);                 /* 44px */
  border-bottom: 1px solid var(--line);
  overflow-x: auto;                      /* ≤720 时横向滑动，隐藏滚动条 */
}
.subnav-item {
  position: relative;
  display: inline-flex; align-items: center; gap: var(--sp-icon);
  padding: 0 2px;
  border: 0; background: none; cursor: pointer;
  font: inherit; font-size: var(--fs-base); font-weight: 500;
  color: var(--muted); white-space: nowrap;
  transition: color var(--dur-fast) var(--ease);
}
.subnav-item:hover { color: var(--ink); }
.subnav-item.active { color: var(--ink); font-weight: 600; }
.subnav-item.active::after {
  content: ""; position: absolute; left: 0; right: 0; bottom: -1px;
  height: 2px; background: var(--ink);
}
.subnav-count { font-size: var(--fs-xs); color: var(--muted); font-variant-numeric: tabular-nums; }
```

激活下划线用 `--ink` 而不是 `--blue`：`--blue` 一色一义里是「可点击的主操作」，用它标"当前位置"会让整页看起来到处是按钮。**当前位置是结构信息，用墨色表达。**

### 2.3 列表页 → 详情页：选「独立子视图」

三种方案的实际代价：

| 方案 | 30 个库时 | 返回行为 | 判断 |
|---|---|---|---|
| 同页向下展开 | 页面长度无上限，文件列表挤在 2500px 处 | 无 | ✗ 这是现在的问题本身 |
| 右侧抽屉（640px） | 抽屉里再放 4 个子分区 → 抽屉内滚动 + 页面滚动双层 | Esc 关闭，不记得列表滚动位置 | ✗ 信息量超载 |
| **独立子视图** | 列表页永远只有一张表 | `#kb/42` 可回退，列表筛选/滚动位置可保留 | ✓ |

落地方式（无构建、无路由库）：

- URL 用 hash：`#kb` 列表、`#kb/42` 详情、`#kb/42/members` 分区。`hashchange` 里做一次渲染分发，约 30 行。
- 详情页返回列表用面包屑「知识库 /」，**不放大号返回箭头**（箭头在后台里是移动端的语汇）。
- 列表状态（搜索词、筛选、页码、滚动位置）存内存，返回时还原。这是「正规感」里最容易被忽略的一条：**别让用户回到列表第一页**。

抽屉仍然保留，但只服务**第三级**：看一行数据的纵深（单个文件的路径/分块数/审批流水、单个成员的授权来源）。宽 420px，从右侧推入。

```css
.drawer-r {
  position: fixed; inset: 0 0 0 auto;
  width: min(var(--drw-w), 100vw);            /* 420px */
  background: var(--surface);
  border-left: 1px solid var(--line);
  box-shadow: var(--shadow-pop);
  z-index: var(--z-drawer);
  transform: translateX(100%);
  transition: transform var(--dur-base) var(--ease);
  display: flex; flex-direction: column;
}
.drawer-r.open { transform: none; }
```

### 2.4 页头规范（列表页与详情页两版）

**列表页页头**（无面包屑，因为已在第一层）：

| 元素 | 字号/字重 | 位置 | 数值 |
|---|---|---|---|
| 页面标题 | `--fs-xl` 20px / 700 / `--serif` | 左，基线对齐 | `letter-spacing: .02em`，`line-height: 1.35` |
| 副标题（对象总数） | `--fs-xs` 12px / 400 / `--muted` | 标题右侧 | 间距 `--sp-3` 12px，与标题**基线对齐** |
| 主操作 | 36px 高按钮 | 右，`margin-left:auto` | 距副标题至少 `--sp-6` 24px |
| 页头下边距 | — | — | 上 `--head-pad-y` 20px，下 `--sp-4` 16px；**不加分隔线**（下面紧接工具条，加线会形成双线） |

**详情页页头**（有面包屑）：

```

财务制度库   KB-FIN-001  [内部]  ● 启用
12 个成员 · 128 个文件 · 最后更新 3 天前
──────────────────────────────────────────────────────────────
文件 128    成员与授权    分组授权    设置
```

| 元素 | 规格 |
|---|---|
| 面包屑 | `--fs-xs` 12px / `--muted`，分隔符 `/` 用 `--line-strong` 且左右各 8px；最后一项 `--ink` 500 且不可点 |
| 面包屑下间距 | `--sp-2` 8px |
| 标题行 | 标题 20px 衬线 700；其后紧跟编码（`--mono` 12px `--muted`，间距 12px）、分级签、状态徽标（间距 8px）；**不换行**，超长时标题 `max-width: 46ch` 后截断 |
| 副信息行 | `--fs-xs` 12px `--muted`，项间用 ` · `，距标题行 `--sp-1` 4px |
| 右侧操作 | 主操作 1 个（蓝底 36px）+ 次操作最多 2 个（ghost 36px）+ 溢出进 `⋯`（32×32）；与标题行**底部对齐**，不居中 |
| 元信息条（可选） | 56px 高，`1px --line` 上下边框，4 个键值对横排：键 12px `--muted`，值 13px `--ink` 500，组间距 `--sp-8` 32px |
| 二级导航 | 紧跟元信息条，见 2.2 |

**硬规则（防堆砌）**：页头右侧最多 **3 个可见控件**（含 `⋯`）。主操作永远只有 1 个，且必须是这个页面上"用户 80% 时间来干的那件事"（列表页 = 新建知识库；详情页 = 上传文件）。「删除」不进页头，进 `设置` 分区底部。

## 三、表格规范（核心）

「正规感」的 70% 来自表格。下面每一条都是可以照着写的数值。

### 3.1 结构：真 `<table>` + `<colgroup>` + 不横向滚动

- 用语义 `<table>`（不是 div 网格）：屏幕阅读器可读出「第 3 行第 2 列」，且 `<colgroup>` 定宽 + `table-layout: fixed` 能让所有行严格对齐。
- **不提供横向滚动**。列放不下时按优先级收起（3.3），或降级成卡片（3.8）。「能横向滚动的表格」在领导眼里等于"没做完"。
- **例外：分组授权矩阵，规格见 §10.1**。它的列数 = 分组数，是运行时数据，收起列等于隐藏授权关系（功能性损失，不是密度取舍）。除该矩阵外任何表格不得横滚。

```css
.kbtable-wrap { container-type: inline-size; container-name: kbtable; }

.kbtable {
  width: 100%; table-layout: fixed;
  border-collapse: separate; border-spacing: 0;   /* 为了圆角裁切 */
  background: var(--surface);
  border: 1px solid var(--line);                  /* 只此一道外框 */
  border-radius: var(--r-md);
  overflow: hidden;
  font-size: var(--fs-sm);                        /* 13px，统一 */
}
```

### 3.2 列定义（知识库列表，完整 10 列 = 复选框 + 9 个业务列）

宽度**已含左右各 12px 内边距**，可直接写进 `<colgroup>`。

| # | 列 | 宽 | 对齐 | 内容层级 | 收起优先级 |
|---|---|---|---|---|---|
| 1 | 复选框 | 44 | 左 | — | **保留（必须常驻，见下方警告）** |
| 2 | 知识库 | auto（min 200） | 左 | 主：库名 13/600；次：描述 12/400 `--muted` | 保留 |
| 3 | 编码 | 136 | 左 `--mono` | 单行，`KB-FIN-001` | **第 1 个收起** |
| 4 | 归属部门 | 104 | 左 | 单行，超长截断 | 第 4 个 |
| 5 | 数据分级 | 88 | 左 | 线框签（4.2） | 保留 |
| 6 | 授权范围 | 96 | 左 | 字符前缀 + 文字（4.4） | 第 3 个 |
| 7 | 状态 | 84 | 左 | 实底徽标（4.3） | 保留 |
| 8 | 文件数 | 68 | **右** `--mono` | 纯数字 | 第 2 个 |
| 9 | 负责人 | 96 | 左 | 单行姓名 | 第 5 个 |
| 10 | 变更时间 | 124 | **右** `--mono` | 相对时间；**不可排序**（见 §3.5） | 保留 |

固定列合计 = 44+136+104+88+96+84+68+96+124 = **840**；+ 库名列最小 200 = **1040**，在 1136px 里仍有 96px 余量，全部给库名列（auto）。

> **`<colgroup>` 的写法（v1.11 补，直接影响"余量归谁"）：定宽列写 `width`，主字段列（知识库 / 文件名 / 成员 / 分组）的 `<col>` **不写 `width`**。**
> `table-layout: fixed` 下，剩余宽度只分配给"没有声明宽度"的列；如果每列都写了数，浏览器会**按比例缩放全部列** —— 结果是主字段列吃不到那 96px 余量、每列都缩一点，看起来就是"整表比设计的窄一号"。三张表同此规则。

> 编码列 136px 可容纳 13 个等宽字符，建议后端把编码规范控制在 **≤12 字符**（`KB-<部门>-<3位序号>`）。超长时截断 + `title`，不允许折行。

**警告：复选框列必须常驻，禁止运行时移除（v1.11，线上已发生过一次）**

用 `display: none` 隐藏、或直接把 `td` 从 DOM 里拿掉，而 `<colgroup>` 里**仍留着那一列的 `<col>`** —— 两份列数一旦不等，浏览器会把 N 个 `<col>` 逐个套到 N−1 个单元格上，**从被删那列起后面所有列整体左移一格**。线上表现（`no-check` 模式）：「知识库」名称列被压成 0 宽、表格右侧凭空多出约 100px 留白。**已热修：复选框列常驻，`.no-check` 规则删除。**

- 这一列的收益是 **44px**，风险是整表错位。**不划算，不要再优化它。**

**这个 bug 的症状不是"列没对齐"，是"点错了"**（UX 译成交互后果，采纳）

| 用户做的事 | 实际命中的是 |
|---|---|
| 点「负责人」列表头 | 相邻列的表头 |
| 点某行的「成员」按钮 | 左边一格的内容 |
| 滚到最右找 `⋯` | 约 100px 空白 |

所以报障会写成"按钮失灵""点错了"，而不是"版式错位"。**验收动作必须是"点一次最右列的按钮，确认打开的是那一行那一列的东西" —— 光看截图对不齐是抓不到的。**
- 如果哪天真要"没有批量需求就不要这一列"，必须**三处同时**处理：`<colgroup>` 去掉对应 `<col>` + 表头 `<th>` 去掉 + **每一个** `<td>` 去掉，少一处就是上面这个 bug。
- 同理适用于**所有**收列动作 —— 见 §3.3「收列的三处同步」，那是本条的一般形式。

### 3.3 密度与列收起（容器查询，不新增视口断点）

「表格几列」取决于**实际可用宽度**，而可用宽度受「rail 是否折叠」影响，视口断点算不准。所以用**容器查询**（`@container`），并在 ≤720 视口仍需折叠 rail 时由现有 `@media` 负责页面骨架——两套系统各管一层，互不干扰。这同时满足上位文档第九节「禁止新增断点」。

| 容器宽度 | 列数 | 显示列 | 典型场景 |
|---|---|---|---|
| ≥ 1060px | 9 | 全列 | 1440 视口（rail 展开） |
| 860–1059 | 7 | 收掉 编码、文件数 | 1280 视口、1024 视口 |
| 660–859 | 5 | 再收 授权范围、负责人 | 861–960 视口、720–760 视口 |
| < 660 | — | **降级卡片**（3.8） | 手机、窄窗 |

```css
@container kbtable (max-width: 1059px) {
  .c-code, .c-files { display: none; }
}
@container kbtable (max-width: 859px) {
  .c-scope, .c-owner { display: none; }
}
@container kbtable (max-width: 659px) {
  .kbtable, .kbtable-foot { display: none; }   /* 由 .kb-cards 接管 */
  .kb-cards { display: grid; }
}
```

**收列的三处同步（硬要求，v1.11 补）**

`display: none` 只作用在**单元格层**，`<colgroup>` 里对应的 `<col>` 仍占着那一列的位置。少同步一处，列映射就从缺口处整体左移（线上已发生过一次，见 §3.2 警告）。

| 要做 | 落在哪 | 谁做 |
|---|---|---|
| ① 该列**所有** `th` / `td` 隐藏 | `@container` 里挂列 class 的 `display: none` | CSS |
| ② `<colgroup>` 里**删掉**对应的 `<col>` | 按当前档位重建 `colgroup.innerHTML` | JS（约 10 行） |
| ③ 重建后核对合计宽 ≤ 该档容器宽 | 对照 §3.2 / §11.9 的最小需求 | 自查 |

> **分工一句话：CSS 负责"看不见"，JS 负责"不占位"。两者不能互相替代。**

阈值必须同源：`1059 / 859 / 659`（CSS 的 `max-width`）与 `1060 / 860 / 660`（档位边界）只允许存在一份定义，JS 常量旁写一行注释指向本节。改一处必须改两处，否则会出现"列隐藏了、col 还在"（左移）或反向错位。

**配套 JS（约 6 行，`app.js` 视图切换处）**：进入 `kb` / `admin` 视图时，若 `innerWidth < 1180` 给 `.shell` 加 `.rail-collapsed`，让会话栏自动折叠成抽屉（用户仍可点 ☰ 展开）。理由：后台页不需要会话列表，而 248px 的 rail 在 1024 屏上会吃掉表格的四分之一。这不是断点，是一个状态 class：

```css
.shell.rail-collapsed { grid-template-columns: 1fr; }
.shell.rail-collapsed .rail { position: fixed; z-index: 30; inset: 0 auto 0 0; width: min(300px, 84vw); transform: translateX(-100%); transition: transform var(--dur-base) var(--ease); }
.shell.rail-collapsed .rail.open { transform: none; }
```

> **注意：JS 是必需的，不是"旧内核的退化方案"**（v1.11 更正）。`<colgroup>` 的列数用 CSS 改不了，所以无论 `@container` 支不支持，都要有一个 `ResizeObserver` 监听 `.kbtable-wrap`、按三档重建 `<col>`（见上「三处同步」②）。
> `@container` 可用 → 隐藏交给 CSS，JS 只管 colgroup；不可用 → JS 顺手加 `.w9 / .w7 / .w5` 把隐藏也接管（两条路径阈值同源）。
> **不要**改回视口 `@media` —— 那会在 `≤860` rail 折叠后出现「列又长回来」的跳动，比留白更破坏正规感。

### 3.4 行高与两种密度

| 密度 | 行高 | 单元格内容 | 应用 |
|---|---|---|---|
| **舒适**（默认） | `--row-h` **48px** | 主字段 + 次字段双行（18 + 2 + 16 = 36px）+ 上下 6px | 日常管理 |
| **紧凑** | `--row-h-compact` **40px** | **仅主字段单行**，次字段隐藏 | 一次要看 50+ 行 |

> 48px 装两行是紧的，所以紧凑档必须砍掉次行（40px 装不下 36px 内容 + 呼吸）。密度切换不只是"高矮"，是"信息量"——这样用户才有理由去点它。
> 密度选择存 `localStorage`，默认舒适；切换时**不加过渡动画**（行高动画会让整表抖动 200ms，非常廉价）。

```css
.kbtable td {
  height: var(--row-h);
  padding: 6px var(--td-px);
  border-bottom: 1px solid var(--line);
  vertical-align: middle;
  overflow: hidden; text-overflow: ellipsis; white-space: nowrap;
}
.kbtable tbody tr:last-child td { border-bottom: 0; }

.kbtable.is-compact td { height: var(--row-h-compact); padding: 0 var(--td-px); }
.kbtable.is-compact .cell-sub { display: none; }
```

### 3.5 表头

```css
.kbtable th {
  height: var(--th-h);                 /* 40px */
  padding: 0 var(--td-px);
  background: var(--paper-2);          /* 必须实色，sticky 时内容不穿透 */
  border-bottom: 1px solid var(--line-strong);  /* 全表唯一一条"重线" */
  font-size: var(--fs-xs);             /* 12px，比表体小一号 */
  font-weight: 600;
  letter-spacing: .04em;               /* 中文小字加字距才不糊 */
  color: var(--ink-soft);
  text-align: left;
  white-space: nowrap;
  position: sticky; top: 0; z-index: var(--z-sticky);
}
```

- 表头是**结构性元素**，不加 checkbox 以外的装饰，不加图标，不加背景渐变。
- 可排序列仅 2 个：**编码 / 文件数**。排序指示用字符（`▲`/`▼`，12px）：未激活 `--line-strong`，激活 `--blue`。其余列不可排序（可排序列 >4 个时用户会到处乱点，反而不专业）。
  - **「变更时间」列不可排序**（原定可排，已撤销）：`kbs.updated_at` 目前只在 `PATCH` 时 bump，上传文件不更新，用它排序会把错误信息放在最显眼的位置。列名同时由「更新时间」改为「**变更时间**」，`title` 写明口径：「仅记录库配置变更，上传文件不计」。
- sticky 表头**不加投影**（`--shadow-sticky` 仅在页面滚动且需要视觉"离开感"时用，此处靠 `--line-strong` 已足够）。

### 3.6 行状态

| 状态 | 表现 | 说明 |
|---|---|---|
| 默认 | 底 `--surface`，行间 `1px --line` | **不用斑马纹** |
| hover | 底 `--row-hover`（= `--paper` `#F6F4EE`） | 暖一档纸色，不用灰。灰会让整行"变脏" |
| 选中（批量） | 底 `--row-sel`（= `--blue-bg`）+ 首列 `inset 3px 0 0 var(--blue)` | 选中必须同时有底色与左侧竖条，只给底色在 5 列时会被误读为 hover |
| 键盘聚焦 | `outline: 2px solid var(--blue); outline-offset: -2px` | 整行 `tabindex="0"`，`Enter` 进详情 |
| 不可访问 | **本产品不实现**（`GET /kbs` 只返回有 role 的库，无权限库不进列表） | 见 §10.2 第 3 条，不要写这条 CSS |
| 归档 | 行内**不加**任何底色 | 归档是"存在且正常"，只由状态徽标表达。给整行加灰底是最常见的过度设计 |

```css
.kbtable tbody tr:hover td      { background: var(--row-hover); }
.kbtable tbody tr.is-sel td     { background: var(--row-sel); }
.kbtable tbody tr.is-sel td:first-child { box-shadow: inset 3px 0 0 var(--blue); }
.kbtable tbody tr:focus-visible { outline: 2px solid var(--blue); outline-offset: -2px; }
```

**为什么不用斑马纹**：暖纸底 `#F6F4EE` 与白 `#FFFFFF` 的明度差只有 4%，斑马纹在纸感主题里根本看不见，只会让行线显得脏；而密集表格里 8 个徽标色块 + 斑马纹会互相干扰。行线 + hover 已经足够定位。

### 3.7 单元格内的信息层级

一行里只允许三种东西：**主字段 / 次字段 / 标识**。

| 层 | 字号 | 字重 | 颜色 | 位置 |
|---|---|---|---|---|
| 主字段 | 13px `--fs-sm` | 600 | `--ink` | 单元格第一行，单行截断 |
| 次字段 | 12px `--fs-xs` | 400 | `--muted` | 主字段下方 2px，单行截断 |
| 标识（徽标/签） | 12px `--fs-xs` | 500–600 | 见第四节 | 独立列，**不塞进主字段所在列** |

```css
.cell-main { display: block; font-size: var(--fs-sm); font-weight: 600; color: var(--ink); overflow: hidden; text-overflow: ellipsis; }
.cell-sub  { display: block; margin-top: 2px; font-size: var(--fs-xs); color: var(--muted); overflow: hidden; text-overflow: ellipsis; }
```

三条细则：

1. **主字段最多挂一个 12px 以内的标识**（如库名后的「默认」二字，`--fs-2xs` `--muted`）。挂两个就会和状态列打架。
2. 一行最多 **2 个实底徽标 + 1 个线框签**（见 4.5 色彩预算）。
3. 行操作按钮**默认显示**（不做 hover 才出现的渐变隐藏）：这是给非技术人员用的后台，悬停才出现等于没有。

### 3.8 数字、时间、空值

| 内容 | 对齐 | 字体 | 规则 |
|---|---|---|---|
| 计数（文件数/成员数/分块数） | **右** | `--mono` + `tabular-nums` | 0 显示为 `—`（`--muted`），不显示 `0`。满屏的 0 会让表格看起来"全是空的" |
| 时间（业务列） | **右** | `--mono` 12px `--muted` | ≤7 天：「3 天前」「2 小时前」；>7 天：`2026-10-21`；`title` 恒为 `2026-11-02 14:32:07` |
| 时间（审计表） | 右 | `--mono` 12px | 一律绝对时间 `YYYY-MM-DD HH:mm`，宽 130px |
| 金额/大小 | 右 | `--mono` | 固定 1 位小数 + 单位后缀（`2.4 MB`），单位与数字之间 `4px` |
| 空值 | 跟随列对齐 | — | 统一 `—`（em dash，`--muted`）。**绝不空白**：空白格看起来像渲染 bug |
| 长 ID / 编码 | 左 | `--mono` | 截断 + `title`，不换行 |

```css
.num  { text-align: right; font-family: var(--mono); font-variant-numeric: tabular-nums; }
.dash { color: var(--muted); }
.time { text-align: right; font-family: var(--mono); font-size: var(--fs-xs); color: var(--muted); }
```

**`—` 的例外登记表（**记号级**例外，全局 2 处，判据都是"不是数据缺失"）**

| # | 位置 | 现象 | 为什么不算"缺失" | 现行做法（消费处只引编号） |
|---|---|---|---|---|
| **A** | 分组授权表「人数」= 0 | 0 人 | 空组是**可清理的动作对象**（收回整组授权），必须让人看见 | 显示 `0`（`--muted`），见 §11.5 |
| **B** | 文件表「操作」列 · 非库管的 `pending` / `rejected` 行 | 没有可执行操作 | `—` 的含义是"这里有数据、但没读到"；"你没有这个能力"不是缺失 | **留空单元格**，不写任何字符，见 §11.8 |

> **规则：任何地方想用 `—` 以外的表示，先登记到上表、再在消费处引编号。**
> 不允许"就地写一句这是例外" —— 例外清单只能有一份。本轮就撞上过：§11.5 和 §11.8 各写了一句"这是唯一例外"，两条互不知情，读者无法判断到底几处。

**这张表只登记「记号级」例外，不登记「能力级」例外（v1.12 边界，与 UX 对齐）**

| 类型 | 是什么 | 登记在哪 | 例 |
|---|---|---|---|
| **记号级** | **同一个值的不同写法**（不写 `—`、写 `0`、留空），消费处遍地都是，读者需要一处可查 | **本节这张表**（编号 A / B） | 人数 0 显示 `0`；操作格留空不写 `—` |
| **能力级** | **一种平时被禁止的能力，被允许用一次**，本身带一套规格 | **授予它的那一节**，那里写"唯一"，别处只写"见 §X" | 横滚 → §10.1（不在本表，**别来 §3.8 找**） |

> **不设"全局例外总表"。** 记号级例外集中，是因为它们只是替换一个值 —— 集中成本为零，收益是"读者只需查一处"。能力级例外一旦进总表，就变成"任何东西都能被登记进来"的通道，而 §3.12 的护栏要求**每条例外都能算出代价**（几行？占了什么？换回了什么？）。**登记表会把这个代价问题悄悄跳过** —— 表格里的格子是免费的，代价不是。

### 3.9 长文本截断与悬浮展示

- 所有单元格默认 `overflow: hidden; text-overflow: ellipsis; white-space: nowrap`。
- 截断后必须给 `title` 属性（浏览器原生 tooltip，延迟约 1s）。**不自造 tooltip**：无构建、无框架，自造 tooltip 的定位/边界/触屏逻辑成本远高于收益。
- 描述类长文本在列里**最多两行**（舒适密度），超出进详情页，不在列表里展开。
- 文件路径类（可能 100+ 字符）不进行列表，只在抽屉/Dialog 里 `word-break: break-all` 展示。

### 3.10 行操作列

- 位置：**最右**，`text-align: right`，与主字段形成"左读右操作"的固定视线动线。
- 最多 **3 个文字按钮**（`--fs-xs` 12px，无边框，`--blue`；危险操作 `--red`）。第 4 个起进 `⋯`。
- 按钮间距 `--sp-3` 12px；点击区用 `::after` 扩到 28px 高（视觉小、热区大）。
- 整行可点进详情，行内按钮必须 `e.stopPropagation()`。

**操作列宽度必须算，不能拍**（v1.4 补，来自一次真实的溢出）：

```
内容宽 = 列宽 − 24（左右各 12 padding）
所需宽 = Σ(按钮字数 × 12) + (按钮数 − 1) × 12
```

| 按钮组合 | 所需内容宽 | 最小列宽 | 结论 |
|---|---|---|---|
| 2 个 3 字（`改角色` `移除`） | 36+12+24 = 72 | 96 | ✓ 用 112（含余量） |
| 1 个 3 字 + 1 个 2 字（`改角色` `收回`） | 36+12+24 = 72 | 96 | ✓ 用 112 |
| **3 个 2 字（`下载` `审批` `删除`）** | 24×3+12×2 = **96** | **120** | ⚠ 112 会顶出 8px → 用 **124** |
| 1 个 6 字（`解除整组授权`） | 72+36+12 = 120 | 144 | ✗ 不要用长词，见下 |

- **超过 3 字的中文动词一律改短词**：`解除整组授权` → **`收回`**（2 字，72→24px）；`下载查看` → **`下载`**（"不能在线预览"用 `title` 说）。完整语义放确认弹窗标题 `解除「财务组」的整组授权？`——一句话里两个词都出现，用户不会不懂。为迁就一个长词把列宽从 112 改到 160，会连锁改三档收列断点，代价远大于收益。
- **危险操作位置恒定（贴最右）**：行操作里若含危险动作（删除/收回/停用），它永远是本列最后一个。这样前序按钮数量随行内状态变化时（1 个 / 2 个 / 3 个），**危险目标的 x 坐标不变** —— 用户第二次点删除不会因为这一行少了个「审批」而点到别的东西。这条比"按钮总数固定"重要：**数量可以变，危险动作的位置不能变。**
- **默认不要用常驻禁用来"保持对齐"**：为了列宽稳定而摆一个在该行永远不可能变为可用的按钮，本质是"不可达态"换了件衣服（见 §10.5 推论 ② 与 §3.12 判据）。**"位置恒定"不靠占位保，靠右对齐保** —— 等宽按钮 + 恒 12px 间距 + 右对齐，则从右边缘起算每个存在的按钮 x 都是常量，缺少的那一格只是空白。
  - **本案（v1.9 终局）**：文件表「审批」按 §3.12 属 **unreachable → 直接不画**，不走任何"例外"通道。v1.6 的"常驻占位 + 灰块占比 + `visibility: hidden`"整套作废（`visibility: hidden` 也是占位，同样不用）。
- 列宽改动必须回头检查所属表格的总宽与收列断点（§11.9），不要只改一列。

### 3.11 ≤720 视口：卡片模式

表格在 <660px 容器下换成卡片清单。**不是"把表格横过来"**，是重新排信息：

```
┌────────────────────────────────────────┐
│ ☐ 财务制度库                 ● 启用     │  14/600 + 状态徽标
│ KB-FIN-001 · 财务部                     │  11px mono + 12px muted
│ [内部]  ▤ 3 组   128 个文件  3 天前      │  签 + 范围 + 计数 + 时间
└────────────────────────────────────────┘
```

| 项 | 数值 |
|---|---|
| 卡片间距 | `--sp-2` 8px |
| 卡片内边距 | `--sp-3` 12px |
| 卡片描边 | `1px --line`，圆角 `--r-md`，底 `--surface`，零阴影 |
| 卡片高 | 约 76px（三行：19 + 2 + 15 + 4 + 16） |
| 第一行 | 库名 14/600 + 右侧状态徽标；复选框在库名左侧，间距 8px |
| 编码/部门行 | 11px `--mono` `--muted`，用 ` · ` 连接 |
| 第三行 | 分级签 + 授权范围 + 计数 + 相对时间，`gap: --sp-3`，可换行 |
| 点击 | 整卡进详情 |

卡片模式下**页面级工具条保留**（搜索 + 筛选），批量条同样替换工具条位置。

### 3.12 禁用还是不可用：locked / forbidden / unreachable（v1.9）

同样是"禁用"，成员表的「移除」要画、文件表的「审批」不画。差别不在风格，在**这个控件能不能解套、以及它的规则在别处有没有落点**。

| 类型 | 定义 | 做法 | 例子 |
|---|---|---|---|
| **locked** | 同一行的其它操作能让它重新可用 | **画**，`title` 说明钥匙在哪（写"怎么做"，不写"不能做"） | `kb_admin` 行的「移除」→ 先把角色改成「只读」，它就会亮 |
| **forbidden** | 谁都解不开，但这条策略**在界面别处没有落点** | **画**，`title` 写规则原句 | 创建者行的「改角色」「移除」→ 来源列只写了「创建者」这个身份，读不到"创建者不可移除"这条规则 |
| **unreachable** | 状态不会逆转，该能力永远不再存在 | **不画**（状态列已经说过了这件事） | 已入库文件的「审批」→ 状态列写着「已入库」 |

> 一句话：**暂时用不了的按钮要画（给钥匙）；规则没处说的按钮要画（给原句）；状态已经说过的按钮不要画。**

**`title` 只有两种合法写法，其余都是噪音**（与 UX 附录 D2.3 同一份措辞，改一处必须改两处）

| 类型 | 写什么 | ✅ 合格 | ❌ 不合格 |
|---|---|---|---|
| locked | **怎么做**（钥匙在哪） | `库管理员不可直接移除，请先把角色改为「只读」` | `该成员不可移除` |
| forbidden | **规则原句**（别处读不到的那句） | `创建者不可移除`（说清了"为什么"是创建者身份） | `操作不被允许` ／ `该成员不可移除`（只把用户看到的结论念一遍） |

> **把用户已经看到的结论念一遍，等于没说。** 用户看见按钮灰了，不需要 `title` 再告诉他"这个不能点"；他要的是"那我该怎么办"，或者"这是谁定的"。

**区分 forbidden 与 unreachable 只问一句**：

> **删掉这个按钮之后，用户还能从别处读到这条规则吗？**
> 读得到 → unreachable，不画；读不到 → forbidden，画。

- 创建者行：来源列的「创建者」只说明他是谁，"不可移除"这条规则**没有第二个落点** → 画。
- 文件表「审批」：状态列「已入库」本身就是"不能再批一次"，**这件事不需要被额外知道** → 不画。

**判据的演进值得记一笔**：UX 最初只分 locked / unreachable，我拿创建者行去套它——套不上（创建者既不能降级也不能移除，没有钥匙），当时的处理是"用代价可量化来辩护这个例外"。UX 没有接受那个辩护，而是补出第三类 **forbidden**：**问题的根在判据少了一档，不在案例。**
> **当一个判据要靠"例外"才能用，通常说明判据少了一档 —— 先怀疑判据，再怀疑案例。**

**两个方向的护栏，缺一不可**：

| 护栏 | 防的是 |
|---|---|
| 类型决定**画不画**（本节） | 有人为了对齐/稳定，随手加一个死控件 |
| **例外必须能算出代价**（几行？占了什么？换回了什么？） | 有人拿"这是例外"当挡箭牌，什么都能加 |

**本案已裁定（v1.9）**：文件表「审批」属 **unreachable** → **不渲染**。v1.6 的"常驻占位 + 灰块占比判据 + `visibility: hidden` 退路"全部作废：`visibility: hidden` 是"看不见但占位"，本质仍是常驻方案，**同样不用**。

## 四、数据分级与状态的色彩语义

### 4.1 核心方法：一个维度只用一种「形态」

现有的 4 个语义色（蓝/绿/红/琥珀）已经占满"状态"这条赛道。要在不破坏「一色一义」的前提下再塞进 3 个新维度（分级/状态/范围），办法不是找 3 个新色相，而是**让不同维度用不同的视觉形态**：

| 维度 | 形态 | 色彩用量 | 认知负担 |
|---|---|---|---|
| 数据分级 | **白底 + 1px 描边框**（密级戳） | **0 个填充色**，只用墨色深浅 + 1 处朱砂描边 | 低（线框很轻） |
| 库状态 | **实底 + 5px 圆点 + 文字** | 2 个既有语义色（松绿/琥珀）+ 1 个中性灰 | 中 |
| 授权范围 | **字符前缀 + 纯文字** | 0 个背景色 | 最低 |
| 角色权限 | **纯文字 + 字重差**（不用颜色） | 0 | 最低 |

结果：一行 9 列里，**彩色填充块最多 2 个**。这就是"正规"与"花哨"的分界——企业后台的花哨感几乎全部来自同一种形状（彩色胶囊）被复制了 4 遍。

### 4.2 数据分级：线框戳 `.cls`（公开 / 内部 / 机密）

公文里的密级标识本来就是**方框文字**，不是色块。这里照抄这个语汇。

| 分级 | 描边 | 文字 | 底色 | 语义依据 |
|---|---|---|---|---|
| 公开 | `--line-strong` | `--muted` | `--surface` | 与"待处理/成功"无关，用最弱的中性 |
| 内部 | `--ink-soft` | `--ink-soft` | `--surface` | 深一档墨 = "请留意"，不引入色相 |
| 机密 | `--red` | `--red` | `--surface` | 朱砂在档案语汇里就是「密件 / 不可外流」，与现有「危险·拒答」共享同一底层语义：**需要谨慎对待** |

```css
.cls {
  display: inline-flex; align-items: center;
  height: var(--badge-h);              /* 20px */
  padding: 0 7px;
  border: 1px solid var(--line-strong);
  border-radius: var(--r-sm);
  background: var(--surface);
  font-size: var(--fs-xs); font-weight: 600; line-height: 1;
  color: var(--muted); white-space: nowrap;
}
.cls-internal { border-color: var(--ink-soft); color: var(--ink-soft); }
.cls-secret   { border-color: var(--red);       color: var(--red); }
```

对比度实测（12px 600，AA 需 ≥4.5:1）：`公开` 4.6:1 ✓ ｜ `内部` 7.4:1 ✓ ｜ `机密` 5.6:1 ✓。
**朱砂签必须白底**——`--red` on `--red-bg` 只有 4.3:1，上位文档已明确"朱砂不能做浅底小字"，所以机密签不做朱砂浅底填充。

### 4.3 状态徽标：实底 + 圆点 `.st`

**库状态（库级，`kbs.status`）**

| 状态 | 类名 | 底 | 字 | 复用语义 |
|---|---|---|---|---|
| 启用 | `.st-on` | `--teal-bg` | `--teal` | 沿用「成功 / 已激活」✓ |
| 索引中 | `.st-index` | `--amber-bg` | `--amber` | 沿用「待处理」✓（**当前只在控制台用**，见下方说明） |
| 归档 | `.st-arch` | `--paper-2` | `--ink-soft` | 新增中性档：**归档不是错误，不用朱砂** |

**文件状态（文件级，`kb_files.status`）** —— v1.3 新增，与库状态是**两个维度**，不可混用类名

| 状态 | 类名 | 底 | 字 | 说明 |
|---|---|---|---|---|
| 待审批 | `.st-pending` | `--amber-bg` | `--amber` | **不复用 `.st-index`**：`.st-index` 的语义已被移交"库索引中"，让"待审批"挂上去会让维护者以为文件在跑索引（Q2 裁定 = 方案 a） |
| 已入库 | `.st-on` | `--teal-bg` | `--teal` | 与库"启用"同色同义（已通过） |
| 已驳回 | `.st-reject` | `--paper-2` | `--ink-soft` | **中性，不用朱砂**：驳回是终态不是故障；驳回原因进抽屉，不在列表里堆红字。注意用 `--ink-soft` 而非 `--muted`（后者在 `--paper-2` 上仅 3.9:1，不合格） |

```css
.st {
  display: inline-flex; align-items: center; gap: 5px;
  height: var(--badge-h); padding: 0 8px;
  border-radius: var(--r-sm);
  background: var(--paper-2); color: var(--ink-soft);
  font-size: var(--fs-xs); font-weight: 500; line-height: 1;
  white-space: nowrap;
}
.st::before { content: ""; width: 5px; height: 5px; border-radius: var(--r-full); background: currentColor; flex: none; }
.st-on      { background: var(--teal-bg);  color: var(--teal); }
.st-index   { background: var(--amber-bg); color: var(--amber); }
.st-pending { background: var(--amber-bg); color: var(--amber); }   /* 文件级，语义独立 */
.st-arch,
.st-reject  { background: var(--paper-2);  color: var(--ink-soft); }
```

圆点 + 文字是双通道：色弱用户靠文字，快速扫读靠颜色。`归档` 用 `--ink-soft` on `--paper-2` = 6.2:1（用 `--muted` 只有 3.9:1，不合格，**不要省这一步**）。

> **`.st-index` 用在哪**（v1.1 修订）：`kbs.status` 只有 `active|archived`（`backend/app/workspace.py:27`），知识库列表渲染不出"索引中"。该样式移交 **控制台 → 语料索引** 的全局索引状态（`/admin/index-status` 返回 `building` 时用 `.st-index`）。索引**失败**不新增徽标，复用现有 `.index-state.err` 红字块。
>
> **状态：预留启用位，不是漏实现。** 等后端把单库状态扩出 `indexing`（`kbs.status` 或独立字段）之后，在知识库列表启用 `.st-index`；在那之前它只服务控制台。前端如果看到这个 class 未在 `#kbList` 使用，**不要删除、不要补一个假状态**。

### 4.4 授权范围：字符前缀 + 文字 `.scope`

| 值 | 前缀字符 | 文字色 | 依据 |
|---|---|---|---|
| 全员 | `◎` | `--ink-soft` | 范围最广，比默认深一档 |
| 分组 | `▤` | `--amber` | 上位文档已定义「琥珀 = 分组签」✓ |
| 指定成员 | `◦` | `--muted` | 最窄，最弱 |

```css
.scope { font-size: var(--fs-sm); color: var(--muted); white-space: nowrap; }
.scope::before { content: "◦ "; }
.scope-all { color: var(--ink-soft); } .scope-all::before { content: "◎ "; }
.scope-grp { color: var(--amber); }    .scope-grp::before { content: "▤ "; }
```

文字形态即可：授权范围是**属性**不是**状态**，用徽标会变成第 3 个色块。`▤` 与现有 `.ugroup` 分组签同义，用户能迁移认知。

### 4.5 三条防冲突规则

1. **形态即维度**：分级=线框，状态=实底+圆点，范围=文字，角色=字重。任何新维度先选形态，再考虑颜色。
2. **每行色彩预算：≤2 个实底 + ≤1 个线框 + ≤1 处朱砂描边**。超了就把其中一个降级为文字。
3. **一个色相只服务一个语义域**：`--red` 全域含义 = 「不可外流 / 出错 / 品牌印」。机密、危险操作、拒答、印章都是"要停一下"的东西，是同一个域；`--amber` 全域 = 「等一等」（待处理、待审批、分组签）；`--teal` = 「已通过」；`--blue` = 「可点」。

### 4.6 对比度验收表

| 组合 | 比值 | 结论 |
|---|---|---|
| `--ink-soft` on `--paper-2`（归档徽标） | 6.2:1 | ✓ |
| `--teal` on `--teal-bg` | 5.3:1 | ✓ |
| `--amber` on `--amber-bg` | 5.3:1 | ✓ |
| `--red` on `--surface`（机密签） | 5.6:1 | ✓ |
| `--muted` on `--surface`（公开签） | 4.6:1 | ✓（12px 600 达标边界，不可再降） |
| `--muted` on `--surface`（次字段 400 12px） | 4.6:1 | ✓ 但**不得再用于 11px** |
| `--muted` on `--paper`（表体在 hover 行） | 4.4:1 | ⚠ hover 行内的次字段会掉到 AA 边缘 → hover 底改用 `--row-hover` 时，次字段字色提到 `--ink-soft`（见下） |

```css
/* hover / 选中行：底色变暖后，次字段深一档以维持对比度 */
.kbtable tbody tr:hover .cell-sub,
.kbtable tbody tr.is-sel .cell-sub { color: var(--ink-soft); }
```

## 五、列表域的状态设计

### 5.1 加载态：骨架，不是转圈

- 首次加载：6 行骨架，行高跟随当前密度；每列一个灰条（高 10px，`--r-sm` 圆角，宽 40%–70%，三条固定宽度序列循环，避免随机造成"抖动感"）。
- 刷新（筛选/翻页）：**保留旧数据**，在工具条上方出现 2px 高的不确定进度条（`--blue`，从 0%→100% 循环 1.2s），表格高度不变化。
- 骨架只在 150ms 后才出现（`setTimeout` 保证），避免闪光。
- 不用 spinner：上位文档已定「加载 = 骨架块闪烁」。

```css
.sk { background: var(--skel-bg); border-radius: var(--r-sm); height: 10px; }
@keyframes sk-pulse { from { opacity: .55 } to { opacity: 1 } }
.sk { animation: sk-pulse 900ms var(--ease-inout) infinite alternate; }
.progress-line { height: 2px; background: var(--blue-bg); overflow: hidden; }
.progress-line::after { content: ""; display: block; height: 100%; width: 40%; background: var(--blue); animation: pl 1.2s var(--ease-inout) infinite; }
@keyframes pl { from { transform: translateX(-100%) } to { transform: translateX(250%) } }
```

### 5.2 空态：必须分三种，不能一句话走天下

| 类型 | 触发 | 主文案（衬线 `--fs-xl`） | 副文案（13px `--muted`） | 动作 |
|---|---|---|---|---|
| 真空态 | **仅 `rows === 0`**（默认库被删 / 接口异常） | 「还没有知识库」 | 「先建一个，把制度文档传进来」 | 主按钮「新建知识库」 |
| 无结果 | `rows > 0` 但搜索/筛选后 0 条 | 「没有符合条件的知识库」 | 「试试缩短关键词，或清除筛选」 | 文字按钮「清除筛选」 |
| 无权限 | **本产品不实现**（见 §10.2 第 3 条） | — | — | — |

- **空态只属于 `rows === 0`。** 本产品 `GET /kbs` 恒含默认库（`kb_id == 1` 兜底给 viewer），所以常态不是"空"，而是"只有 1 行"。**只有 1 行数据时绝不能渲染空态大块**——一张表下面垫一块 200px 高的"还没有知识库"是最刺眼的层级错误。这种情况用下一条 `hint-bar`。
- `hint-bar`（轻提示条，用于「只有默认库」这类可达常态）：
  - 高 **32px**，无外框，无底色，位于工具条与表格之间，上间距 0、下间距 `--sp-2` 8px。
  - 文字 `--fs-xs` 12px `--muted`；行首字符 `·`（`--line-strong`）+ 4px。
  - 动作是**文字动作**，不是按钮：`--fs-xs` 12px / **600** / `--blue`，跟在句末，间距 `--sp-2`；多个动作之间 `--sp-2` 8px。
  - **条高恒 32px，不因内容变成按钮而长高**。32px 里塞 28px 按钮会撑破上下文；要实底按钮说明这个动作不该放提示条里，应该上移到工具条或页头。
  - 文案（由 UX 定，我只约束形态）：「只有一个默认库 · 默认库是内置语料，不能上传。 <u>新建一个知识库</u> 来放你们部门的文档」。
  - 与空态的区别：**hint-bar 是"提示"，不占版面重量**；空态是"没有数据"，占满容器。
- 版式：垂直居中，上下留白 `64px`；字符图形 `▤`（36px，`--line-strong`，非 emoji）+ 16px 间距 + 主文案 + 8px + 副文案 + 20px + 动作。
- **禁止**用插图/SVG 插画：无构建、且插画会把档案风拉成 SaaS 风。
- 空态出现在**表格容器内部**（保留外框），不替换整个页面。保留外框 = 「这块区域是表格，只是暂时没内容」，页面结构不塌。

### 5.3 错误态

- 位置：表格容器内，左对齐，`--red` 文字 13px + 「重试」文字按钮。
- 文案格式：**原因 + 怎么解决**。「加载失败」不算文案。例：「读取知识库列表超时（5s），请检查网络后重试」。
- 工具条保持可用（筛选不锁死），页头主操作保持可用。

### 5.4 批量操作条

```
┌──────────────────────────────────────────────────────────────┐
│ 已选 3 项   取消选择          [ 移动到分组 ][ 导出 ][ 归档 ] 删除 │
└──────────────────────────────────────────────────────────────┘
```

| 项 | 规格 |
|---|---|
| 位置 | **与工具条同一位置替换**（不是浮在底部） |
| 高度 | `--bar-h` 60px（与工具条等高 → 表格不位移，这是关键） |
| 底/框 | `--blue-bg` + `1px --blue` |
| 左区 | 「已选 3 项」13px 600 `--ink`；「取消选择」文字按钮 12px `--muted`，间距 `--sp-4` |
| 右区 | 常规操作 2–3 个（ghost 32px 高）；危险操作（删除）最右，`--red` 文字按钮 |
| 禁用 | `opacity: .45` 且 `title` 写明原因（如「含无权操作的知识库」），不隐藏（批量条按钮是**带框**按钮，故用 opacity；行内**文字**按钮禁用用 `--muted` 换色，见 §11.8） |
| 全选 | 表头复选框支持半选（`indeterminate`）；全选范围 = 当前筛选结果，文案写「已选全部 128 项」而非「已选本页」 |

**为什么不用底部浮起条**：会遮住最后一行与分页；移动端还与会话输入区抢位置。顶部替换工具条，用等高容器承载，视觉完全不动 —— 用户不会"感觉页面跳了一下"。

### 5.5 撤销条（10s 可撤销，同位置复用）

与批量条**共用同一个容器与同一套等高规则**（`--bar-h` 60px，替换工具条，表格位移 0px），但**不用 `--blue-bg`**。

原因（UX 提得对，我采纳并升级）：`--row-sel` 的值就是 `--blue-bg`，页面里已经表示"行被选中"。撤销条表达的是"刚刚改过一条授权"，同底会在「既选中多行、又刚改过授权」时撞语义。

| 项 | 规格 |
|---|---|
| 底/框 | `--amber-bg` + `1px --amber-line`（**不是** `--paper-2`，理由见下） |
| 文字 | 13px `--ink`：`已更新「财务组」的授权` |
| 动作 | 文字按钮「撤销」，12px 600 `--amber`，边框 `--amber-line`，高 28px |
| 倒计时 | 12px `--mono` `--amber`，**`10s` 递减到 `1s`**（与我 §8 强度表、UX A4 恢复路径的 10s 一致）；靠右、位于「撤销」左侧 `--sp-3` |
| 末段强调 | 剩余 **≤3s** 时倒计时字重 500 → **600**，**不改颜色**（红色属于危险域，撤销窗口到期不是"出问题"） |
| 消失 | 到时直接消失（`opacity` 200ms），不做进度条 |

**适用范围（v1.5 收紧，只给可反悔的操作）**

撤销条只用于**能被一次反向请求还原**的变更。判据是一个必须能回答的问题：**撤销时调哪个接口？** 指不出来的一律不给撤销条，改成"不可撤销"的二次确认。

| 操作 | 撤销路径 | 有无撤销条 |
|---|---|---|
| 改成员角色 / 加成员 / 整组授权变更 | 反向 `PATCH`，参数明确 | ✓ 有 |
| 归档 / 取消归档 | 反向 `PATCH status` | ✓ 有 |
| **审批通过 / 驳回文件** | **无**（`approve_file` 前置 `status='pending'`，驳回后无法再批准） | ✗ 无，走确认弹窗 + 终态提示 |
| **删除文件 / 删除库** | **无**（只移磁盘 `.trash/`，无恢复接口） | ✗ 无，走 §10.3 危险确认 |

> **规则：凡在规范或交互稿里标"可撤销"，必须写出撤销所调的接口和参数。写不出来的一律改成不可撤销。** 一个点下去必然 400 的"撤销"按钮，比不给撤销更伤信任 —— 用户会以为系统坏了。（这条由 UX 自查发现，我方原稿从未把审批/驳回列为可撤销，但此前没写"为什么不能"，现已补成判据。）

**为什么不用 `--paper-2`（UX 的原方案）**：`--paper-2` 与页面底 `--paper` 明度差仅 2%，60px 高的一条几乎看不见 —— 一个"看不见的撤销入口"等于没有撤销，用户只会记得"我误操作后没法挽回"。`--amber` 在上位文档里的语义域是「待你处理 / 待确认」，而 10 秒撤销窗口正是"在等你决定"，语义严丝合缝，且不必新增任何颜色。对比度：`--amber` on `--amber-bg` = 5.3:1 ✓。

若同屏已有 amber 元素造成混淆（矩阵页的 `▤ 分组签`），退化方案：`--surface` 底 + `1px --line-strong` + 左侧 `3px --amber` 竖条 —— **保留 amber 的 3px 竖条**，那才是让人看见它的东西。

> **窗口时长锁死 10s（Q1 裁定）**：单一常量 `UNDO_MS = 10000`，倒计时从 **10 显示到 1**，不显示 `0`。理由：我 v1.1 里标题写 10s、表里写 8s 是笔误，以 **10s** 为准 —— 与 §8 强度表、UX 的 A4 恢复路径三处一致即可，**不要为了"看起来更紧张"改成 8s**（缩短窗口只会降低撤销成功率，视觉上没有任何收益）。

## 七、三个最容易做丑的地方

### 陷阱 1：表格描边过重 —— 「每格都画线，看着像 Excel 表格贴上来」

**症状**：`border: 1px` 画满所有边 + 表头深灰底 + 外框 2px + 圆角 0。远看是网格，近看每个字都被框住，整页像报表截图。

**规避**：一张表只允许**一条强调线**。

| 线 | 规格 | 数量 |
|---|---|---|
| 表头底线 | `1px --line-strong`（全表唯一的深线） | 1 |
| 行间线 | `1px --line` | n−1 |
| 表格外框 | `1px --line` + `--r-md` 圆角（靠 `overflow: hidden` 裁齐） | 1 |
| 竖向分割线 | **0 条** | 0 |
| 单元格独立边框 | **0 条** | 0 |

对比度上的直觉校验：`--line` `#E4E0D5` 对 `--surface` 的对比约 1.15:1 —— 是"能感觉到但不刺眼"的强度。换成 `--line-strong` 到处画，立刻变成密网格。**再想加线时，先想想是不是该加留白。**

### 陷阱 2：徽标颜色爆炸 —— 「一行 8 个彩色胶囊」

**症状**：分级（3 色）+ 状态（2 色）+ 授权（3 色）+ 角色（3 色）全做成彩色胶囊。30 行 × 4 个 = 120 个色块，页面像仪表盘灯板，任何单个状态都失去强调力。这也是"不够标准化"最真实的来源——不是不够正规，是**视觉噪音太高，读不出重点**。

**规避**：
1. 执行 4.1 的「形态即维度」：分级线框、状态实底、范围文字、角色字重。**一行彩色填充块 ≤2 个**。
2. 每加一个新维度，先问："能不能用文字/字重/字符前缀解决？"三个新维度里有两个答案是"能"。
3. 新增颜色前必须先在 4.5 第 3 条里找到"语义域"，找不到就不加色。
4. 校验法：把界面截图**缩小到 50% 并去色**。如果去色后还能分出层级（哪些是名字、哪些是状态、哪些是辅助），说明层级做对了；如果去色后一片平，说明你靠颜色硬撑结构。

### 陷阱 3：页头操作堆砌 —— 「标题被 7 个按钮挤到左边」

**症状**：新建 / 导入 / 导出 / 批量 / 刷新 / 设置 / 帮助 全放在页头右侧，标题只能换行或缩到 8 个字。用户第一眼看到一排按钮，找不到"这个页面是干什么的"。

**规避**：
1. 页头硬上限 **3 个可见控件**（含 `⋯`），主操作恒为 1 个。
2. 出现顺序：`主操作` → 次操作（≤2，ghost） → `⋯`。低频操作（导出、刷新、帮助）默认进 `⋯`。
3. 屏幕占比校验：页头右侧控件总宽 **≤ 内容宽度的 1/3**（1136px 版心下 ≤ 380px）。超了就把次操作移进工具条右侧。
4. 位置校验：`批量操作` 属于**工具条**（数据操作），不属于**页头**（页面操作）。这两类混在一起是最常见的层级错误。
5. 标题与按钮**不同字号、不同基线条**：标题 20px 衬线，按钮 36px 高 14px 字。若两者看起来一样重，说明按钮太多了。

- [ ] 文字按钮禁用态是 **`--muted` 换色**、无 `opacity`、hover 无变化、可聚焦且焦点环可见（`aria-disabled` + tabindex）

**协作约定（v1.8，一次真实踩坑的产物）**

> **任何结论变更（尤其是"裁定撤回"），必须同时通知视觉 / UX / 前端三方。**
> 本轮出现过一次：裁定撤回只传到了一方，另一份文档仍按旧结论实现，两边各自以为自己还欠一次确认，前端拿到两个相反的口径。**结论的传播面和它的修改面一样大 —— 改在一处，就要通知所有引用处。**
> 落地：我们的两份规范互相引用时，只引用**章节号**、不复制结论正文；被引用的章节一旦变更，引用方只需复核章节号是否仍成立，不必比对文案。

**文档机制三条（v1.12，与 UX 对齐；这不是审美问题，是"结论会不会活错版本"的问题）**

1. **结论必须留在章节里，不要散落在注记 / 脚注 / 附录。** 被引用的只有章节号；写在注里的结论没法被正确引用，于是两边各自演化出两个版本 —— 上一轮"审批是否常驻"那次分歧，一半原因就是两边都复制了结论正文。
2. **理由可以留在原地，规格必须回到它的归属章节。** 一段"为什么这么定"的论证里如果顺手写了一条要照着做的规格，读者会把它当论证的一部分读过去。
   > UX 给的理由比我的更硬：**藏起来的规格是免于被核对的规格** —— 理由块不会被拿去和模块树对账，更不会和代码对账。他文档里"矩阵是第 4 个 tab"那条错就这样活过了一个版本（实为第 3 个，且不是新增 tab 而是已有 tab 换内容）。
3. **例外按级登记**：记号级进 §3.8 表（A / B）；能力级只在授予处写"唯一"，其余处写"见 §X"。**不设全局例外总表**（理由见 §3.8）。
4. **一个"允许"的撤回成本，等于引用它的处数。** 本轮实例：文件表「上传时间」那一格的优先级写着"第 1（**与复选框成组退让**）"—— 复选框改成常驻后，"成组退让"这个许可就过期了，可它已经扩散出去，光我这边加 UX 那边共 4 处要逐个回收。
   - 推论一：**许可不要起短名。** "成组退让"这种四字短语比整句更好复制，复制到别处之后就没人回去核它是否还成立。**能被复制的短语，就是会被复制的错。**
   - 推论二：撤回时按"谁引用过它"逐个回收，别以为改了正文就完事。引用处不会自己发现源头变了 —— 这正是第 3 条要求"只引章节号"的第二个理由：**章节号可以被复查，短语不行。**

**跨文档引用消歧**：本文没有附录，所以本文里所有 `§x.y` 都是本文自己的。引用 UX 文档时一律带 `UX` 前缀 + 它自己的编号（`UX 附录 D2.3`、`UX 附录 C`）；裸 `§3.x` / `§10.x` / `§11.x` 一律指本文 —— UX 侧已按同一约定写成"凡出现 `§3.x`/`§10.x`/`§11.x` 即指视觉规范"，因为他的 §三 只到 3.7。

## 十、与交互规范的交叉裁定（v1.1）

`docs/后台交互规范.md` §11 报了 6 处与本规范的差异。逐条裁定如下——**doc 之间不并存矛盾，以本节为准**。

### 10.1 分组授权矩阵：唯一允许横向滚动的表格

**批准例外**，但必须做成"看得出是故意的"：

- 条件：列数 = 分组数（运行时数据），收起即隐藏授权关系，属功能性损失。
- 与列表页的形态区分：矩阵**用紧凑行高 40px**（它是做决策的密度视图，不是浏览视图），列表页默认 48px。
- 除本节之外，任何表格不得 `overflow-x`。
- **两个冻结必须配套高度约束，否则表头不吸顶**：`overflow-x: auto` 单独写会让 `overflow-y` 自动变成 `auto`，`wrap` 成为滚动容器；但若它没有可滚区间（无 `max-height`），表头 `sticky top: 0` 就永远黏不住，只会跟着页面滚走。所以矩阵必须给 `max-height: calc(100vh - 220px)`（220 ≈ topbar 56 + 页头 100 + 二级导航 44 + 余量），此时**表头黏 wrap 顶部、首列黏 wrap 左侧**，两个冻结才同时成立。
- 验证项：矩阵竖向滚动时表头不动、横向滚动时首列不动、两者交叉时左上角格始终可见。

```css
/* 全产品唯一允许横滚的表格 */
.matrix-wrap {
  overflow: auto;                     /* 两轴都要 auto，见下方说明 */
  max-height: calc(100vh - 220px);    /* 关键：没有高度约束，表头 sticky 永远不会吸顶 */
  border: 1px solid var(--line);
  border-radius: var(--r-md);
  background: var(--surface);
  padding-bottom: 4px;                /* 给 8px 横滚条留位，不压住最后一行 */
}
.matrix {
  width: auto;                    /* 不要 100%：必须能超出容器，才会产生横滚 */
  min-width: 100%;                /* 分组少时铺满，不留断口 */
  border-collapse: separate;      /* sticky 单元格必须用 separate，否则边框会丢 */
  border-spacing: 0;
  font-size: var(--fs-sm);
  /* 列宽由 <colgroup> 给：240 + 96×N。
     不要写 table-layout: fixed —— 它会让 width:auto 失效，横滚就不出现了 */
}
.matrix th, .matrix td { padding: 0 var(--td-px); height: var(--row-h-compact); }

/* 表头冻结 */
.matrix th {
  background: var(--paper-2);                    /* 必须实色，否则滚动的行会穿透 */
  border-bottom: 1px solid var(--line-strong);
  text-align: center;
  position: sticky; top: 0; z-index: 3;
}
/* 首列双向冻结（行列交叉格层级最高） */
.matrix .m-row-head {
  position: sticky; left: 0; z-index: 2;
  width: 240px; min-width: 240px;
  background: var(--surface);                    /* 必须实色 */
  border-right: 1px solid var(--line);            /* 冻结分界线，不是"描边" */
  text-align: left;
}
.matrix th.m-row-head { z-index: 4; background: var(--paper-2); }

/* 行悬停时冻结列要跟着变，否则会出现"半行变色"的断裂 */
.matrix tbody tr:hover td          { background: var(--row-hover); }
.matrix tbody tr:hover .m-row-head { background: var(--row-hover); }
```

| 项 | 规格 |
|---|---|
| 分组列宽 | 96px（内容 72px：`○ 只读` / `● 管理` 均容纳） |
| 首列宽 | 240px（库名 13/600 单行截断） |
| 分组列表头 | 12px 600 `--ink-soft`，居中，超长以 `…` 截断 + `title` 全文 |
| 单元格内容 | **字符 + 无填充色**（角色 = 形态维度，不用颜色）：`○` 只读 `--muted`／`◐` 可上传 `--ink-soft`／`●` 库管理员 `--ink` 600／无授权留空 |
| 无授权格 | 默认留空；hover 时显示 `＋`（`--line-strong`）作为"可点"暗示 |
| 可编辑格 | `cursor: pointer`；hover 底 `--row-hover` + `inset 0 0 0 1px var(--line-strong)` 内框 |
| 图例 | 表格上方 12px `--muted`，一行：`○ 只读　◐ 可上传　● 库管理员　· 点单元格切换`，间距 `--sp-4` |
| 滚动暗示 | 靠**首列右侧那条 1px 分界线** + 原生 8px 细滚动条。**不做右侧渐隐遮罩**（会吃掉最右一列内容） |
| 缺字退化 | 若目标字体缺 `◐`，改用二字 `上传`（11px），其余字符不变 |

**≤720 视口**：矩阵不可用（240px 冻结列 + 96px×N 在 390px 上只剩 1.5 列，等于没做）。改「选库 → 分组勾选清单」替代视图，沿用现有 `.user-row`（行高 48px：分组名 13/600 + 当前角色 `select.role-select` + 勾选框），**不新增组件**。

### 10.3 危险操作确认弹窗（因"回收站文案不成立"而新增）

- 顶部 **3px `--red` 通栏条**（贴顶、贯穿全宽、无圆角，靠 `overflow: hidden` 裁齐）。

### 10.5 本产品的 5 个「不可达态」（v1.4 汇总，禁止再实现）

这套系统有三个结构性事实：`GET /kbs` 恒含默认库、`GET /kbs` 只返回有 role 的库、`create_kb` 会写入创建者成员。它们让 5 个"标准后台"的状态在本产品里**永远不会出现**。已经写过的按此表回退，**不要在验收时按"设计稿都有"去补**。

| # | 原设计态 | 为什么不可达 | 正确处理 |
|---|---|---|---|
| 1 | 列表页「一个库都没有」真空态 | `GET /kbs` 恒含默认库（`kb_id==1` 兜底给 viewer） | 32px `hint-bar`「只有一个默认库…」（§5.2） |
| 2 | 列表页「不可访问」行态（`opacity .55` + 状态列「无权限」） | `/kbs` 只返回有 role 的库，无权限库不进列表 | **废弃**，不写该 CSS（§3.6） |
| 3 | 列表页「索引中」徽标 `.st-index` | `kbs.status` 只有 `active\|archived` | 移交控制台索引 `building` 态；列表侧预留不启用（§4.3） |
| 4 | 成员表「还没有单独授权的成员」空态 | `create_kb` 写创建者 `kb_admin` 成员，成员表恒 ≥1 行 | `hint-bar` 两种文案；`rows===0` 仅作兜底且改文案为「成员数据为空」（§11.5） |
| 5 | 「授权范围」列读后端字段 | 后端无 `scope` 字段，只有 `member_count` / `group_count` | 前端推导 + 列头 `title` 自曝推导口径（§10.2 第 4 条） |

> 共同教训：**"标准后台都有的状态"不等于"本产品可达的状态"**。写任何空态/异常态之前，先去读那个接口的过滤条件；不能渲染出来的状态，写进规范就是给下一个人埋一个测不到的验收项。

**推论：不可达态有两种伪装形态（v1.5）**

| 形态 | 长相 | 为什么同样是问题 |
|---|---|---|
| ① 渲染不出来的态 | 一句话状态永远不出现 | 写进规范 = 一条测不到的验收项 |
| ② **永远禁用的控件** | 该行不可能出现的按钮，灰着占位"保持对齐" | `disabled` 不可聚焦、读屏读不到、`title` 在触屏不出现；为了对齐摆一个永远用不了的东西，等于用"视觉稳定"换"可访问性和诚实"。**判定用 §3.12 的三分判据**：locked / forbidden 要画，unreachable 不画 |

两种都要避免。对齐问题用**右对齐 + 危险项贴最右**解决（§3.10），不用禁用占位解决。

**还有一个自己造的第 6 种**：把某个状态的行从表里抽走单独展示（例如"待审批行抽到文件表上方"），会让那个状态的徽标（`.st-pending`）在表里**永远渲染不出来**。**状态徽标存在的前提是那一行还在表里** —— 抽走行的同时要问一句"那这个状态还怎么表达"。

## 十一、详情页三张表（文件 / 成员 / 分组）

三张表都在「知识库详情」里（文件 tab 一张，成员与授权 tab 两张），**复用 §3 的 `.kbtable` 基类**（行高、表头、行态、hover、骨架、空态、圆角、唯一重线等全部继承）。本节只定义三件新东西：**列宽、收列断点、以及"多来源授权怎么不打架"**。

容器查询各自命名（`ftable` / `mtable` / `gtable`），因为三表可能同屏上下堆叠、可用宽度相同但列数不同，不能共用一个容器名。三表断点汇总见 **§11.9**（前端照那张表写，不必逐节读）。

> **为什么「人数」保留为独立列，不并进次行**（与 UX 附录 D3 的唯一分歧）：
> 1. 「哪个组人数多」是**治理问题**，需要竖向扫读比较、并且可排序。塞进次行只能横着逐行读，72 个组的场景直接失效。
> 2. §11.4 用**字重 600** 表达 ≥20 影响面，这需要一个独立的数字位置；次行里混合"12 人（3 未激活）"时，加粗哪几个字符会变得随意。
> 3. 成本从「分组」列出（min 200 已够放次行），不是从别的列挤 —— 总宽 716 仍在 740 容器内。
> 收窄到 4 列时人数**并入次行**（`12 人 · 3 未激活`），此时已无扫读比较需求，是合理的降级。
> **收窄到 4 列、人数并入次行后，字重规则不随之改变**（`<b>24</b> 人 · 3 未激活`，≥20 仍是 600）—— 规格在 **§11.4 第 1 条**，本节不复述。理由只有一句：收列可以减信息位，**不能减语义**（UX 附录 C 的建议，已采纳）。

### 11.3 角色 + 授权来源：双授权怎么不打架

**核心规则：角色徽标永远只有 1 个（生效角色）；多来源只在「授权来源」列用文字层级表达。**

出现两个徽标 = 用户以为一个人有两个角色 = 必须让他自己在脑子里做 `max(个人, 分组)` 的运算。这个运算应该由界面做完，用户只读结论。

**角色列**（`.role`，沿用 §4.5「角色 = 字重维度，零颜色」）：

| 值 | 文字 | 样式 |
|---|---|---|
| `viewer` | 只读 | 13px / 500 / `--muted` |
| `editor` | 可上传 | 13px / 500 / `--ink-soft` |
| `kb_admin` | 库管理员 | 13px / 600 / `--ink` |

角色后必须带 `title`，说明这个结论怎么来的：`生效角色来自 直接授权` ／ `生效角色来自 分组「财务组」` ／ `个人授权优先于分组授权，已覆盖分组「财务组」的 只读`。

**授权来源列**（`.src`，单行 13px，链式，**深色在前 = 决定者**）：

| 来源状态 | 呈现 | 样式 |
|---|---|---|
| 只有直接授权 | `直接` | `--ink` 600 |
| 只有分组授权 | `▤ 财务组` | `--amber`（沿用 §4.4 分组签） |
| 多个分组 | `▤ 财务组 +2` | `--amber`，`title` 列出全部组名 |
| **直接 + 分组（双授权）** | `直接` + `（另 ▤ 财务组）` | 前半 `--ink` 600；后半 11px `--muted` 400 |
| 库创建者（自己） | `创建者` | `--ink` 600；操作列**两个操作全禁用**（见下） |

```css
.src        { font-size: var(--fs-sm); color: var(--ink-soft); white-space: nowrap; overflow: hidden; text-overflow: ellipsis; }
.src-direct { color: var(--ink); font-weight: 600; }              /* 决定来源，在前 */
.src-grp    { color: var(--amber); }                             /* 只有分组时才用它当主色 */
.src-also   { margin-left: 4px; font-size: var(--fs-2xs); color: var(--muted); font-weight: 400; }  /* 被覆盖的那一段 */
```

- 宽度校验（按 UX 的 24 汉字最坏情况）：列内容宽 200−24 = 176px。`直接（另 ▤ 财务组）` ≈ 96px ✓；最坏情况 `个人「只读」+ 分组「财务管理组」「库管理员」` ≈ 300px **仍会溢出**，但**截断的永远是被覆盖段（次要），决定段永不被截** —— 这是"深色在前"的第二个好处。全量文字进 `title`，明细进抽屉。
- **收窄到 3 列时（容器 <660）**：`.m-source` 列隐藏，把**决定段**并入成员列次行：`@zhangsan · 决定来源：直接`。只并决定段、不并被覆盖段 —— 决定段通常很短（`直接` 或一个组名），被覆盖段才长。这样既不截断关键信息，也不会因为没有长度余量而把"更严格的那一方"吃掉。
- **不要用删除线**标被覆盖的来源 —— 看起来像纠错，在权限表里会让人怀疑数据出错。
- **不要给被覆盖的分组单独一行** —— 一个成员的授权来源必须能被一眼读完（这是"我在改谁"的判断依据）。

**操作列的禁用档位（4 档，v1.4 补；v1.7 加"类型"列）**

禁用态视觉按 §11.8「文字按钮禁用态」：**换 `--muted`，不加 `opacity`**（文字按钮没有边框底色撑形），`cursor: not-allowed` + `aria-disabled="true"` + 保留 `tabindex`，**不移除按钮、不改布局**。

| 档位 | 对象 | 改角色 | 移除 | 类型（§3.12） | `title` |
|---|---|---|---|---|---|
| 1 | 创建者 | **禁用** | **禁用** | **forbidden**（规则在别处无落点 → 画） | 改角色：`创建者恒为库管理员，请添加其他成员作为库管理员`／移除：`创建者不可移除` |
| 2 | 其他 `kb_admin` | 可 | 可 | — | — |
| 3 | `editor` / `viewer` | 可 | 可 | — | — |
| 4 | 库里唯一的 `kb_admin`（非创建者）降级时 | **提交前拦截** | — | locked（需先加另一管理员） | `该成员是当前唯一的库管理员，请先指定另一名库管理员` |

> **为什么创建者要禁两个操作**（UX 提出的加码，我采纳）：后端 `remove_member` 的条件是 `AND role != 'kb_admin'`，所以"先把创建者降级成只读、再移除"是**两步就能绕过**的门槛。只禁「移除」不禁「改角色」，等于给了一条绕行路径，最后会得到一个"显示为只读、移除按钮灰着"的怪东西 —— 比两个都禁更让人困惑。**禁用要禁在"能让约束失效的那一步"上，而不是禁在约束最终触发的那个按钮上。**

档位 1 的类型是 **forbidden**，既不是 locked，也不是"例外"：谁都解不开，且"创建者不可移除"这条规则在界面别处没有落点（来源列只写「创建者」这个身份，读不到这句话），所以**要画**并给规则原句 —— 这是 §3.12 判据的正例。判据原文、决策程序与 `title` 的两种合法写法统一见 **§3.12**，本节不复述。

### 11.4 人数 ≥ 20 的组要不要在行内提示"影响面大"？

**结论：行内不加警示色、不加警示徽标。** 三层处理，一层都不新增颜色：

1. **量级靠字重**：人数 ≥ 20 时数字从 `--ink` 500 提到 **600**，并加 `title="该分组 24 人，改动将同时影响 24 人"`。**收窄到 4 列、人数并入分组列次行时这条不变**：`<b>24</b> 人 · 3 未激活`，`<b>` 仍是 600 —— 否则收窄后"影响面大"这条唯一线索就消失了（收列可以减信息位，不能减语义）。
2. **护栏放在确认环节**：对 ≥ 20 人的组改角色 / 解除授权时，确认弹窗内出现一行 12px `--amber` 文本「本次改动影响 24 人」，正文列受影响账号前 3 个 + 「等 24 人」。这是 amber 的合法用途（等你确认）。
3. **行内禁止 amber 徽标**：6 列表格里一行突然一个橙色，多行可能同时触发，amber 立刻贬值（违反 §4.5 色彩预算）。**"影响面"是操作后果，属于确认环节，不属于列表。**

阈值固定 **20 人**（≈ 一个部门），不做配置。理由：可配置的阈值等于没人配，最后会变成"全部 0 或全部 999"。

### 11.5 三表共用规则（补齐易漏项）

- **行高**：默认舒适 48px（次行 = `@账号` / `3 未激活` / 文件元信息），紧凑 40px 时次行消失 —— 与 §3.4 完全一致。
- **可排序列**：文件表仅 **上传时间**；成员表仅 **授予时间**；分组表 **人数 / 授予时间**。角色与来源不可排（聚合/推导值，排序无意义）。
- **基准顺序（默认排序）不能用后端返回顺序**（v1.4 补）：
  - **成员表**：后端 `list_members` 是 `ORDER BY role, username`，按**字符串**排 → 实际是 `editor → kb_admin → viewer`，库管理员被夹在中间。必须在前端按角色权重降序重排：`kb_admin → editor → viewer`，同权重按姓名/账号升序。取消排序（第三态）时回到这个基准序。
  - **分组表**：人数降序（影响面大的先看到），组名升序兜底。
  - 列表页（知识库）保持 §3.5 的编码升序。
- **复选框**：只有**文件表**有（文件才是批量操作对象：批量下载/批量删除）。成员表与分组表**不加**（见本节末）。
- **空态**（容器内，版式同 §5.2）。注意成员表 `rows === 0` **不可达**：`create_kb` 会把创建者写成 `kb_admin` 成员（`workspace.py:220`），所以成员表恒有 ≥1 行。
  - **成员表 `rows === 1` 且无分组授权**（可达常态）→ 用 32px `hint-bar`：`· 目前只有你（创建者）能访问这个库。` + 文字按钮「添加成员」/「按分组授权」。
  - **成员表 `rows === 1` 且有分组授权** → `hint-bar`：`· 除你之外没有单独授权的成员；当前 3 个分组（24 人）可访问本库。` + 「添加成员」。
  - **成员表 `rows === 0`（兜底，正常不会出现）** → 空态文案写 `成员数据为空` / `未读到创建者记录，请刷新或联系平台管理员。` —— **不要写"还没有单独授权的成员"**，那会让人以为这是正常状态。
  - **分组表 `rows === 0`**（这是**可达**真空态）→ 空态：「还没有整组授权」/「按分组授权后，组内成员（含之后新加入该组的账号）自动获得权限」/ 动作「整组授权」。**这句副文案是"分组授权覆盖未来成员"的唯一可见说明，不允许省略。**
- **人数为 0 的组**：显示 `0`（`--muted`），**不用 `—`**。依据 **§3.8 例外登记 A**（空组是可清理的动作对象，必须让人看见；`—` 会让人以为数据缺失）。
- **成员表 / 分组表不做批量**：不加复选框列。权限是低量、单项、高风险的决策，批量改权限的收益远小于误操作代价（文件表另当别论，见 11.8）。

### 11.7 成员列显示降级（`display_name` 拿不到时）

`GET /kbs/{id}/members` 只返回 `username`；`display_name` 需要 `GET /admin/users` 映射，而那是**系统管理员**权限。所以普通库管（`kb_admin`）看到的是用户名，不是姓名。这不是 bug，但会直接把列宽估算打偏 —— 按人名（3 个汉字 ≈ 39px）定宽，实际来一个 `zhangsan` 就截断。

| 数据情况 | 成员列主字段 | 次行 |
|---|---|---|
| 有 `display_name` | 姓名，13/600 `--sans` | `@username`，12 `--mono` `--muted` |
| 无 `display_name` | `username`，13/600 **`--mono`** | **不显示次行**（避免同一串字符出现两次） |

- 宽度校验按较坏情况：`zhangsan` 8 字符 × 7.8px ≈ 62px；12 字符 ≈ 94px，均远小于 200−24 = 176px ✓。
- 降级时**不要**弹错误、不要显示"未知用户"、不要留空 —— 用户名本身就是有效标识（这是内部系统的账号，员工认得）。
- 主字段是 `username` 时用 `--mono`：等宽字形本身就是"这是账号不是姓名"的视觉信号，比加标签更省地方。
- 若某个成员的 `display_name` 与 `username` 相同，按"无 display_name"处理（同样不出次行）。

| `approved` × 非库管 | `下载` | 24 ✓ |

**审批预览仅支持文本类，二进制类一律下载（v1.11 定案，不留待办）**

`预览` 只对 `md` / `txt` 有效；`pdf` / `docx` / `xlsx` / `pptx` 只有 `下载`，`title` 统一为 `该类型无法在线预览，下载后查看`（现有实现已如此：`app.js` 只在 `md` 时 push 预览按钮，其余渲染诚实提示）。**不引 pdf.js**，四条理由记在此处，避免以后被重新提出：

1. **包体不匹配**：legacy build ≈ 1MB gzip（worker 另计），与「无构建、`vendor/` 只放两个小库」的纪律冲突。
2. **失败形态更糟**：worker 加载失败时 Safari 静默降级为空白页 —— 用户看到白屏，比「无法在线预览」的诚实提示更坏。
3. **安全链路**：审批的前提是「读不到内容就不该批准」。浏览器里**渲染出来 ≠ 内容被审过**，滚动两屏就点批准和没读一样；强制下载反而让审批动作变重、变慢。
4. 未来真要做，走**服务端抽取**（入库时对二进制跑文本提取，审批弹窗给纯文本），那时才有依赖管理可言。

> **要重启这个话题，请先驳第 3 条，别拿"PDF 浏览器能原生渲染"当理由 —— 那正是被否决过的那个论据。**
> 第 1、2 条对 PDF 都不是决定性的（浏览器确实能原生渲染 pdf，不需要第三方库）；真正一票否决的是第 3 条：**渲染出来不等于内容被审过**。前两条只在讨论 docx/xlsx/pptx 时成立。
> **不写"哪条论据已被否决"，等于邀请别人再提一次。** —— 一份写了理由的规范，还要写清"哪条理由不算理由"。

- **`审批` 不常驻**（v1.8：原 v1.6 的常驻禁用方案已随裁定撤回）。已入库行不渲染灰色「审批」—— 按 §3.12 判据它属 **unreachable**（已入库是终态，这一行没有任何操作能让它重新可用，没有钥匙），所以不画。
- **"位置恒定"在不渲染方案下已成立，不需要占位来保证**（几何推导，UX 提供）：按钮等宽（2 字 = 24px）、间距恒 12px、整体右对齐 ⇒ 从右边缘起算，`删除` 恒在右数第 1 格、`下载` 第 2 格、第 3 格（`审批`/`预览`）有无只改变最左侧空白的宽度，**每个存在的按钮 x 坐标都是常量**。变的只有最左那一段空白，而空白跳动不构成视觉噪声。
- **库管在 `pending` 行不放「预览」**：`审批`+`预览`+`下载`+`删除` = 4 个 = 132 > 100（124−24）会顶出列。预览下沉到**点行进抽屉**与**审批弹窗正文** —— 顺带把"盲批"从"多一个按钮"升级成"看不到内容就批不了"。
- **非库管在 `pending`/`rejected` 行是零按钮**（后端没有"上传者可下载自己未审批文件"的例外）。**操作列空态留空单元格，不写 `—`** —— 依据 **§3.8 例外登记 B**（`—` 表示"数据缺失"，而"你当前没有可执行操作"不是缺失，写 `—` 会让人以为漏渲染）。
- **待审批行留在文件表内**（`.st-pending` + 基准序置顶 + 参与复选框批量批准），**不要单独抽到表格上方的独立列表**。抽上去会让 `.st-pending` 永远渲染不出来（第 6 个不可达态）。表上方只放一条 32px `hint-bar`：`· 待审批 3 个文件` + 文字动作「全部批准」。

**文字按钮禁用态（v1.6 新增，全站通用）**

文字按钮（`.uact`、行内文字按钮）的禁用**不用 `opacity`**，用**换色**：

```css
.uact[aria-disabled="true"] {
  color: var(--muted);          /* 不保留 --blue / --red */
  cursor: not-allowed;
  /* 不加 opacity：文字没有边框和底色撑形，透明度会让它淡到读不出来 */
}
.uact[aria-disabled="true"]:hover { color: var(--muted); background: none; }
```

| 按钮形态 | 禁用做法 | 原因 |
|---|---|---|
| **文字按钮**（无框无底） | 文字换 `--muted`，**不加 `opacity`** | `opacity: .45` 的 `--blue` 会变成一层浅蓝，仍带"品牌/可点"的气质；换 `--muted` 才是"这个能力现在不存在"。且 `--muted` on `--surface` = 4.6:1，**读得出字**（用户要知道这里有什么、为什么灰） |
| 实底按钮（`.btn-primary` / `.btn-danger`） | `opacity: .45`（§10.3） | 填底按钮靠色块撑形状，换色会丢掉"这是个按钮"的轮廓 |
| 带框次按钮（`.btn-ghost`） | `opacity: .45` + 保留边框 | 同上：能看见形状，才不会让布局跳动 |

- **禁用时不保留任何语义色**：`--blue` 与 `--red` 都退成 `--muted`。颜色的职责是"能做什么"，能力没了颜色就得收回去 —— 灰色的红按钮会让人以为"这是个危险的不可用操作"，信息反而错。
- 无障碍（与 UX 一致）：用 `aria-disabled="true"` + **保留 `tabindex="0"`**，拦截点击/回车；**不用原生 `disabled`**（原生 disabled 不可聚焦 → 键盘用户 Tab 跳过、读屏用户听到的按钮数从 3 变 2，位置恒定的意义也就没了）。`title` 的写法见 **§3.12**（写"怎么做"或"规则原句"，**不要把用户已经看到的结论念一遍**）。本产品在用的两句：locked → `该成员是当前唯一的库管理员，请先指定另一名库管理员`；forbidden → `创建者不可移除`。（v1.6 在这里举的例子是 `该文件已审批，无需重复操作`，但 v1.9 起已入库行**不渲染**「审批」，这个 `title` 已经不可能出现，例句作废。）
- 禁用态**必须有可见焦点环**（`:focus-visible` 沿用全局 `2px --blue`）—— 能聚焦就必须看得见焦点。

> **已否决的做法留痕（v1.9）**：`visibility: hidden` **不用**。它看似"保留占位不保留视觉"，但本质仍是常驻方案 —— 版面里仍留着一个空槽，而那个槽的存在理由（对齐）在"不渲染 + 右对齐"下已经不成立（见上条几何推导）。记录于此只为避免以后有人重新发明它。
