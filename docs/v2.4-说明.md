# v2.4 说明：把"评测说自己好"改成"评测敢说自己差"

v2.3 解决了格式与规模两条边界。v2.4 做的事更别扭：**回头审自己上一轮的评测结果**，
结果发现 13/15 的拒答准确率里混着一道真幻觉，另外几道是标注口径把模型冤枉了。

两条主线：

1. **格式口子再补一格**：xlsx / pptx 入库（配额表、SOP 幻灯片是技术支持最常被问的东西）；
2. **评测口径重做**：拒答判定从"关键词命中"改成三态（pass / partial / fail），
   并修掉两处 substring 误伤；同时给生成 prompt 加了第 10 条「术语不可替换」规则。

---

## 一、格式：xlsx / pptx 入库

### 怎么抽

| 格式 | 抽法 | 关键取舍 |
|---|---|---|
| `.xlsx` | 每个工作表一段，每行转成 `列名=值；列名=值` | 不用裸的 `a \| b \| c`：切块是 800 字符硬切，一行被切走时只有带列名才知道每个数字是什么 |
| `.pptx` | 每页一段，含组合形状、表格、**演讲者备注** | 备注里常写"这个口径来自哪次会议"，是最有价值的一句 |

细节：

- **公式**先取缓存值（`data_only=True`）；文件从没被 Excel/WPS 打开保存过时缓存为空，
  自动退回读公式文本，并在 `note` 里说明，避免"表格入库成功但一个字没有"。
- **超大表**按 `SHEET_MAX_ROWS=5000` 行截断，`note` 里写明哪张表被截了。
- **旧格式**（.xls / .ppt / .doc）不硬撑，直接告诉用户"请另存为 .xlsx 后再上传"——
  比起含糊的"不支持该格式"，用户知道下一步该干什么。
- **白名单单点化**：上传校验、建库扫描、前端 accept 全部指向 `extract.SUPPORTED_EXTS`，
  原来 `workspace.py` 里那份手抄的 `ALLOWED_FILE_EXTS` 已删（两处漂移是 v2.3 踩过的坑）。

### 实测

用两份自造文件验收（`temp/fmt/`，不入库）：

```
腾讯会议版本配额表.xlsx  → 265 字符 / 2 个工作表 / engine=openpyxl
  版本=企业版；同时在线人数=2000；单个会议时长上限=不限；联席主持人=50 位；云录制空间=100 GB
存储桶运维SOP.pptx       → 156 字符 / 2 页 / engine=python-pptx
  【第 1 页】存储桶删除 SOP / 备注：本页口径来自 2026 年 9 月运维例会…
```

边界用例：空表 → `未抽出任何文字`；坏 zip → `解析失败，原文可能已损坏`；
`.xls` → `请另存为 .xlsx`；缺依赖 → `缺少解析 .pptx 的依赖`（不会 500）。

## 二、评测口径：三态 + 两处误伤

### 起因：一条被"判对"的幻觉

q020 问「腾讯会议可以设置几个联席主持人」，知识库里只有「指定主持人，最多 10 位」。
模型答：

> 腾讯会议最多支持设置 10 个联席主持人。该功能称为"指定主持人"…
> 当您**不在**会议中时，被指定的成员将优先成为主持人。

旧判分器把「不在」当成拒答标记词（表里还有「不能」「建议您」「知识库」「人工」），
substring 一匹配 → `said_refuse=True` → 判为"正确拒答"。**一条把两个功能混为一谈的错答，
在报表上变成了加分项。**

### 改法

`eval/grading.py` 统一口径，`run_eval.py` 与 `recheck.py` 都改成调它：

- 拒答标记只用**整句表达未覆盖**的强短语（`无法确定` / `资料未包含` / `知识库中没有` / `没有相关文档`）；
- 「建议通过官方渠道 / 转人工」这类礼貌尾巴只在答案**前半段**出现才算拒答；
- 三态：

| 判定 | 含义 | 为什么单列 |
|---|---|---|
| `pass` | 首句就在说"资料未覆盖"，且无泄漏 | 用户第一眼就读到"不知道" |
| `partial` | 先给结论，后面才补"资料未包含具体步骤" | 最危险的一种：大多数人只读第一句 |
| `fail` | 通篇没拒答，或命中禁答内容 | 真错答 |

- 新增 `must_not_regex`：给单题留"禁答正则"的口子。`must_not_contain` 是 substring，
  拦不住「最多可以设置」→「最多支持设置」这种一字之差，也容易把「已删除标记对象」
  误判成「已删除」（q025 就被这条冤枉过）。

### q018 / q020 的标注复核结论

| 题 | 原标注 | 复核结论 | 处置 |
|---|---|---|---|
| q018 | 禁「转低频」 | 库内确有"低频存储"这个概念，模型说"能转"不算编造；真正缺的是**配置步骤** | 去掉「转低频」，改禁"首句直接说可以配置" |
| q020 | 禁「最多可以设置」 | 库内**没有**「联席主持人」，只有「指定主持人」——两个不同角色 | 保留应拒答，新增正则拦"10 位联席主持人" |

## 三、生成侧：规则 10「术语不可替换」

只改评测不改生成，等于把尺子校准了却不管刻度。所以同步加了 prompt 规则：

> 问的是专有名词（功能名/角色名/配额项）时，只有资料里出现该名词本身才可作答；
> 资料里只有名字相近的另一功能 → 视为未覆盖，**第一句就说明**，不得做"应理解为"式等价推断，
> 也不得把相近功能的数字安上来。
> 只约束专有名词：普通动词近义（「新增成员」vs「创建成员」）不算不一致，该给的接口照给。

最后这句是**必须**的：第一版规则没写这句，结果 q008 从"给出 `user/create` 与完整请求格式"
退化成"调用创建成员 API"一句话——术语规则把正常答题也吓保守了，`must_contain` 掉到 86.7%。

## 四、结果（标准集 30 题，各自独立整轮）

| 轮次 | must_contain | 拒答(严) | 拒答(宽) | 半拒答 | 标识符幻觉 | P95 |
|---|---|---|---|---|---|---|
| v2.3 旧口径（E7-final-30） | 100% | 86.7%① | — | — | 11 | 18.6s |
| E8（规则 10 初版，无例外句） | 86.7%② | 80% | 93.3% | 2 | 8 | 18.4s |
| E9 + E9b（规则 10 定稿，两轮） | 100% / 93.3%③ | 86.7% / 86.7% | 93.3% | 1 / 1 | 4 / 5 | 22.4s / 18.2s |
| E10（规则 5 加术语例外） | 见下节 | | | | | |

① 旧口径把 q020 的幻觉算成了拒答，这个 86.7% 是虚高；
② 术语规则写过头，把 q008 的正常答题也压掉了；
③ q008 是单题噪声：同一份代码两轮一轮写全、一轮只写一句话。

**结论：把口径改诚实之后，账面数字变难看了（拒答严 86.7%），但每一分都能对上具体题号。**
汇报里把 q018 的 partial、q020 的 fail 明写出来，比报一个 93.3% 更有说服力——
评委只要抽查一题就能验证。

## 五、还没做的（如实记账）

- **q020 仍拦不住**：模型先给"10 个"，再自己承认"资料中未出现联席主持人"。
  这是"近邻概念"问题，靠 prompt 只能压到 partial，要彻底解决得在检索层判断
  "问题名词的语义最近邻是否是另一个功能"，成本高、误杀风险大，暂列 P2。
- **规模仍是单机**：chromadb 单进程 + 20k chunk 上限，十万级要换 ES / Milvus。
- **OCR 按页计费**：扫描件默认只处理前 `OCR_MAX_PAGES` 页，超出的页在 `note` 里报数。

## 六、线上验收发现的两个问题（比跑分更重要）

跑分全过之后照例做了一遍线上验收：上传一份 Excel → 问表里的数字。**第一次没答出来。**

### 6.1 多库检索的"名额垄断"

- **现象**：新建一个库，上传 5KB 的配额表（1 个 chunk），问"企业版联席主持人上限是多少"，
  系统答"资料未包含"，`sources` 里只有默认库的文档。
- **定位**：直接调 `hybrid_search(db, q, 8, ['default','4'])` 打印候选——
  默认库 185 个 chunk 把 top-8 全占了，新库的切片排在第 9 名之后；
  只查 `['4']` 时排第 1。**不是权限过滤错，是全局 top-k 让大库吃掉全部名额。**
- **为什么这条路以前没暴露**：评测集 40 题全在默认库里跑，从来没测"跨库混合"。
- **修法**：多库时按库分配额——每个库各取 `per = max(2, ceil(k*2/库数))` 个候选（向量 + BM25 各一份），
  再用同一套 RRF 合并。embedding 只算一次（`similarity_search_by_vector`），不随库数增加重复向量化。
- **效果**：同一问题，配额表切片从「进不了 top-8」变成「排第 1」，答案给出「50 位」并正确引用该表。
- **代价**：库多时向量查询次数 = 库数（本地 SQLite，单次约十几毫秒）；相关性由 doc_grader 兜底。

> 一句话：**"我刚传的你就该知道"是用户心智，全局 top-k 会违背它。**

### 6.2 引用行露出容器路径

- **现象**：上传文件的引用写成 `参考：/app/backend/db/kb_files/4/780a7c84_腾讯会议版本配额表.xlsx`。
- **根因**：G2 校验通过后直接回填模型原文，而 `source` 元数据是容器内绝对路径。
- **修法**：`verify_citations` 命中白名单后，把引用行**重写成白名单里的文档名**
  （顺带去掉上传时加的 `780a7c84_` 随机前缀与 `_609ecc9cc2` 哈希后缀），
  正文里若还有残留文字则接在引用行之后。
- **回归**：六种引用形态（占位符 / 整条路径 / 标题代文件名 / 一行多文档 / 伪造 / 无引用）逐个验过，
  伪造引用仍然整段降级。
