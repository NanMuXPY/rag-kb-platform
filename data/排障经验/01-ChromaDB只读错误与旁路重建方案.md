# ChromaDB 只读错误排查与旁路重建方案

## 现象

重建向量索引时，删除 Chroma 目录后新建同名路径的库，或原地清空 collection 后重新写入，均报错 `readonly database`，且删除文件、修改权限均无法解决，只能重启进程。

## 原因

Chroma 底层依赖 SQLite。PersistentClient 按**路径**缓存连接单例：目录被删除重建后，旧连接仍指向已删除的旧 inode（文件句柄未释放），对新路径的写入全部落到失效句柄上。原地清空 collection 也一样——连接内部的锁状态比文件系统更深层，`rmtree` 级别的清理都不够。

## 解决方案：旁路重建

不要在原路径上动手术，而是：

1. 把新库建到一个**全新路径**（如 `db_md_rebuild`），新路径意味着新连接，完全绕开旧锁；
2. 新库写入完成后，把旧库目录改名备份（如 `db_md_old`），再把新库目录**原子改名**为正式路径；
3. 调用 `os._exit(0)` 直接退出进程，由 Docker Compose 的 restart 策略拉起新进程；
4. 新进程启动时用状态文件（放在持久化卷里）判断"刚完成重建"，直接加载新库。

## 关键注意点

- 如果数据目录本身是 Docker **bind mount 挂载点**，`rename` 会报 `Device or resource busy`——解决办法是把挂载点上移一层到父目录，让数据目录变成挂载点下可改名的普通子目录。
- 进程退出到重新拉起约有 20 秒空窗，前端应通过状态轮询接口消化这段不可用时间，而不是直接报错。
- 重建必须纳入"已批准"的正式文件清单，避免重建后把待审批文件也索引进去。
